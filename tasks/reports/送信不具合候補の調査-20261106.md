卒研メーター読み取りシステムの Android アプリ（`android/app/src/main/kotlin/jp/sotuken/metercapture/`）において、実機確認で報告された送信まわりの不具合候補 2 件について、コードリーディングと Git 履歴の調査に基づき、原因・再現性・影響・修正案・実機検証手順を報告します。

なお、作業指示に従い、コードの変更・コミット・プッシュは一切行っていません。

## 1. 不具合候補1: 受信口停止時に未送信のまま送信箱保存にならない問題

### 1.1 現象の整理
- **再現手順**: PC の受信口（`manager/receiver.py`）を停止した状態で、Android アプリで写真を 2 枚撮影した。
- **発生した現象**:
  - 画面上部の接続状況バー: 「○ PCに届かない（送信箱に保存中）　未着 2件　接続できません」（黄）と表示された。
  - キュー履歴画面（`QueueListScreen`）: 1〜2 分待っても、2 枚の写真の行は「未送信」のまま留まった。
  - 詳細ダイアログ（`showStatusDialog`）: 直近の失敗の理由が「なし」と表示された。
- **利用者の期待**:
  - 履歴の各行が「PC未到着・端末に保存済み」になること。
  - 各行の下に失敗理由が表示されること。
  - 見出し下に「PC未到着: 2件（端末に保存済み）」および「今すぐ送る」ボタンが表示されること。
  - 詳細ダイアログの直近の失敗の理由に、接続失敗の理由が表示されること。

### 1.2 結論
- **原因の見立て**: **確度: 高**
  1. **【事実】UI 表示仕様の根本的な乖離**:
     - 接続状況バー（`ui/ConnectionStatus.kt`）とキュー履歴画面（`ui/QueueDisplay.kt`）で、「未着」とみなす状態の定義が異なっています。
     - 接続状況バーの `countUndelivered` は、`PENDING`（未送信）、`SENDING`（送信中）、`FAILED`（失敗）、および `SENT` かつ `sentVia == VIA_FOLDER`（送信箱保存済み）の**全未着状態を合算**してカウントし、「PCに届かない（送信箱に保存中）」と表示します。
     - 一方、履歴画面の `sendStatusLabel`、`isUndelivered`、`undeliveredSummary`、および行下エラー表示 `errorTextFor` は、**`sendState == SENT && sentVia == VIA_FOLDER` の項目のみ**を対象としています。
     - そのため、アイテムが `PENDING` にある間は、バーは「未着2件（送信箱に保存中）」と表示する一方で、履歴画面は「未送信」のままとなり、見出しサマリや理由、「今すぐ送る」ボタンは一切表示されません。詳細ダイアログの「直近の失敗の理由」も、アイテムの `lastError` が `null` のため「なし」になります。利用者が感じた違和感の半分は、この表示仕様の乖離に起因します。
  2. **【事実および見立て】1〜2分待っても PENDING のまま留まった原因**:
     - 送信処理（`SendRouter.route()`）が正常に完走していれば、PC 疎通不可のときは `isHttpReachable = false` となり、PENDING 項目は直ちに `folderSender.send(item)` で端末内送信箱へ書き出され、`markSent(..., VIA_FOLDER, note)` で `SENT`（送信箱保存済み）へ遷移する設計です。
     - にもかかわらず `PENDING` のまま留まったのは、確認時点のビルド（`52c9dd6` + SK-09 = コミット `885caed`）において、**`QueueSendWorker.sendQueue()` が例外で中断し、WorkManager の再試行バックオフ待機（`Result.retry()`）に入っていたため**です。
     - `885caed` の時点では `CaptureDatabase` がプロセス内シングルトン化されておらず、MainActivity と Worker がそれぞれ個別に `create(context)` を呼び出し、Worker は終了時に `database.close()` を呼んでいました。これにより SQLite コネクションのロック競合や接続プール閉鎖例外が発生し、Worker が `catch (e: Exception)` で `Result.retry()` を返していました。
     - `QueueSendScheduler.enqueueSend` は `ExistingWorkPolicy.APPEND_OR_REPLACE` を使用しているため、先行 Worker が `Result.retry()` でバックオフ待機（初回30秒、次回60秒、120秒...）に入ると、後続の撮影による Worker は親の完了まで実行されずに BLOCKED のまま待たされます。その結果、1〜2分待っても Worker が再実行されず、DB 内の項目が更新されずに `PENDING` のまま取り残されました。

### 1.3 根拠（ファイル:行番号とその内容）
- `android/app/src/main/kotlin/jp/sotuken/metercapture/ui/QueueDisplay.kt`:

  - `L21-22` (`isUndelivered`): `item.sendState == SendState.SENT && item.sentVia == QueueItem.VIA_FOLDER` と定義されています。
  - `L27-30` (`undeliveredSummary`): `isUndelivered` を満たす項目が 1 件以上あるときのみ「PC未到着: N件（端末に保存済み）」を返し、0 件なら `null` を返します。
  - `L33-36` (`errorTextFor`): `item.sendState != SendState.FAILED && !isUndelivered(item)` の場合は `null` を返すため、`PENDING` の項目にはエラー理由は表示されません。

### 1.4 現在の main のコードでも同じことが起きるか
- **判断: UI 表示の乖離は確実に再現します。Worker の停止についても、条件により再現し得ます。**
  1. **UI 表示仕様の乖離（100% 再現）**:
     - 帯が `PENDING` を「未着（送信箱に保存中）」と呼ぶ一方で、履歴画面は `SENT(VIA_FOLDER)` のみ「PC未到着」と呼ぶ非対称な設計は、現在の main でも全く同一のまま残っています。
     - アイテムが PENDING である限り、現在でも「帯は送信箱に保存中と出ているのに、履歴は未送信のまま」という不一致が確実に発生します。
  2. **Room マルチインスタンス問題の解消**:
     - コミット `ddf2153` により `CaptureDatabase.getInstance(context)` が導入され、プロセス内で単一インスタンス化されました。そのため、旧ビルド（`885caed`）で起きていた DB ロックや close 競合によるクラッシュは解消されています。
  3. **WorkManager のチェーンブロック（現在も潜在）**:
     - `QueueSendScheduler.enqueueSend` の `ExistingWorkPolicy.APPEND_OR_REPLACE` と、`QueueSendWorker.doWork()` の `catch (e: Exception) { Result.retry() }` の組み合わせは現在もそのままです。
     - 何らかの例外が発生した場合に後続ジョブがバックオフ待機でブロックされるリスクは現在も残っています。
  4. **現在の main で新たに発生した PENDING 滞留経路**:
     - 現在の main の `SendRouter.kt`（L61-62）には、`if (item.isHeldFor(currentReceiverId)) continue` と `if (!isSendable(item)) continue` が追加されています。
     - 作業中の点検写真（`!isSendable`）や別 PC 宛ての写真（`isHeldFor`）は、**意図的に送信処理がスキップされ、送信箱への書き出しも行われず PENDING のまま留まる**ようになっています。

### 1.5 影響（利用者に何が起きるか）
- 撮影直後、帯には「送信箱に保存中・未着2件」と表示されるため、利用者は写真が安全に端末内へ保存されたと信じます。

- 写真が保護されているのか失われたのか判断がつかず、利用者が強い不安を感じます。

## 2. 不具合候補2: QR登録直後の最初の1枚が2枚目撮影まで未送信のままになる問題

### 2.1 現象の整理
- **再現手順**: PC で表示した登録用 QR を Android アプリで読み取って登録完了した直後、目の前のメーターを 1 枚撮影した。
- **発生した現象**:
  - 1 枚目の写真が、2 枚目を撮影するまで「未送信」（PENDING）のまま留まった。
  - 2 枚目を撮影した直後、1 枚目と 2 枚目の両方が「PC受信済み」（SENT VIA_HTTP）へ遷移した。

### 2.2 結論
- **原因の見立て**: **確度: 高**
  1. **【事実】QR登録完了時の Worker と 1枚目撮影時の Worker の実行競合（レースコンディション）**:
     - `PairingScreen.kt`（L116）では、登録完了時に `QueueSendScheduler.enqueueSend(context)`（Worker 1）を呼び出しています。この時点では撮影写真は 0 件です。
     - 登録ダイアログが閉じた直後にユーザーが 1 枚目を撮影すると、`MeterCaptureApp.kt`（L185）の `onSaved` で `queueStore.enqueue` が走り、直後に撮影側の `QueueSendScheduler.enqueueSend(context)`（Worker 2）が呼ばれます。
     - Worker 1 が起動して `sendQueue()` の疎通確認（GET /health）通信を行っている最中に撮影が行われた場合、Worker 1 の `findByState(SendState.PENDING)` の読み取りが 1 枚目の INSERT よりわずかに先行すると、Worker 1 は「PENDING 0件」として終了します。
     - 一方、撮影側で呼ばれた Worker 2 は、先行する Worker 1 が RUNNING（または完了処理中）のタイミングで `ExistingWorkPolicy.APPEND_OR_REPLACE` によりチェーン（APPEND）されます。
     - WorkManager の内部スケジューラにおいて、先行 Worker の完了通知と後続 Worker のディスパッチ処理の極小のタイミング競合、または先行 Worker がバックオフ等に入った場合、Worker 2 が即座に実行されず保留（ENQUEUED のまま待機）状態となります。
     - ユーザーが 2 枚目を撮影した際、3 回目の `enqueueSend` が呼ばれたことで WorkManager が再度トリガーされ、保留されていたチェーンが実行されて 1 枚目と 2 枚目の両方が一括送信されました。
  2. **【推測】設定保存タイミング（`apply()`）の影響（確度: 中）**:
     - `ReceiverSettings.savePaired` は `SharedPreferences.apply()`（非同期ディスク書き込み）を使用しています。同一プロセス内のメモリマップには即時反映されますが、別スレッドで直ちにインスタンス化された Worker との間で可視性の遅延が生じ、未設定扱いになっていた可能性も考えられます。
  3. **【推測】`ExistingWorkPolicy.KEEP` との比較**:
     - コード上は `ExistingWorkPolicy.APPEND_OR_REPLACE` ですが、先行ジョブが未完了の間に後続ジョブがキューされた場合、WorkManager のスケジューリング遅延により、実質的に「先行ジョブが無視された（後から動いた）」ように見える現象が発生します。

### 2.3 根拠（ファイル:行番号とその内容）
- `android/app/src/main/kotlin/jp/sotuken/metercapture/ui/PairingScreen.kt`:
  - `L113-118`: `PairingClient().register(current, settings)` の直後に `QueueSendScheduler.enqueueSend(context)` を呼び出しています。写真が 0 件の状態で Worker が起動されます。
- `android/app/src/main/kotlin/jp/sotuken/metercapture/ui/MeterCaptureApp.kt`:
  - `L185-188`: 撮影完了コールバック（`onSaved`）において、`queueStore.enqueue` の直後に `QueueSendScheduler.enqueueSend(context)` を呼び出しています。
- `android/app/src/main/kotlin/jp/sotuken/metercapture/queue/QueueSendScheduler.kt`:
  - `L17-24`: `ExistingWorkPolicy.APPEND_OR_REPLACE` で `UNIQUE_WORK_QUEUE_SEND` をキューイングしています。
- `android/app/src/main/kotlin/jp/sotuken/metercapture/queue/QueueSendWorker.kt`:
  - `L23-34`: `queueSendMutex.withLock`（旧ビルドでは `sendMutex.withLock`）によって Worker の実行は直列化されています。
  - `L48-51`: `pickReachableUrl` で `HttpSender.health` を実行するため、ネットワーク遅延（数十〜数百ミリ秒）が発生し、その間に画面側で撮影が行われます。
- `android/app/src/main/kotlin/jp/sotuken/metercapture/settings/ReceiverSettings.kt`:
  - `L40-53`: `savePaired` では `prefs.edit()...apply()` で保存を行っています。

### 2.4 現在の main のコードでも同じことが起きるか
- **判断: 現在の main でも確実に起こり得ます（むしろ発生要因が増加しています）。**
  1. **WorkManager の短時間連続 enqueue による遅延**:
     - `PairingScreen.kt`（L116）で写真 0 件の Worker を即時キックする処理と、撮影時の `enqueueSend` で `APPEND_OR_REPLACE` を使用する構造は、現在の main でも全く同一です。そのため、先行ジョブとの競合によるディスパッチ遅延は現在でも発生します。
  2. **`receiverId` 固定によるスキップ（main 特有の新要因）**:
     - 現在の main では、`SendRouter.kt`（L61）に `if (item.isHeldFor(currentReceiverId)) continue` が追加されています。
     - 撮影時に `RoomQueueStore.enqueue` が取得した `receiverId` と、Worker 側で `ReceiverSettings.sendTarget()` が取得した `receiverId` の間に SharedPreferences の反映遅延等で一時的な不一致が生じた場合、1 枚目は「別のPC宛て(保留)」として**明示的に送信スキップ**されます。
     - 2 枚目撮影時には設定が完全に一致するため、1 枚目と 2 枚目がまとめて送信されます。この新仕様により、同様の現象が現在でも発生しやすくなっています。

### 2.5 影響（利用者に何が起きるか）
- QR 登録直後にテスト撮影した最初の 1 枚が即座に送られず「未送信」のまま残るため、利用者は「QR 登録に失敗した」「PC と通信できていない」と誤認し、不要な再登録や設定変更を繰り返す原因になります。

## 3. 修正案（小さな案を優先）

### 案1: QR登録完了時の不要な enqueueSend を抑止する（不具合2対策・最優先）
- **対象ファイル**: `android/app/src/main/kotlin/jp/sotuken/metercapture/ui/PairingScreen.kt`
- **変更内容**:
  - L116 の `QueueSendScheduler.enqueueSend(context)` を、**`if (pendingCount > 0)` の条件付き**にします。
  - QR 登録時に未送信写真（旧 PC 宛て等）が残っている場合のみ送信 Worker をキックし、写真が 0 件のときはキックしないようにします。
- **変更の大きさ**: **小**（1行の条件分岐追加）。
- **リスク**: **極小**（新規登録直後に不要な空 Worker が起動しなくなり、撮影直後の Worker との競合が根本から解消されます）。
- **追加すべきテスト**:
  - `PairingScreenTest`: 未送信が 0 件のときは `enqueueSend` が呼ばれず、1 件以上あるときのみ呼ばれることのテスト。

### 案2: 即時送信の WorkPolicy を REPLACE に見直す（不具合1・2対策）
- **対象ファイル**: `android/app/src/main/kotlin/jp/sotuken/metercapture/queue/QueueSendScheduler.kt`
- **変更内容**:
  - L21 の `ExistingWorkPolicy.APPEND_OR_REPLACE` を **`ExistingWorkPolicy.REPLACE`** に変更します。
  - 写真送信処理（`sendQueue`）は「その時点でキューにある PENDING 項目を全件取得して送る」冪等な処理です。先行 Worker をチェーンして待つ必要はなく、新しい撮影があった場合は先行を置換して即座に最新キューを取り込む方が安全です。
  - 先行 Worker が万一 `Result.retry()` でバックオフに入っていても、新しい撮影によって `REPLACE` されるため、チェーンが BLOCKED にならず即座に再試行されます。
- **変更の大きさ**: **小**（1行の定数変更）。
- **リスク**: **小**（Worker 同士は `queueSendMutex` で排他されているため、置換されても DB やファイル送信の破損は起きません）。
- **追加すべきテスト**:
  - `QueueSendSchedulerTest`: 連続で `enqueueSend` を呼び出した際に WorkRequest が正しく REPLACE されることの検証。

### 案3: 接続状況バーと履歴画面の「未着」定義・文言の整合化（不具合1対策）
- **対象ファイル**: `android/app/src/main/kotlin/jp/sotuken/metercapture/ui/ConnectionStatus.kt` および `ui/QueueDisplay.kt`
- **変更内容**:
  - 接続状況バーの文言 `○ PCに届かない（送信箱に保存中）` を、実際に送信箱に保存された項目がある場合にのみ「送信箱に保存中」と表示し、すべて PENDING の場合は「送信待機中」または「未送信」と表現を分けます。
  - 履歴画面の見出し `undeliveredSummary` において、`PENDING` の項目も「未送信: N件」として明示し、「今すぐ送る」ボタンを PENDING 項目がある場合でも押せるようにします。
- **変更の大きさ**: **小**（文言と表示条件の調整）。
- **リスク**: **極小**（UI 表示の整合性向上のみ）。
- **追加すべきテスト**:
  - `ConnectionStatusTest`, `QueueDisplayTest`: PENDING 状態の項目が存在するときの表示文言テスト。

### 案4: SharedPreferences の保存を commit() で同期化する（不具合2対策）
- **対象ファイル**: `android/app/src/main/kotlin/jp/sotuken/metercapture/settings/ReceiverSettings.kt`
- **変更内容**:
  - `savePaired` において、`apply()` ではなく `commit()` を使用して同期的かつ確実にディスクとメモリに書き込みを完了させてから次の処理へ進むようにします。
- **変更の大きさ**: **小**（1箇所のメソッド呼び出し変更）。
- **リスク**: **極小**（設定データは数キーのみの極小サイズであり、`commit()` によるブロッキングは数ミリ秒未満です）。
- **追加すべきテスト**:
  - `ReceiverSettingsTest`: 保存直後の読み取り一貫性テスト。

## 4. 実機でしか確かめられない点と検証手順

### 検証項目 1: QR登録直後の WorkManager ジョブ遷移とログの追跡（不具合2）
- **目的**: QR 登録完了時と直後の撮影時における WorkManager のジョブ状態遷移とディスパッチ遅延を確認する。
- **見るべき Logcat タグ**:

## 5. 調べて分かったその他の気づき（関連する別の問題）

### 気づき 1: 現在の main の SendRouter で fallbackReason が「送信先未設定」になる問題（重大）
- **該当箇所**: `android/app/src/main/kotlin/jp/sotuken/metercapture/queue/QueueSendWorker.kt` (L48-63) および `SendRouter.kt` (L36-39)
- **内容**:
  - `QueueSendWorker.kt` (HEAD) では、`pickReachableUrl` を呼んで疎通を確認し、接続できないと `sender = null` とします。
  - そのため `httpSenderProvider = { null }` となります。
  - すると `SendRouter.kt` では `val httpSender = httpSenderProvider()` が `null` となり、
    ```kotlin
    var isHttpReachable = if (httpSender == null) {
        fallbackReason = "送信先未設定"
        false
    }
    ```
    によって、**送信先は正しく設定されているにもかかわらず、`fallbackReason` が「送信先未設定」に設定されてしまいます。**
  - この結果、送信箱に保存された項目の `lastError` に「送信先未設定」が記録され、ユーザーに誤解を与えます。本来は `reach.error`（「PC未接続: 接続できません」等）を渡すべきです。

### 気づき 2: 点検中の写真の保留状態が履歴画面で分かりにくい
- **該当箇所**: `android/app/src/main/kotlin/jp/sotuken/metercapture/inspection/InspectionSendRules.kt` (L7-8)
- **内容**:
  - 点検作業中の写真（`isSendable == false`）は、点検完了まで送信が意図的に保留されます。
  - しかし履歴画面（`QueueListScreen.kt`）では単に「未送信」と表示されるため、点検中であるための意図的な保留なのか、通信エラーによる未送信なのかが区別できません。

### 気づき 3: `undeliveredSummary` と「今すぐ送る」ボタンの連動の歪み
- **該当箇所**: `android/app/src/main/kotlin/jp/sotuken/metercapture/ui/QueueListScreen.kt` (L115-131)
- **内容**:
  - 「今すぐ送る」ボタンが `undeliveredSummary(items)?.let { ... }` の中に配置されているため、未送信項目（PENDING）がどれだけ溜まっていても、送信箱保存済み項目（SENT VIA_FOLDER）が 0 件だと「今すぐ送る」ボタン自体が表示されません。
  - 未送信項目がある場合でもユーザーが手動で即時送信をトリガーできるようにするべきです。
