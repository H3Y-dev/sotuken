`tools/demo_catalog.py` の契約

- `load_catalog(path: Path) -> list[dict]` は列順・列数・ID順・ID重複・名前重複を検査し、CSV順に返す。型は `sweep_deg` が整数、`min_value/max_value` が有限の数値、許容範囲が有限の数値または `None`、2つのフラグが真偽値、残りが文字列。台帳の全行で列挙値、目盛り定義、`build_payload(id, name, unit, min, max)` を検査する。不正なら行番号と理由付きで `ValueError`。
- `appearance_key(device: dict) -> tuple` は `meter_key,sweep_deg,dial_color,number_position,font,needle_shape,needle_color,bezel_color,danger_band,max_pointer,unit,min_value,max_value` の順の組を返す。2台に同じ組があれば、エラーに両方のIDを出す。名前や許容範囲で外観を区別しない。
- `check_catalog_history(previous: list[dict], current: list[dict]) -> None` は旧IDの削除、旧IDの名前・外観変更、旧集合の最大番号以下への新規追加を拒否する。`python -m tools.demo_catalog --previous <旧CSV>` は規定パスの現行台帳と比較する。初版は `--previous` なし。以降のPR受入では `git show <PRのベースSHA>:eval/demo_devices.csv` のUTF-8内容を一時CSVに書き、旧CSVを指定する。生成器の外観定義を変更するPRでも旧IDを再解釈しない。今回取り込むレンダラーを初版として固定する。

## 2. 画像の生成

### 配布と呼び出し

`tools/meter3d/meter3d.html`、`tools/meter3d/batch/generate.cjs`、`tools/meter3d/batch/final_set_plan.cjs` を外部ソースからコピーする。依存している `final_set_plan.cjs` も同じ版を使う。コピー前に3ファイルのSHA-256を採取し、`tools/meter3d/README.md` に記録する。READMEに実行条件、`CHROME_PATH` の設定例、Three.jsの固定URL、外部 `DESIGN.md` と `batch/README.md` を参照したことを記す。Nodeのnpmパッケージは不要。後処理ツール `postprocess.py` は見本として扱い、台帳と真値の結合はPython側で行う。

`python -m tools.generate_demo_photos` はリポジトリ直下の `demo/photos/` を新規に作る。既にあれば終了コード1。画像、Chromeプロファイル、生成器の生出力は `demo/` 内に収める。実行前にHTMLとJSのハッシュが取り込み時の値と一致することを確かめる。検査後、3ファイルを同じ相対配置のまま `demo/photos/renderer/` にコピーし、コピー先の `batch/generate.cjs` を実行する。生成器がレンダラー直下に作る `.checks/` とChromeキャッシュもこの作業用コピーに収まる。フォントの対応はレンダラー既定の Arial、Georgia、Courier New。Chrome・描画環境を変えた場合のPNGのバイト一致は受入条件から外し、外観と条件の一致を確認する。

`tools/generate_demo_photos.py::render_frame(device: dict, shot: int, raw_dir: Path) -> tuple[Path, dict]` は1条件ずつレンダラーを呼ぶ。引数配列で起動し、終了コード0を必須とする。タイムアウト90秒。出力先は `demo/photos/raw/<ID>/<shot>/` とし、子プロセスの `--out` に絶対パスを渡す。次の値を引数にする。

| 引数 | 値 |
|---|---|
| --meters | CSVの meter_key 1件 |
| --values, --cameras, --lightings | 下表の各1件 |
| --distance | 5.6 |
| --seed | 1000 + IDの末尾番号 × 10 + shot |
| --sweep-deg, --dial-color, --number-position, --font, --needle-shape, --needle-color, --bezel-color, --danger-band, --max-pointer | CSVの対応列を1値ずつ。真偽値は小文字 |
| --glass-scratches, --sensor-noise | 下表の値 |
| --out | フレーム固有の raw_dir |

他の劣化・盤面への追加印字は既定の0。`--legacy-grid` と `--final-set` は渡さない。外観設定を配列で巡回させる機能は使わない。生成器の `manifest.json` の `frames` が1件であること、その `file` と `json` が raw_dir 内の実在ファイルを指すことを確認する。`frames[0]` の真値・範囲・外観と個別JSONの単位を読み、台帳と照合する。真値は `min_value + (max_value-min_value) * 値割合 / 100` に絶対誤差 `1e-8` 以内。外観は指定全項目が一致すること。

| shot | 値割合 % | yaw:pitch | 照明 | 傷 | ノイズ |
|---:|---:|---|---|---:|---:|
| 1 | 7 | 0:0 | normal | 0 | 0 |
| 2 | 48 | 30:0 | glare | 0.2 | 0.08 |
| 3 | 93 | 0:25 | normal | 0.35 | 0.15 |
| 4 | 27 | 45:0 | normal | 0.1 | 0.04 |

全台にshot 1〜4を生成する。初版は80枚。shotの値・角度・照明・劣化だけを変更する。

### QRと真値

偶数IDは元のPNGをそのまま使い、送信時に `device_id` と `device_name` をサイドカーに付ける。奇数IDは写真右にラベルを置き、PC側の読み取りを試す。元の1280×960の右に背景色 `#e5e7eb` の幅256 pxの帯を足す。ラベルは左上 `(1296, 64)`、224×224 px。QRはレベルM、余白4モジュール。既存の `tools/embed_qr_into_synthetic.py::create_qr_plate` に後方互換のキーワード専用引数 `unit=None, min_value=None, max_value=None` を追加して再利用する。関数内の `build_payload(device_id, device_name, unit, min_value, max_value)` に渡し、モジュールの境界が揃うよう、範囲付きQRは希望幅200 px以下で最大の整数倍で描く。既存呼び出しの描画は維持する。許容範囲はQRに含めない。生成した全40枚のラベルから `manager.qr_decode.read_device_qr` でIDを取得し、さらにOpenCVのデコード文字列を `parse_payload` に渡して名前・単位・最小最大を照合する。失敗したフレームがあれば画像生成を失敗にする。縁・針・目盛りにはラベルを重ねない。

公開用画像は `demo/photos/frames/<ID>-<shot>.png`。最後に `demo/photos/groundtruth.json` をUTF-8で書く。トップレベルは `{"v":1,"frames":[…]}`。ID昇順、shot昇順。各要素は `file,sha256,device_id,device_name,appearance,shot,seed,true_value,unit,min_value,max_value,value_percent,yaw_deg,pitch_deg,lighting,glass_scratches,sensor_noise,qr_bbox`。fileは photos からのPOSIX相対パス、sha256は最終PNGの小文字64桁、appearanceは外観組の列名付きオブジェクト、qr_bboxは `[1296,64,224,224]` またはnull。公開用画像80枚のSHA-256は相互に一意とする。生出力とファイル名が同じでも、結合は生成時に確定した台帳行とshotで行う。撮影値の照合にはこのJSONを使い、アップロード用の `operator_value` は送らない。PR3では全件のqr_bboxをnullにし、PR4で奇数IDの最終PNGとハッシュを差し替える。

## 3. デモDBを作る

### 隔離と事前検証

`python -m tools.make_demo_db --run demo-01`。必須の `--run` は `demo-[a-z0-9][a-z0-9-]{0,23}` に限定する。出力はリポジトリ直下の `demo/runs/<run>/` を新規作成する。再実行は別の名前を使う。失敗時はログと部分データを残し、完了マーカーは書かない。DB・受信・画像・オーバーレイ・ログへの個別パス指定は作らない。プロジェクトルートから出力位置を計算し、既存の `demo` と `demo/runs` のリンク・ジャンクション・再解析ポイントを拒否する。runディレクトリは `exist_ok=False`。照合エラーは受信口起動前に終了コード1で報告する。

`load_catalog` と真値JSONを読み、ID・名前・単位・範囲・外観、20台分のshot 1〜4、PNGのハッシュとパスの包含関係を検査する。画像生成後に台帳を直して使い回すと検査で落ちる。ファイル配置は `manager.db`、`incoming/`、`images/`、`overlays/`、`watcher.log`、`result.json` をrunディレクトリ直下に置く。本番設定ファイルを読まず、ポートは `127.0.0.1:0`、合言葉は `secrets.token_urlsafe(32)`。変数 `run_dir` 以下の絶対パスだけを各コンポーネントへ渡す。

`seed_catalog_and_routes(db_path: Path, catalog: list[dict]) -> None` は既存の `sync_devices(csv_path, db_path, apply=True)` を使う。列は `device_id,device_name,kind,unit,min_value,max_value,provisional,note` に投影してrun内 `devices.csv` に書き、provisionalは0、noteは「3Dデモ」。errorsが空でappliedが真、登録数20を確認する。続いて `save_route(Storage(str(db_path)), name, devices, route_id=…)` を呼ぶ。devicesはID昇順の `{"id":文字列,"name":文字列}` の配列。

| route_id | 名前 | 機器 |
|---|---|---|
| DMO-ROUTE-A | 動力設備巡回 | 001〜010 |
| DMO-ROUTE-B | 冷却・熱交換設備巡回 | 011〜020 |

### 点検と送信順

`build_inspections(catalog: list[dict], truth: dict) -> list[dict]` は日付昇順、日内A→Bで6回分を返す。各要素は `manifest` と `uploads`。uploadsの要素は `file_name,body,sidecar,sha256`。日付は2026-11-16、17、18、時刻は全て日本時間。ルートA開始08:00、B開始14:00、完了は開始20分後。点検IDは `DMO-YYYYMMDD-A` または `-B`。点検名は `YYYY-MM-DD 動力設備巡回` または `YYYY-MM-DD 冷却・熱交換設備巡回`。担当は「デモ担当」、場所は「設備棟」。各ルートのID順を基本にし、点検内の送信番号1から1分刻みで撮影時刻を付ける。各ユニーク写真のlocal_idは全点検を通した1始まりの連番。ファイル名は受信口の検査に合わせて `<撮影時刻をYYYYMMDDTHHMMSSにした文字列>_<local_id>.png`。撮影時刻は日本時間、local_idはゼロ埋めしない。

| 日付 | 通常写真 | 追加条件 |
|---|---|---|
| 11/16 | 各ルート10台のshot 1 | Aの001のみ同じファイル名・同じ本文・同じサイドカーを直後に再送する。manifestは1件。 |
| 11/17 | 各ルート10台のshot 2 | 追加条件なし。 |
| 11/18 | 各ルートのshot 3 | Aは010を撮らず、末尾に011のshot 4（ルート外）と001のshot 4（別写真の撮り直し）を付ける。Bは019の本文をASCII `DEMO-BROKEN-PNG-v1` のバイト列で置換する。 |

壊れた019はサイドカーにIDと名前を付け、送信ハッシュを置換後の本文で算出する。受信・照合と画像読み取りの失敗を別々に見せるため、壊れたケースにもmanifestの写真1件を記録する。正解JSONの元PNGは残す。正常な奇数IDのサイドカーは `device_id/device_name/device_id_source` を省略する。偶数IDと壊れた019は `device_id/device_name` を付ける。全件のサイドカーに `local_id,captured_at,inspection_id,inspection_name,route_id` を含める。

`upload_photo(base_url: str, token: str, photo: dict) -> dict` は `POST /upload` を使う。本文は生バイト列。ヘッダーは `X-Sotuken-Token`、`X-File-Name`、`Content-Length`、小文字hexの `X-Image-Sha256`、UTF-8 JSONの末尾パディングなしbase64urlである `X-Sidecar-Json`。HTTPタイムアウト10秒。成功は200と `stored == file_name`。再送ではさらに `duplicate == true`。ほかはただちに失敗。

点検の写真を全て送った後、`POST /inspections/<inspection_id>/manifest` に同じ認証ヘッダーと `Content-Type: application/json` で送る。manifestは `v:1,inspection_id,inspection_name,route_id,operator,place,started_at,completed_at,missing,extra,photos`。missingとextraはID文字列の配列。11/18 Aに限り `missing=["DMO-010"],extra=["DMO-011"]`。photosは再送を除く送信順で `file_name,sha256,device_id,device_id_source,captured_at`。送信時点でIDを省略した写真のmanifestは `device_id:null,device_id_source:null`。ID付きは `device_id` を設定し `device_id_source:null`。200、`ok == true`、`matched == len(photos)`、`missing_photos == []` を必須とする。11/18 Aの受信状態は「完了」、010のルート進捗は「未撮影」となる。

### 取り込みと完了条件

`ReceiverServer(("127.0.0.1", 0), token, str(incoming_dir), quiet=True, db_path=str(db_path))` をスレッドの `serve_forever` で起動し、割り当てポートだけを使う。全送信後に `shutdown()`、join、`server_close()` を実行する。送信完了後に次の子プロセスを起動すれば、再送の検査がウォッチャーと競合せず、通常の初回ディレクトリ走査を通る。

`python -m manager.watch_inbox --watch-dir <run>/incoming --db <run>/manager.db --images-dir <run>/images --overlays-dir <run>/overlays`

子には現在のPythonを使い、標準出力と標準エラーを `watcher.log` へ追記する。DBはポーリング側で読み取り専用接続を使う。expectedは小文字SHA-256をキーに `file_name,inspection_id,route_id,device_id,device_id_source,broken` を持つ辞書。build_inspectionsの結果と真値から作る。`wait_for_ingest(db_path: Path, expected: dict, watcher: subprocess.Popen, timeout_s: int = 1200) -> dict` は1秒間隔。途中終了なら直ちに失敗し、期限超過なら未処理ファイル名とwatcher.logのパスを出す。DBの `readings.image_sha256` と `inspection_id` ごとに期待件数が1、IDが台帳と一致、通常の奇数IDは `device_id_source='pc_qr'`、ID付きは `device_id_source='sidecar'`。壊れた画像は失敗行が1件で `stage='image_unreadable'`、`status='failed'`、`failure_stage='unknown'`、`failure_code='unknown_failure'`、`value IS NULL`。既存の `manager.pipeline_caller.execute_pipeline` と `manager.record.judge_failure` の結果を使う。読める画像のOCR成功は測るが、全件成功を要求しない。各ルートで少なくとも1件の `stage='ok'` と有限の値を受入で確認し、満たさない場合は生成条件とOCR結果をメインに返す。DBへ数値を補記しない。前処理がエラー結果を返す契約を利用し、失敗行が作られない場合は成功扱いせずログを確認する。

`finally` で受信口と自分のウォッチャーだけを停止する。取り込み完了後は読み取った画像とオーバーレイをrunに残す。`result.json` は全照合が通ったときだけ一時ファイルから置換する。含めるキーは `v,uploads,unique_photos,duplicates,devices,routes,inspections,ocr_ok,ocr_failed,elapsed_seconds`。受入の固定件数は送信62、固有写真61、再送1、登録20、ルート2、点検6。想定内シナリオとして、11/18 Aの010は未撮影、011は追加、001は2記録を確認する。取り込み時間は61×10秒で約10分10秒、上限は20分。画像生成と画面の確認時間は別に測る。

Reactは次のコマンドでrunのDBを開く。ここで<run>には `demo/runs/demo-01` の絶対パスを入れる。点検一覧で6件、11/18 Aで未撮影・追加・撮り直し、Bで読み取り失敗、各ルートで計器盤に数値が出ることを確認する。画面の起動はデモDB生成とは別プロセス。点検画面と計器盤だけを確認し、受信設定とペアリングは開かない。

`python -m pc_api.launcher --db <run>/manager.db --incoming-dir <run>/incoming --images-dir <run>/images --overlays-dir <run>/overlays --port 18766 --owner-port 18767 --no-streamlit`
