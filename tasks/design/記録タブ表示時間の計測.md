# 記録タブ表示時間の計測レポート

## 1. 要約
記録タブの純粋なデータ処理時間は100件で約9ms、500件で約14msと高速であり、PR #67によるDB肥大化解消の効果が維持されていることを確認しました。
表示遅延の主因は、行選択時に約2.9MBのオーバーレイ画像を直接読み込んで表示する処理（サーバー側処理で約39ms増加、実通信ではさらなる遅延要因）と、行選択ごとに画面全体の処理が再実行される点にあります。
`watch_inbox`が取り込みごとにOCRエンジンを再読み込みしているという疑いは誤りであり、モジュール変数によるシングルトン保持によって2回目以降の初期化オーバーヘッドがゼロであることを実測で確認しました。

## 4. 疑い(4)の検証結果（OCRエンジンの読み直し疑惑）

### 4.1 結論
**「watch_inboxが取り込みごとにOCRエンジンを読み直している」という疑いは誤りです。**
OCRエンジン（RapidOCR）はモジュールレベル変数にキャッシュされており、同一プロセス内では初回呼び出し時に1回だけ初期化され、2回目以降は既存のインスタンスが再利用されます。

### 4.2 該当コードの引用
OCRエンジンの管理は `scale_value_detect.py` の22行目から34行目で以下のように実装されています。

```python
# scale_value_detect.py 22-34行目
_engine = None
_load_lock = threading.Lock()


def _load_engine():
    global _engine
    if _engine is not None:
        return _engine
    with _load_lock:
        if _engine is None:  # ロック待ちの間に他スレッドが読み込み済みの場合
            from rapidocr import RapidOCR
            _engine = RapidOCR()
    return _engine
```

`manager/watch_inbox.py` は `FolderWatcher` を起動したあと常駐するスクリプトであるため、プロセスが終了することはありません。
したがって、1枚目の取り込み時に `_load_engine()` で生成された `RapidOCR` インスタンスはそのまま保持され、2枚目以降で再度モデルの読み込みやONNX Runtimeセッションの初期化が走ることはありません。

### 4.3 実測値（1枚目と2枚目以降の時間差）
同一プロセス内でパイプライン（`meter_pipeline.read_meter`）を連続実行した実測値です。

```text
[出力抜粋: tmp_perf/test_ocr_timing.py]
Testing OCR / pipeline timing with image: eval/images/meter1.png
scale_value_detect._engine initially: None
1st run time: 27.6158 s, stage: ok, value: 22.600521446997796
scale_value_detect._engine after 1st: True
2nd run time: 22.4906 s, stage: ok, value: 22.600521446997796
3rd run time: 22.1695 s, stage: ok, value: 22.600521446997796

```

- 1回目の実行時間: **27.6158 秒**（OCRモデル読み込み・初期化を含む）
- 2回目の実行時間: **22.4906 秒**（キャッシュされたエンジンを再利用）
- 3回目の実行時間: **22.1695 秒**
- 1回目と2回目の差: **5.1252 秒**

エンジンの初期化コストは約5.1秒であり、これはプロセス起動後の最初の1枚でのみ発生します。2枚目以降は初期化コストが完全に排除されていることが実測からも証明されました。

## 5. 遅い箇所の上位3つと改善案（見込み効果つき）

### 第1位: 約2.9MBのオーバーレイ画像の直接読み込みとブラウザ転送（疑い1）
- **現状の課題**:
  - 行選択時に `selected_row.get("overlay_path")` で指定された約2.9MBのPNG画像をそのまま `st.image` に渡しています。
  - サーバー側のファイル読み込みとPILデコードで約15〜18ms、Streamlitの内部処理で約39msのオーバーヘッドが生じています。
  - さらに、実際の利用環境においてブラウザ（特にスマホなどのWi-Fi接続端末）へ約2.9MBの画像をHTTP/WebSocket転送する場合、（推測ですが）一般的な無線LAN環境（実効20〜50Mbps）では **約0.5〜1.2秒のネットワーク遅延** が発生します。これが利用者の感じる「行を選んだときの待ち時間」の最大要因と考えられます。
- **改善案**:
  - オーバーレイ画像保存時、または初回表示時に、表示用の軽量サムネイル（長辺800px程度のJPEGまたはWebP、品質85%、容量約50〜80KB）を生成して保存・表示します。原寸画像は別タブで開くリンクやモーダル表示に限定します。
- **見込み効果**:
  - 転送データ量が2.9MBから約80KBへと **約97%削減** されます。
  - ネットワーク転送時間が（推測として）約0.8秒から約0.02秒へ短縮され、行選択時の画像表示がほぼ体感ゼロ遅延になります。

### 第2位: 行選択に伴うスクリプト全体の再実行と無関係な集計処理（疑い3）
- **現状の課題**:
  - Streamlitのテーブル行選択イベント（`on_select="rerun"`）により、行を1つ選ぶたびに `app.py` 全体が先頭から再実行されます。
  - その結果、行選択とは直接関係のない「機器別推移グラフ（`group_by_device`、`readings_to_series`、`st.line_chart`）」の集計と再描画（約2.6〜3.0ms＋フロントエンド描画）が毎回走ります。
- **改善案**:
  - Streamlit 1.33以降で標準提供されている `@st.fragment` デコレータを導入します。
  - 記録テーブルと画像プレビュー表示部分をひとつのフラグメント関数に切り出し、行選択時はそのフラグメント内のみを局所再実行（fragment rerun）させます。
- **見込み効果**:
  - 行選択時に画面全体の再実行が回避され、トップレベルの `get_history` や下部の推移グラフの再集計・再描画が完全にスキップされます。
  - 画面全体の再描画によるチラつきが解消され、行選択の応答速度が向上します。

### 第3位: 履歴取得（`get_history`）およびテーブル成形のキャッシュ不在（疑い2）
- **現状の課題**:
  - `app.py` の95行目で `history = manager.get_history(include_raw=False)` がキャッシュなしで毎回実行されています。
  - PR #67の効果により、現行では100件で約1.86ms、500件で約4.52msと十分高速ですが、行選択やフィルタ変更など画面のあらゆる操作のたびにSQLiteへのクエリが発行されます。
  - また、取得したリストを表示用DataFrameへ成形する `_to_display_table` にも毎回約4〜6msを要しています。
- **改善案**:
  - `@st.cache_data(ttl=60)` を用いて `manager.get_history(include_raw=False)` をラップし、一定時間（または画像取り込み完了時）まで結果をキャッシュします。
  - また、成形済みDataFrame（`_to_display_table` の結果）もキャッシュ対象とします。
- **見込み効果**:
  - 画面再実行時のDBクエリおよびDataFrame生成時間（500件時で合計約10.6ms）がキャッシュヒット時は0.1ms未満になります。
  - 記録件数が将来1,000〜5,000件規模に増えた場合でも、画面操作時のもたつきを予防できます。

## 6. 計測できなかったこと

1. **実ネットワーク環境におけるクライアント側の描画・転送時間**
   - 今回はStreamlitをローカル環境で直接起動せず、テストハーネス（`AppTest`）およびPython内蔵タイマーで計測しました。
   - そのため、PCやスマホのブラウザがWebSocket経由で2.9MBの画像データを受信し、ブラウザ上でレンダリングを完了するまでの実時間は計測できていません（上記改善案の転送遅延は通信帯域からの「推測」です）。
2. **1,000件を超える大規模データ時のパフォーマンス**
   - 今回の依頼要件に基づき100件および500件で計測しました。数千件規模になった場合のSQLiteインデックスの影響やメモリ使用量は未計測です。
3. **複数端末からの同時アクセス時の挙動**
   - 単一セッションでの実行時間を計測しており、スマホからの無線送信とPCでの閲覧が同時に発生した場合のロック競合や負荷は計測していません。
