# 記録タブの見せ方（DESIGN）

## 目的
点検後に「**どのメーターが、いくつの値で読み取れたか**」を一目で分かるようにする。ユーザーが最も困っている点（2026-10-30）。

## 方向性（合意済み）
A: メーター別の最新値一覧。メーター1台につき1行。全履歴と機器別の推移グラフは、その下に残す（畳める形）。

## 画面の構成（上から）
1. **各メーターの最新の読み取り**（新設・最上部）
   - 列: メーター名 / 読み取り値 / 時刻 / 状態
   - 並び: 状態が「要確認」「失敗」のものを上、その中で時刻の新しい順。
   - 状態の表示: `ok` → 「✓ 正常」、`low_confidence` → 「要確認」（目立つ色）、`failed` → 「失敗」（目立つ色）。色だけに頼らず文字でも区別する。
   - 機器名が空（DB上は `unknown`）→ 「名前なし」と表示し、状態は必ず「要確認」扱い。上に並べる。
2. **絞り込み**（機器・開始日・終了日。現行どおり）
3. **全履歴**（現行の表。畳める。行を選ぶと画像を表示する現行の動きは維持）
4. **機器別の推移**（現行どおり）

## 使えるデータ（既存DBの列。新しい列は足さない）
- メーター名: `device_name`（空は `unknown`）
- 読み取り値: `value`
- 時刻: `timestamp`（現状は取込時刻。撮影時刻は DB に保存されていない）
- 状態: `status`（`ok` / `low_confidence` / `failed`、`manager/record.py` の `judge_status`）
- 単位: **データに無い**。当面は表示しない（QR 案で機器名と一緒に持たせる可能性あり）。

## 変えないもの
- 「読み取り」タブ、サイドバー（スマホの送信先）。
- 全履歴の表の列と、行を選んだときの画像表示。

## 実装の順（依存）
1. P-04b（速さの改善、`app.py` を変更中）がmainに入った後に着手する（同じ `app.py` を触るため）。
2. 最新値一覧（`manager/` に「メーターごとの最新の1件」を返す関数を追加し、テストを書く → `app.py` に表示を追加）。
3. 画面の見た目はスクリーンショットで確認し、ユーザーが最終判断する。

## 未決
- 機器名が空の記録の扱い（QR による機器名の入力を検討中。決まるまでは「名前なし＋要確認」）。
- 撮影時刻を DB に保存するか（インストーラー化の設計書で検討）。
