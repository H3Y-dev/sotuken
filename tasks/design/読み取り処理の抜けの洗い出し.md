# 読み取り処理の抜けの洗い出し（2026-10-28）

作成: Claude（大久保の指示「検出結果だけで評価しているが、アルゴリズムの中でどこが抜けているかを洗い出す」）。
根拠: main `3471006` のコード（`meter_pipeline.read_meter` ほか）と、合成画像294枚の工程別評価（AIなし、既定）。Argon（gemini-4-argon-high）のセカンドオピニオンでコードと照合し、誤りを直した（下の「訂正」）。主な指摘はClaudeがコードで確かめた（印 ✔）。
数字はすべて、生成バグを直した後の294枚（正面・斜め・反射・ブレ170枚は `stage_default_20261028.jsonl`、汚れ・紛らわしい文字・背景と画質124枚は `stage_default_regen124_20261028.jsonl`。PR #63 適用前）。

## 0. 処理の流れと、全体にかかる抜け

```
画像 → ①向きの補正（4方向でOCR。0°より2個以上多く読めた向きへ回す）
     → ②中心（小円Hough → 目盛りから補正。3%以上ずれたら目盛り側）
     → ③目盛り線（CLAHE 2.0 の画像で、極座標の周期的な暗線）
     → ④数字（OCRを複数の前処理で計5回）と目盛りの対応付け → 最小値・最大値・0点・満尺点
     → ⑤針（中心の近くを通る直線のうち最長。赤くない針を優先）
     → ⑥値（0点〜満尺点の比率と、数字による区分線形補間。比率は0〜1に丸める）
```

**全体の抜け: 前の段階の結果を、後の段階が疑わずにそのまま使う一方通行になっている。**
- 前で外れると後ろは全部引きずられる（中心を数字の上に取る → 目盛り0本 → 範囲が決まらない。PR #63で直した5枚のうち4枚）。
- 前の段階で分かっていることが、後ろに渡されていない（④は数字が角度の順に増えるか減るかを知っているのに、⑥は目盛りの本数の多数決で回る向きを決め直す。下の④→⑥）。
- **「この結果は怪しい」を表す信頼度が、途中で潰されている。** ✔ `determine_min_max` は使えた点の数・採用率・OCRの網羅率・満尺が標準的な数かで `is_confident` を計算しているのに、`detect_scale_values` が「4回の試行のうち2回で最小・最大が一致した」だけで `is_confident = True` に上書きしている。しかも4回のうち2回は同じ元画像へのOCRで、独立していない。**値が出た175枚のうち63枚（36%）が範囲を読み違えたまま値を返し、13枚が誤差25%FS超**なのは、この上書きで「要確認」が付かないため。

## 1. 段階ごとの抜け

| 段階 | 今のやり方 | 抜け（根拠） |
|---|---|---|
| ①向き | 0/90/180/270°でOCRし、0°より2個以上多く読めた向き | 正しい向きの合成画像294枚のうち**9枚（3%）を誤って回転**（180°が7枚）。向きを確かめる別の手がかり（数字が増える向き、目盛りの死角の位置）が無い |
| ②中心 | 小円Houghで軸を探し、目盛りから補正 | (a) 小円Houghが数字（丸い文字）や模様を軸と取り違える（PR #63の調査で4枚）。(b) ✔ **「目盛りから中心を補正する」処理は実質なにもしていない。** 目盛り線の向き（`line_angle`）を、今の中心から見た角度そのものにしているので、全部の線が今の中心を通り、最小二乗の答えが今の中心に戻る。(c) 補正に失敗すると（目盛り3本未満）、目盛りで否定されたはずのHoughの中心をそのまま使って先へ進む |
| ③目盛り | 極座標で周期的な**暗い**線。櫛の間隔を当てはめて目盛りを並べる | (a) 白い目盛り（黒盤面）を拾えなかった（PR #63で、3本未満のときだけ反転して再試行するよう直した）。(b) 線が見えなかった櫛の位置（最大8割）も目盛りとして返す。死角を見つけられないと、全周に目盛りを並べてしまう。(c) 検出した本数が正しいかを確かめる手段が無い |
| ④数字 | OCRを複数の前処理で計5回。5桁以上の数字は除く。単調に並ぶ部分列で外れ値を除き、最小値側は最大3目盛り分まで外挿で補う。0の位置だけ4倍に拡大して読み直す | (a) **小さい数字の読み落とし**（目盛りの外側に小さく並ぶデザインで端の0・4・12などを読めない）。拡大の読み直しは0の位置だけで、ほかの数字には無い。(b) 数字と目盛りの対応付けが角度だけで、**中心からの距離を見ない**。型番・単位・2重目盛りの内周の数字・死角の文字を区別できない（紛らわしい文字40枚で範囲が正しいのは11枚）。(c) 等差の確かめ（`_filter_arithmetic_progression`）や目盛りの通し番号との直線性（`_fit_major_grid_line`）は**既にあるのに、最小値・最大値（端点）の決定には使われていない**。(d) 端の数字が欠けたときの補い方が、最小値側だけで、**最大値側には無い** |
| ⑤針 | 中心から短辺3%以内を通る直線のうち最長。赤くない針を優先（置き針対策） | **針の角度が正解から20°以上ずれる画像が280枚中74枚（26%）**。内訳: 150°以上（尾を針先と取る）12枚、90〜150°（別の線）27枚、20〜90°35枚。(a) ✔ 中心までの距離を**線分ではなく、線を無限に延ばした直線**で測っている。中心へ向かう放射状の目盛り線は延ばすと中心を通るので、全部候補に残る。線分の内側の端が中心の近くにあるか、線分が目盛りの半径より内側にあるかを見ていない。(b) 赤くない針を優先する条件が「最長の線の95%以上の長さ」で、本物の針の線が少し途切れると赤い置き針に切り替わる。(c) 既定では、針先までたどった角度ではなく、線分の傾きを針の角度に使う |
| ⑥値 | 0点〜満尺点の比率（0〜1に丸める）と、数字の区分線形補間 | ✔ 値は読んだ範囲の中に丸められるので、値そのものが範囲外に出ることは無い（誤差7186%FSは、④で満尺を型番のような大きな数に読み違えたため）。(a) **針が目盛りの弧の外を指していても、0か1に丸めるだけで知らせない。** (b) **回る向き（時計回りか）を、④の数字の並びではなく、0点〜満尺点の間に目盛りが何本入るかの多数決で決める。** 端の数字を読み落として0点〜満尺点の幅が狭くなると、向きが逆になり、正しく指している針まで弧の外とみなされて端に丸められる |

### 訂正（Argonの指摘で直したもの）
- ⑥で「値が範囲の外に大きく出ても返す」と書いていたのは誤り。値は読んだ範囲に丸められる。大外れは④の範囲の読み違いによる。
- ②・③の「目盛りから中心を補正」は、実際にはほとんど効いていない（上の②(b)）。
- ④の「OCRは1回・拡大の読み直しが無い・文字の除外や等差の確かめが無い」は誤り。部分的にはある。抜けは「端点の決定に使われていない」「0以外の拡大読み直しが無い」こと。
- ⑤の「置き針の区別が無い」は誤り。赤くない針を優先する処理はある。抜けはその条件が厳しすぎること。

## 2. 評価（測り方）の抜け

- 合成画像には数字付き目盛りの正解（値と座標）と全目盛りの正解座標があるのに、OCRの読み（読めた数・読み違い・余計な文字）、数字と目盛りの対応付け、目盛りの本数を、まだ正解と比べていない。ここを数えれば、③④の抜けを人の目に頼らず全294枚で測れる。改修の前後比較にも要る。
- 向き補正で回った画像（9枚）は座標を比べられず、工程別の誤差から外れている。

## 3. 優先順位（Argonの異論を受けて組み替えた案）

1. **評価を広げる**（読み取り処理に手を入れないので副作用が無く、以降の全部の前後比較に要る）: OCRの読み・対応付け・目盛りの本数・向きの誤回転・針の向き（尾か先か）を正解と比べる列を `eval/stage_errors.py` に足す。
2. **信頼度の上書きをやめ、既にある確かめ（等差・目盛りの通し番号との直線性・全体方式と局所方式の突き合わせ）を端点の決定と既定の経路に使う**。怪しいものに「要確認」を付ける（安全網）。最後に外付けで確かめるのではなく、④の中で効かせる。
3. **④の範囲の読み違い**: 数字と目盛りの対応付けに中心からの距離を使う（T1）、最大値側の補い、拡大しての読み直し。⑥の回る向きを④の数字の並びから受け取る。
4. **⑤の針**: 中心までの距離を線分で測る、線分の内側の端が中心の近くにあること、尾と先端の区別。③④を直してから（針の確かめは目盛りの弧の範囲に依存するため）。
5. ②の中心（数字を軸と取る件、効いていない補正）と、①の誤回転。

## 4. 人の目での確認（絞って行う）

3の1で自動化できる部分は数字で出るので、人には**自動では分からない「なぜ外れたか」**だけを見てもらう。外れ方の型（向き・中心・目盛り・数字・針）がそろうように、1人10枚（2人で20枚）に絞って選ぶ。確認シートは段階ごと・検出1つずつ（`eval/review_overlays.py` で作る。Googleスプレッドシートで渡す）。
