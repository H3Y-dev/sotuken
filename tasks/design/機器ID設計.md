## 決定事項
1. **機器ID（`device_id`）と表示名（`device_name`）を分ける。** IDは変えない・束ねるキー。表示名は後から直してよい。
2. **QRにIDと表示名を持たせる。** スマホ（またはPC）がQRを読んで、各データに付ける。
3. **機器の表（`devices`）を作る。** QRを読んだときに自動で登録・更新する（10/21「PCに機器マスターは作らない」を見直し。入力の手間が増えないため）。
4. **テスト画像にもIDを振る。** 3Dメーター画像は、**メーターの種類（`meter_id`、10種類）×文字盤の色（`appearance.dial_color`: white・cream・black）ごとに1台（30台、`SYN-001`〜`SYN-030`、表示名「合成 圧力計0-150 白」の形）**とする（2026-10-30 メイン決定。当初の「種類×`appearance_variant`」は、`appearance_variant` が60枚にしか付かず、残り234枚の見た目も17〜23通りに分かれていて、見た目の違いに対応しないため取りやめ）。**制約**: 合成画像は、画像ごとに文字盤・書体・針の形・縁の色などをランダムに組み合わせて作ってあり、「同じメーターを条件だけ変えて撮った」画像は無い。針の形・書体・縁の色は、同じ台の中でも混ざる。機器ごとの集計を現実に近い形で試すには、メーターの固定の組を先に作り、値と条件だけを変えて生成し直す必要がある（将来の改善）。企業提供画像・一般画像にも**仮のID**を振る（`JSW-001`〜、`GEN-001`〜）。
5. 現場に管理番号・設備番号があるかは**未確認**（`tasks/先方への確認事項.md` の質問6b）。**あるものとして設計**し、QRの`id`にそのまま使えるようにする。

## 取り決め（3つの作業が守る契約）

### 機器IDの形式
`[A-Za-z0-9._-]` の1〜32文字。大文字小文字は区別する。空・空白・日本語は不可。例: `A-101`、`SYN-001`。

### QRのペイロード（v1。仕様は `QR機器ラベル仕様.md`）
```json
{"v":1,"id":"A-101","name":"ボイラー圧力計"}
```
- `v`・`id`・`name` が必須。`unit`・`min`・`max` は任意。知らないキーは無視。`id`が無いQRは機器QRではない。
- `parse_payload(text)` は、機器QRなら `{"id":..., "name":..., ["unit"], ["min"], ["max"]}` を返し、そうでなければ `None`。
- `build_payload(id, name, unit=None, min=None, max=None)`。

### サイドカーJSON
項目 `device_id` を足す（`device_name` はそのまま）。未入力は null。任意項目 `device_id_source`（`qr` または `manual`。省略時は出所不明）を足してよい。

### 機器の表のファイル（git管理）
`eval/devices.csv`（UTF-8 BOM）。列: `device_id,device_name,kind,unit,min_value,max_value,provisional,note`。

## 1. 場面と出力（設計の起点）

場面は推測。先方に確認するものは（先方確認）と書く。

- **場面A 巡回点検**: 点検者が順路で機器を撮って回る。終了時に点検結果を出し、撮られていない機器を確かめる（順路・予定一覧は先方確認）。
- **場面B 異常の確認**: 管理者が、要確認・失敗・範囲外の行を一覧で見て、必要なら現場入力値を入れる。
- **場面C 傾向の確認**: 機器ごとに日・週の推移を見る（グラフの元データ）。
- **場面D 監査・提出**: いつ・どの機器を・何と読んだかを、後から追える帳票にする。

**画像の採用規則（①②⑤共通）**: 同じ画像（`COALESCE(image_sha256,'id:'||id)`）につき、最大の`id`の1件だけを採る。再処理で増えた旧い行は出力に出さず、DBには残す。

**出力（優先順: ①②が初版、③は次、④⑤は後）**

① **点検結果**（場面A）: `点検結果_YYYYMMDD_点検ID.csv`。1行=1機器の採用値（点検期間内で最新の撮影。失敗でも最新を採り、隠さない）。並びは機器番号順。
```
点検ID,機器番号,機器名,単位,測定値,読取状態,要確認理由,撮影日時,測定方法,現場入力値,備考,画像参照
PT-0001,A-101,ボイラー圧力計,MPa,0.42,正常,,2026/10/30 09:12,自動,,,images/3f2a.jpg
PT-0001,A-102,冷却水温度計,℃,,失敗,読み取り失敗,2026/10/30 09:15,手動,38.5,,images/9b1c.jpg
PT-0001,SYN-003,合成0-1MPaデザイン2,MPa,0.87,要確認,範囲外の疑い,2026/10/30 09:20,自動,,,images/7d4e.jpg
```
「測定値が空で現場入力値がある行」は、測定方法を`手動`とする（`record.py`の`judge_input_method`と同じ規則）。

② **履歴**（場面D）: `履歴_期間.csv`。1行=1撮影。監査の元になる記録。
```
記録ID,撮影日時,取込日時,機器番号,機器名,単位,測定値,読取状態,要確認理由,測定方法,現場入力値,備考,画像参照
1f0c...,2026/10/30 09:12,2026/10/30 09:13,A-101,ボイラー圧力計,MPa,0.42,正常,,自動,,,images/3f2a.jpg
```
機器番号の出所・処理版は、②には出さず`readings_export.csv`とJSONLに残す。

③ **要確認一覧**（場面B）: 1行=1撮影。対象は、読取状態が要確認・失敗、機器番号なし、名称未設定、範囲外（上下限がある機器だけ）。②の列に「目盛範囲」を足す。

④ **未撮影一覧**（場面A）: 予定の機器のうち、点検期間内に撮影が無いもの。予定一覧（先方確認）が無いと作れない。

⑤ **推移**（場面C）: 1行=機器×日。列: 機器番号・機器名・単位・日付・件数・最後の測定値・最小・最大・平均（有効値のみ）。

**出力に要るデータ項目（列を足すのは、この出力で使うものに限る）**

| 区分 | 項目 |
|---|---|
| 既存で取れる | 測定値、読取状態（`status`）、失敗理由（`failure_code`）、処理日時（`timestamp`）、記録ID（`reading_id`）、測定方法（`input_method`）、現場入力値（`operator_value`）、備考（`operator_note`）、目盛範囲（`raw_data_json`の推定値） |
| QR・機器の表から | 機器番号、機器名、単位、上下限（QRの`min`・`max`、表） |
| 新しく取る（コード） | 撮影日時（`captured_at`）、取込日時（`received_at`）、機器番号の出所（`device_id_source`）、機器番号の問題（`device_id_issue`）、画像の相対パス（`image_rel`）、処理版（`pipeline_version`を常に書く）、点検ID（7章）、要確認理由（読取状態・範囲外・名称未設定から作る） |
| 先方確認 | 点検者、場所・エリア、順路、点検区分（定期・臨時）、警報値（上下限）、予定機器一覧 |

## 2. 読み取りログとDBの切り分け

現状は、`logs/<reading_id>.log` が読み取り結果の全体をJSONで書いており、手元で774件・6.2GB（最大740MB/件）（コーディネーターの確認値）。原因は、`ingest.py`が`processed_img`を含む結果をそのまま書いている点（`ingest.py:98,113`）。`raw_data_json`（`storage.py:11`）は`processed_img`を除外済み（PR #67）。

| 置き場所 | 中身 | 人が触るか | 方針 |
|---|---|---|---|
| DB（`manager.db`） | ①〜⑤の出力に要る列 | 画面とCSVで触る | 3章の列だけ |
| ログ（`logs/`） | （作らない） | - | **書かない**（2026-10-30 決定）。診断はDBの`raw_data_json`で見る。画面から診断を見られるようにする（別タスク） |
| 原画像（`images/`） | 撮影画像 | 再処理の入力 | 正本。自動削除しない |
| 検出結果画像（`overlays/`） | 人が見る確認用の画像 | 確認するとき | 原画像と同じ期間 |
| `processed_img` | 処理途中の画素配列 | 触らない | DBにもログにも残さない。必要なら原画像から再実行して作る |

- **ログの容量**: ファイルのログは書かないので、増えない。`raw_data_json`は1件数KB（`processed_img`除外済み）。
- **`raw_data_json`**: 同じ除外規則（`processed_img`と`ticks`だけ）で書く。専用列にはしない。
- **保存期間・容量（先方確認）**: ログのファイルは無い。画像・記録は自動では消さない。
- **インストーラー化後**: 全部 `%LOCALAPPDATA%\SotukenMeter\` 配下。DB内のパスは相対パス（`image_rel`・`log_path`）で持つ。

## 3. DBに保存する列

`meter_readings`（現行18列）。**列は削らない**（SQLiteの列削除と表の作り直しを初版で避ける）。使い方を変える。

| 列 | 扱い・書き込み担当 |
|---|---|
| `id` | 内部の主キー（4章） |
| `reading_id` | 業務キー。UNIQUE。旧行の空・NULL・重複はB1で`legacy:<id>`に埋める |
| `image_sha256` | 画像の同一性。索引を付ける |
| `device_id`・`device_id_source`・`device_id_issue` | **新規**。取込（B5）が書く。`device_id_source`は`sidecar_qr`・`sidecar_manual`・`sidecar`・`pc_qr`・NULL |
| `captured_at` | **新規**。サイドカーの`captured_at`をB4がUTCに正規化し、B5が書く。後着サイドカーでも反映する。無ければNULL |
| `received_at` | **新規**。`incoming/`へ画像が置かれた時刻（ファイルの`mtime`。推測: USBやコピーで変わるおそれがあるためB5で確かめる） |
| `image_rel` | **新規**。B5が書く。データ領域からの相対パス |
| `pipeline_version` | 常に書く（B5）。再処理は`reprocess.py`が書く |
| `timestamp` | 処理後の保存時刻のまま |
| `device_name` | 読み取り時点の名前。表示は`devices`を優先。`unknown`は書かずNULLにする（B5・B6） |
| `value`・`status`・`failure_*`・`input_method` | 既存 |
| `stage`・`confidence`・`image_path`・`log_path`・`overlay_path` | 旧列または既存。出力では`captured_at`・`image_rel`を使う |

**時刻の使い方（B6）**: 期間の絞り込みと最新の比較は`COALESCE(captured_at, received_at, timestamp)`と`id DESC`。CSVの撮影日時は`captured_at`（NULLは空欄）。`export.py`の`timestamp`別名は、この代替を入れてから消す。

**単位・目盛範囲・点検者は`meter_readings`に足さない。** 単位と目盛は`devices`を正とし、優先順は「`devices` ＞ `image_truths` ＞ `raw_data_json`」とする。目盛を付け替えたら別の機器なので、新しいIDを振る。

**正規化（初版）**: 画像の表は作らない（`image_rel`で足りる）。関係は、機器（`devices`1対多 記録）、画像と正解（`image_truths`、画像ハッシュで1対1）の2つ。

## 4. 主キー

| 対象 | 採用する一意キー | 理由 |
|---|---|---|
| 機器 | `devices.device_id`（TEXT PRIMARY KEY、大文字小文字を区別） | 不変。名前変更はIDを変えず表示名だけ直す |
| 読み取り（1回の処理） | `id`（主キー）＋`reading_id`（UNIQUE） | `id`は内部の参照先として安定。`reading_id`は出力に出す業務ID |
| 撮影（同じバイト列の画像） | `image_sha256`（UNIQUEにしない） | 再処理で複数の読み取りが出るため。採用は最大`id`の1件（1章） |
| 点検 | 点検ID（ファイル名と①の列に入る文字列。表は作らない） | manifestが対象の`reading_id`と`id`を両方残す |
| 処理版 | `pipeline_version`（キーに含めない） | 旧行はNULLで、UNIQUEにすると機能しない |

**比較**
- 案A（採用）: `id`を主キー、`reading_id`をUNIQUE。再処理は新しい`reading_id`で行を増やし、採用は最大`id`で決める。
- 案B: `reading_id`（TEXT）を主キーにする。外部参照が重く、表の作り直しが要るため不採用。
- 案C: `(image_sha256, pipeline_version)`の複合キー。旧行のNULLで一意性が崩れるため不採用。
- 案D: `(device_id, captured_at)`。撮影日時が欠けた旧行と同じ秒の衝突があるため不採用。

**作り直しの判断**: 点検の対象（manifestの`reading_id`と`id`）は固定する。名称・単位は`devices`から読み直すため、再出力では名称・単位の変更が反映される（対象は変わらない）。値を固定したい監査は、②履歴を同時に出す。

## 5. 同一性の規則

- 機器ID: 大文字小文字は別の機器。登録時に、大文字小文字だけが違う既存IDがあれば警告する（統合はしない）。
- 名前・単位・目盛: 表に値があれば上書きしない。空欄だけ埋める。食い違いは警告し、記録の`device_name`にはその読みの名前を残す。
- 同じIDのQRが別に貼られた: 同じ機器として扱う。同じIDのラベルを二重に貼らない運用で防ぐ。
- IDの無いQR: 機器QRではない（`qr_not_device`）。機器IDは空欄。
- 後着サイドカー: 6章の4を見る。
- 名前変更: 表示名だけを変える。記録は変えない。
- 統合（2つのIDを1つに）: 初版は画面に作らない。必要になったら、記録の`device_id`を付け替える操作を1トランザクションで行い、元のIDは表に残して`note`に統合先を書く。
- 廃止: 初版は列を作らない。記録が来なくなるだけで、行は消さない。
- 旧データ（`device_id`が無い行）: 自動では移さない。束ねるキーは`name:<device_name>`とし、機器の表とは結びつけない。`unknown`は「名称未設定」として扱う。

## 6. 取り込みの順序（PC読み取り）

1. サイドカーに`device_id`があり、形式が正しければ、それを使う。画像のQRは読まない（出所は`sidecar_qr`・`sidecar_manual`・`sidecar`）。
2. サイドカーの`device_id`が形式違反なら、無効として扱い（`id_invalid`を残す）、画像のQRを読む。
3. サイドカーに無ければ画像のQRを読む（OpenCVの`detectAndDecodeMulti`。新しい依存は増やさない）。機器QRの異なる`id`が2つ以上なら`qr_multiple`でIDを空欄にする。1つなら`pc_qr`で、その`name`を`device_name`に入れる。機器QRでないものは無視する。QRが無ければ`qr_not_found`、機器QRでなければ`qr_not_device`。
4. 後着サイドカーの扱い: 記録の`device_id`が空で、後着が有効なIDなら埋め、`device_id_issue`をNULLにして`devices`へ登録する。後着のIDが空なら既存を維持する。既存と異なる有効なIDが来たときだけ`id_conflict`とし、上書きしない。
5. `unknown`はNULL扱いとし、`devices`に登録しない。

**保留（メインの判断が要る）**
- 取込後に`incoming/`の元ファイルを消すか。案A: 消す（容量は減るが、後着反映と再処理の入力を失う）。案B: 残す（推奨。容量は別途管理する）。
- 同名の画像が既にあるとき、後着のJSONを捨てている箇所（`receiver.py:298-303`、`usb_pull.py:200-204`）を、既存行へ反映するように直すか。直すならB5の範囲を超えるため、別タスクとする。

## 7. 点検の記録（manifest方式）

点検の終了のたびに、点検結果CSVと同じ名前の`点検結果_日付_点検ID.manifest.json`を残す。中身は、点検ID・期間・作成日時・対象の`reading_id`と`id`の一覧・CSVのSHA-256。`inspections`・`inspection_items`の2表は作らない（PCインストーラー化の改訂と合わせる）。再出力は、manifestの対象から作り直す。点検者・点検区分は、先方の答えが出るまで出力に含めない。

**点検IDの列を残す理由**: 1つのフォルダに複数の点検結果が並ぶため、行がどの点検かを示す。PCインストーラー化の改訂の表には点検ID列が無いが、この設計では残す（大久保と整合を取る）。

## 8. 書き出し・同期・移行

- `readings_export.csv`: 既存の列の順は変えない。末尾に`device_id`・`device_id_source`・`device_id_issue`・`pipeline_version`を足す。JSONLにもキーを足す。
- `eval/devices.csv` ↔ `devices`: 取り込みの向きはCSVからDBへ。明示的な操作でだけ行い、既存行はCSVの値で上書きして差分を表示する。単位がNULLのものはCSVで空欄にする。自動登録（QR読み取り）は空欄だけ埋める。
- **退避**: 旧スキーマを検出して列を足すときだけ、ファイルDBに対して1回、移行関数の中で`backups/`へコピーする。`:memory:`は対象外。同じ版の退避が既にあれば作らない。`Storage.__init__`ごとの副作用は作らない。PCインストーラー化の改訂の「退避は作らない」からの例外（ユーザー決定）。
- **列の追加**: `ALTER TABLE ADD COLUMN`の既存方式。1つのトランザクションにまとめ、失敗したら戻して起動を止める。`reading_id`のUNIQUE索引は、旧行の空・NULL・重複を`legacy:<id>`に埋めて重複0を確かめてから作る。

## 10. 先方への確認（`tasks/先方への確認事項.md` に足す案。このファイルは直接変えない）

工場の担当者が答えやすいよう、選択式で書く。

1. 「メーターの値が決めた上限・下限を外れたら、印を付けたいですか。 1) 機器ごとに上限・下限がある 2) 印は付けなくてよい 3) その他（　）」
2. 「点検の結果に、点検した人の名前を入れますか。 1) 点検ごとに1人の名前 2) 撮影ごとに違う人の名前 3) 入れない」
3. 「点検は次のどれですか。 1) 定期 2) 臨時 3) 両方を区別する 4) 区別しない」
4. 「機器の場所（棟・エリアなど）を結果に出しますか。 1) 機器ごとに決まった場所 2) 点検ごとに変わる 3) 出さない」
5. 「点検の順番は決まっていますか。 1) 決まっていて、一覧を渡せる 2) 機器番号の順でよい 3) 毎回違う」
6. 「撮るべき機器の一覧（機器番号・名称）はありますか。 1) ある（表やCSV） 2) ない（撮った分だけでよい）」
7. 「撮った画像と読み取りのログを、どのくらい残しますか。 1) 無期限 2) 数年 3) 1年 4) 決まっていない」
8. 「設備に貼る管理番号はありますか。 1) ある（英数字だけ） 2) ある（漢字や記号を含む） 3) ない」
9. 「機器の単位は、途中で変わることがありますか。 1) 変わらない 2) 変わる（変わったことを、記録に残したい）。2の場合は、機器を別のIDにして対応する案を検討します」
10. 社内確認（大久保）: PCインストーラー化の改訂（表の単位列の省略・点検ID列の扱い）と、この設計の整合を取る。
