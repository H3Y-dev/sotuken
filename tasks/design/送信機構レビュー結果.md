# スマホ→PC無線送信のレビューとQRペアリング案

調査日: 2026-11-06。根拠の基準コミット: `14e8b39`。コードの静的レビューと公式資料の確認に基づく提案であり、実機での障害再現結果ではない。並行して既知問題の修正が入り、提出前のHEADは`31ddcdd`へ進んだため、本文の行番号は基準コミットのものとして参照する。実装・テスト・設定は変更していない。

## 結論

先に「PC未到着なのに送信済みと見える」「失敗した写真を画面から再送できない」「設定を直してもすぐ送られない」を直すと、現在の仕組みを保ったまま運用しやすくなる。QRは手入力を減らせるが、IPの自動追従、通信の暗号化、写真の送信先の固定は別の対策が必要になる。

依頼で既知とされた、healthの認証、HTTPエラー分類、接続失敗後の短絡、part名衝突、413/409、PC表示IPのキャッシュは改善一覧から除いた。送信側のリダイレクト禁止とWorkerのMutexは既にあるため、新しい問題として数えていない。

工数は既存構造を使った相対見積もり。小は局所変更、中は複数箇所の変更や結合確認、大は通信・認証方式の変更を含む。期限の日付は依頼にないため、「期限前」は次回の実演・現場試行までを指す。

## 2. QRペアリング設計

### 2.1 既存資産と採用案

PCのQR生成には`qrcode==8.2`が既にある（`requirements.txt:38`、`manager/qr_label.py:270`）。`qrcode.make`等で生成して既存のStreamlit画面に表示できるため、PCに新しいQRライブラリは不要。機器ラベル用画像は印刷用の文字や配置も含むので、ペアリングではその描画関数を無理に転用せず、同じqrcodeライブラリを使う。[qrcodeの公式プロジェクト説明](https://pypi.org/project/qrcode/)

AndroidはCameraXによる撮影がある（`A/ui/CameraCapturePanel.kt:44`、`:161`）が、対象ソースと`android/app/build.gradle.kts:40`〜`:57`にはML Kit・ZXing・QR解析処理がない。既存のスマホQRスキャナーをそのまま呼ぶことはできない。PC側の`manager/qr_decode.py:206`はOpenCVによる写真解析であり、Androidからの直接再利用対象ではない。

工場で初回からオフライン利用する前提なら、Androidはモデル同梱型のML Kit Barcode Scanningを1つ追加し、QR形式だけを読む。最小画面では既存CameraXで撮った1枚を読み取る方式にすれば、リアルタイム解析用のCameraX構成変更を抑えられる。初回の画面実装は中程度の工数とみる。自動連続読取は必要になってから追加する。[ML Kit公式資料](https://developers.google.com/ml-kit/vision/barcode-scanning/android)

Google code scannerは読取UIを任せられ、実装量を減らせる。ただしGoogle Play servicesのモジュール取得が必要なので、現場前のダウンロードと対象端末での動作確認が条件。対象端末のGoogle Play services有無は未確認。圏外での初回動作を優先する本案では同梱型を第一候補にする。[Google code scanner公式資料](https://developers.google.com/ml-kit/vision/barcode-scanning/code-scanner)

### 2.2 ペイロード

QRの生文字列は専用接頭辞`SOTUKEN-PAIR:`と、その直後のUTF-8 JSONとする。URLのクエリやフラグメントに秘密を入れず、ブラウザで開く形式にも、OSの汎用ディープリンクにも依存しない。

```text
SOTUKEN-PAIR:{"v":1,"kind":"receiver-pair","url":"http://192.168.1.20:8765","token":"<ランダムな一時登録用合言葉>","receiver_id":"<PC設定に永続化したUUID>","pc_name":"検査PC-01","expires_at":1793920200}
```

| 項目 | 意味・検証 |
|---|---|
| 接頭辞 | 完全一致。専用の「送信先QRを読む」画面でのみ受け付ける。 |
| `v` / `kind` | 整数1（boolean不可）／`receiver-pair`のみ対応。未知版は明示エラー。 |
| `url` | PC受信口のoriginのみ。scheme、私用IPv4、port 1〜65535を検証し、userinfo・query・fragment・任意pathを拒否する。自動リダイレクトは禁止。 |
| `token` | 初版では恒久のX-Sotuken-Tokenではなく、暗号学的乱数32byte以上の一時登録用合言葉。資格情報交換のときだけ使う。 |
| `receiver_id` | 機器IDとは別の、PC受信口の永続UUID。表示名やIPの変更で変えない。 |
| `pc_name` | 作業者に見せるPC名。1〜64文字、制御文字なし。機器名・撮影対象のIDとして保存しない。 |
| `expires_at` | UTCのUnix秒を整数で格納。例の数値は形式例であり、有効な招待を示さない。期限の最終判定はPCが行う。 |

全体は例えば2KiBまでに制限し、秘密やQR全文をログ・クリップボード・エラー画面に出さない。読み取りに成功しても、PC名とURLを表示して確認するまで保存・送信しない。

機器QRの`parse_payload`はJSONの`v=1`・`id`・`name`を要求する（`manager/qr_label.py:149`〜`:169`）。接頭辞付き文字列はJSONとして失敗するため混同しない。接頭辞を除いたJSONにも機器用の`id`・`name`を入れない。将来スマホで機器QRも読む場合は、生文字列の接頭辞で用途を先に分け、失敗したペアリングQRを機器IDへの手入力に流用しない。

### 2.3 期限とワンタイム化

共有TokenをQRに直接入れ、スマホだけでexpires_atを調べる実装は小さく作れる。ただし写真に撮られたTokenは期限後もアップロードに使えるため、それを期限付き・ワンタイムと呼んではいけない。本提案の標準案は以下の登録交換方式とする。

1. 作業者がPCで「スマホを登録」を押す。PC受信サーバーが一時Tokenを生成し、期限5分と未使用状態をメモリに保存する。新規生成・画面の中止・サーバー再起動で前の招待を失効させる。単一招待を上限とし、一覧DBを増やさない。
2. スマホがQRを読み、形式・URL・端末時刻での期限を仮検証して、PC名とURLを表示する。時刻ずれを理由に既存設定を壊さない。PCが期限切れとしたらQRの更新を案内する。
3. 確認後、PCの`POST /pair`へ小さいJSONで一時Tokenを送る。このエンドポイントだけは既存の恒久Tokenなしで受け、接続元制限・本文上限・読取期限・試行回数制限を適用する。GETや/healthでTokenを返さない。
4. PCはロック内でToken一致・未使用・有効期限を確認し、未使用から使用済みへの変更と資格情報の発行を一度だけ行う。期限はPCの単調増加時計で管理し、QRのUTC値は表示用にも使う。Streamlitの再描画で期限やTokenが勝手に再生成されないよう、受信サーバー側を状態の所有者にする。
5. 最小版は応答で既存の共通X-Sotuken-Token、receiver_id、PC名を返す。招待を一度だけ使えることと、登録後の共通Tokenの再利用可否は別である。端末別Token・個別失効・有効期限付きアップロード資格情報は後のPRに分ける。
6. スマホはQR内と応答のreceiver_idが一致することを確認し、成功時だけ設定をまとめて置き換える。失敗・キャンセルでは従来の設定と写真を残す。成功後に送信Workerを起動するが、別receiver_idへの変更では既存の未到着写真を送る前に確認する。

一時Tokenを消費した直後に応答が失われた場合、初版ではPCでQRを作り直して再登録する。これを画面に案内する。登録要求の冪等な再応答まで初版に入れる必要はない。同時に2台が読み取った場合は1台だけ成功することをテストする。

HTTPのままでは一時Tokenや交換後の共通Tokenを盗聴・中継され得る。ワンタイム登録だけでは通信相手を暗号学的に認証できない。専用LAN内の入力補助として提供し、現場のネットワーク要件に応じてHTTPSと公開鍵指紋確認を先に入れる。QR画面も資格情報なので、常時表示・帳票への印刷・スクリーンショットの共有を避ける。

## 3. 中間発表後に「今すぐ効く」3件

1. 送信箱保存を「PC未到着」と表示する。既存のsentViaで判別でき、Roomの移行も通信仕様の変更も不要。作業者が撮影を終えたと判断してPCを確認しない事態を減らせる。
2. FAILEDの「再送」と送信箱の「今すぐ送る」を用意する。既存のretryとenqueueSendを画面につなげるだけで、保存済み写真をやり直せる。再撮影の前に復旧できることが現場で役立つ。
3. 送信設定を保存した直後にenqueueSendする。URLや合言葉を修正しても定期実行待ちになる現状を、小さい変更で改善できる。送信先を変更する場合の未到着写真の確認も同時に入れる。

QRは次のまとまりとして有効だが、現状のAndroidにはスキャナー追加が必要で、本当に期限付き・一回限りにするにはPC側の交換処理も要る。上の3件を先に入れ、QRはPR2〜3で検証してから載せるのが無理の少ない順序である。

## 確認範囲と残る確認

送信側queue・settings・ui、PC受信口・取込処理、PC設定表示、機器QR形式、依存定義を読んだ。工数・優先度は提案であり、実測値ではない。機能の変更を伴わないためAndroidビルド・Pythonテスト・LAN通信・実機の読取は実行していない。現場端末のGoogle Play services、LANの分離方針、PCのNIC構成、HTTPS要否、具体的な期限はメイン側の確認事項。
