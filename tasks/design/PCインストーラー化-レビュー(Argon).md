# PCインストーラー化 設計書レビュー（Argon）

保存先分離や専用Ollama同梱の骨格は妥当だが、点検3表・版管理・旧DB移行は大久保とClaudeの2人体制には重すぎる。
『記録タブ-DESIGN.md』との仕様矛盾や、`incoming/`再走査での全件再推論など既存コードとの食い違いがある。
初版は既存表への列追加と単純なCSV出力に絞り、PyInstallerの代替に埋め込みPython配布案を持つことを勧める。

## 1. 過剰設計（高→低）
- **【高】点検3表・版管理（`PCインストーラー化.md:34-40`）** 何が：`inspections`等3表・行固定・`r001`連番・SHA-256復旧。なぜ問題か：UIとテスト（T1・T8b）が肥大化し2人体制を圧迫する。直す案：**削る**＝3表・行固定・版管理・復旧、**残す**＝一時ファイル保存（`同:66`）と絞り込み出力（`meter_readings`から`点検_日時.csv`を直接出力）。
- **【中】旧データ移行（`同:114,147`）** 何が：`user_version`・退避・旧DB複製・パス変換（T9 `migrate.py`）。なぜ問題か：11/5前で引き継ぐ旧本番DBがない。直す案：**削る**＝T9一式、**残す**＝`manager/storage.py:107-122`の`ALTER TABLE ADD COLUMN`のみ。
- **【低】過剰列と単位強制（`同:21-25,37,146`）** 何が：単位入力・警告、`raw_data_json`の目盛上下限、点検ID・版・`legacy:<id>`。なぜ問題か：『記録タブ-DESIGN.md:21-26』（新列なし・単位非表示）や『QR機器ラベル仕様.md:16』（`unit`は将来用）と矛盾し手入力が負担。直す案：**削る**＝単位強制・目盛上下限・点検ID・版、**残す**＝名称・値・時刻・`status`・画像参照。

## 2. 抜け・矛盾（高→低）
- **【高】「1画像1行」と「1台1行」の矛盾（`PCインストーラー化.md:13`）** 何が：本設計は「1画像1行」だが『記録タブ-DESIGN.md:8-9』は「メーター別最新値（1台1行）」で合意済み。なぜ問題か：撮り直し時に同じメーターがCSVに複数行出て要望の表にならない。直す案：終了時CSVも「メーター別の採用値（最新1件）」に揃え、全履歴出力と分ける。
- **【高】`incoming/`未削除での全件再推論と取込時刻の衝突（`同:104,143,145`）** 何が：`manager/watcher.py:156-181`はDBハッシュを見ずに全画像へ推論し、`manager/ingest.py:80-96`も元画像を消さない。なぜ問題か：再起動のたび過去画像にVLM推論（約22秒/枚）が走り、`manager/watch_inbox.py:109-113`も`scan_existing()`後に`start()`を呼ぶため`同:104`と逆順。T6でJSONへ`received_at`を足すと`manager/usb_pull.py:235`のサイズ検査も失敗する。直す案：推論前に`storage.py:282`の既存ハッシュで弾き取込後に`incoming/`を片付け、`usb_pull.py`はサイズ検査後に`received_at`を追記する。
- **【中】2段階保存・機器名引き継ぎ欠落（`同:13,17,66`）** 何が：`app.py:223-232`は`st.download_button`の2段階UI、画面に機器名編集がなく（`storage.py:174`は後着JSON用）、`manager/reprocess.py:42-47`は`device_name=UNKNOWN_DEVICE`で保存。なぜ問題か：保存先が2つに分かれ、再処理で機器名が消える。直す案：直接`ドキュメント\メーター点検\`へ保存し、画面の機器名更新と`reprocess.py`での同一`image_sha256`からの機器名・時刻引き継ぎを足す。

## 3. タスク分解（T1〜T12）（高→中）
- **【高】同一ファイルの4回編集と記録タブ競合（`PCインストーラー化.md:137-146`）** 何が：`storage.py`・`export.py`・`app.py`・`test_export.py`をT1→T5→T7→T8bで4回書き直す分割。なぜ問題か：表出力を先に置く価値順は妥当だが、T1が重いうえ同じ箇所を何度も直して手戻りが大きく、『記録タブ-DESIGN.md:33-34』の`app.py`変更との順序も未定義。直す案：①保存先とDB時刻列追加（T2＋T5最小版）を先に1回で行い、②記録タブと合わせた簡素なCSV出力（簡素化T1）を実装し、T8b・T9を削り全7〜8タスクに絞る。
- **【中】相対パス・VLM接続先の対象漏れ（実質5ファイル超）（`同:140-141,148`）** 何が：T3b・T4に`app.py:130,148-149`（`temp_`と相対指定）と`manager/overlay.py:66`（`relpath`）がなく、T10に`vlm_scale_value.py`がない。なぜ問題か：書込禁止フォルダで`app.py:130`が落ち、`overlay.py:66`で画像参照が切れる。また`vlm_scale_value.py:61,104`は`ollama.chat()`直呼びのためimport後の環境変数変更では`11435`を見ないおそれがある（推測）。直す案：T4に`overlay.py`、T3bに`app.py`、T10に`vlm_scale_value.py`を入れる。

## 4. リスク（高→低）
- **【高】PyInstallerでのStreamlit・OCR梱包（`PCインストーラー化.md:70,122`）** 何が：`run_pc.py:31-32`（`stcli.main()`）と`scale_value_detect.py:32`（`RapidOCR()`）のexe化。なぜ問題か：Streamlitのプロセス増殖やONNXモデル収集漏れで落ちやすい。直す案：Python Embeddable（または`venv`）をInno Setupで同梱しランチャーから`python.exe`を呼ぶ方式を第一候補（または代替案）にする。
- **【高】5〜9GB配布とCPUでの推論停止（`同:77-78,104,126`）** 何が：6.63GBのblobを含む配布手段と、GPUなしPCでの`--use-vlm`常時有効。なぜ問題か：展開時に約3倍の容量を要し、`vlm_scale_value.py:27-30`の通り8GB GPUでもVRAM不足が起きるためGPUなしPCでは実用にならない（推測）。直す案：不要blob（約3.3GB）除外をT11必須とし配布経路を決め、試行推論が遅い環境は自動でVLMを無効化する。
- **【中】コード署名とDefender誤検知（`同:128`）** 何が：「署名を用意」とある点。なぜ問題か：有料証明書の取得は卒研では非現実的で、未署名PyInstaller製exeは誤検知されやすい。直す案：公式署名済みの`python.exe`同梱で誤検知を避け、`SETUP.md`にSmartScreen手順を載せる。
- **【低】ライセンス表記の後回し（`同:128`）** 何が：配布前確認とされている点。なぜ問題か：終盤での漏れにつながる。直す案：Ollama（MIT）、Qwen3-VL・RapidOCR（Apache-2.0）は再配布可能なため、T11で`THIRD_PARTY_NOTICES.txt`へまとめる。

## 5. 確認事項への意見
1. **Setup.exeと同梱データを1つのZIPで渡す案**：**賛成（`Setup-*.bin`分割ではなく`Setup.exe`と`models/`を分けた1つのZIPを推奨）**。不要blob（約3.3GB）を除けば4.2GB未満に収まる見込みが高い（推測）。モデルを外出し同梱し導入時にコピーすれば、以後の更新は軽い`Setup.exe`単体で配れる。
2. **USBは任意機能とする案**：**強く賛成**。USBデバッグとドライバー導入は非開発者に敷居が高く、`manager/usb_pull.py:28-65`が既に`adb.exe`を探索する作りなので、Wi-Fiを主経路としUSBは任意機能とするのが妥当である。
