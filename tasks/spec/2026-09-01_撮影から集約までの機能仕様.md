# 撮影から集約までの機能仕様

> [!note] タスク番号の体系
> 本書の R1 / A1 / P1 / E1 は、`tasks/todo.md` および `tasks/plan.md` の T1〜T6（精度改善トラック）とは無関係の別体系である。

## 1. 目的と方針

卒業研究「アナログメーター自動読み取りシステム」として、日本製鋼所様の工場にある丸型の圧力計・温度計をスマホで撮影し、数値化して記録・集約する流れを、11月頃に通しでデモできる状態にする。

2026-09-01以降は、読み取り精度を現状水準で凍結する。先方からの要件回答を待つ間に、精度改善ではなく、撮影から集約までの一連の動作を完成させ、動くものを見せて要件を引き出す。工場内ネットワークの整備状況は不明なため、オフラインを前提とする。

構成は、現場のAndroidアプリ、手元PCの既存Python読み取りシステム、先方のデータ管理サーバーの3段とする。Androidアプリは画像を撮影・保留・送出し、値の算出はしない。PCは既存の `meter_pipeline.py` ほかを変更せずに利用する。先方サーバーへの接続は、PC側のアダプタに閉じ込め、今回の範囲はCSVとJSON Linesの出力までとする。

> [!important] スキーマを実装着手前に固定する
> 過去に `export_to_csv` が2人によって二重実装された。以下のレコード定義と出力責任を共通の前提とし、同じ責務を別々に実装しない。

## 2. 確定レコードスキーマ

1レコードは1回の読み取りを表し、以下を必ず保持する。

| フィールド | 型・値 | 内容 |
|---|---|---|
| reading_id | UUID | 主キー |
| local_id | 文字列またはnull | 端末由来。同じ画像の再処理レコード間で同じ値を持つ |
| captured_at / received_at / processed_at | ISO 8601 | 撮影時刻／PC取込時刻／読み取り実行時刻 |
| device_name | 文字列またはnull | 機器名。未登録・未入力を許容 |
| value | 数値またはnull | 読み取り値。失敗時はnull |
| unit | 文字列またはnull | 単位 |
| status | ok / low_confidence / failed | **自動読み取り**の結果状態。人の入力では変化しない |
| input_method | auto / manual / corrected | **最終的に採用した値**の出所 |
| confidence | 0.0〜1.0またはnull | 読み取りの信頼度 |
| image_path | 相対パス | 保存済み原画像 |
| image_sha256 | SHA-256 | 原画像のハッシュ。重複排除キー |
| failure_stage | null / center / scale / needle / unknown | 失敗段階 |
| failure_code | 文字列またはnull | 短い理由コード |
| failure_detail | 文字列またはnull | 人が読む失敗説明 |
| pipeline_version | 文字列 | 使用したパイプラインの版。gitタグ名をそのまま入れる |
| log_path | 相対パス | 詳細ログ |
| overlay_path | 相対パスまたはnull | 中間オーバーレイ画像 |

- 読み取りに失敗しても、必ずレコードを作る。`value` は `null`、`status` は `failed` とし、撮影記録そのものを失わせない。
- 原画像は無加工で必ず保存し、SHA-256で一意化する。これは重複排除にも用いる。
- 再処理時は既存レコードを上書きしない。同じ `image_sha256` の原画像から、新しい `pipeline_version` を持つ新規レコードを追加する。通常表示では同一画像内の最新を採用し、過去レコードも残して改善前後を比較可能にする。
- **`pipeline_version` はgitタグで固定する。** 版を文字列で自由に名乗らせると、どのコードで出た値か後から特定できず、版間比較が成立しない。過去の版にも遡ってタグを打つ（`tasks/plan-android-sprints.md` のO-08）。この「版を変えて再処理すると誤差が改善する」ことを数値で示すのが本研究の主張の実証にあたるため、このフィールドは記録の付帯情報ではなく実験の主キーである。
- **`status` と `input_method` は直交する。** `status` は自動読み取りがどうなったかだけを表し、人が値を入れても書き換えない。`input_method` は最終的に採用した値がどこから来たかを表す。この2つを混ぜると「自動読み取りが失敗したので人が入力した」（`status=failed` かつ `input_method=manual`）が表現できなくなり、**評価に使えるデータが壊れる**。自動読み取りの成否は精度評価の母数そのものなので、人の訂正で消してはならない。
- **`operator_value`（現場で入力された真値）は画像に紐づき、レコードには紐づかない。** 同じ `image_sha256` に対して1つだけ持つ。再処理で新レコードを追加するときは、その画像に紐づく真値を全レコードから参照できるようにする（レコードごとに複製して食い違わせない）。真値は正解データとして評価に使うため、版によって値が変わってはならない。
- **`reading_id` はPC側が採番する。端末は `reading_id` を知らない。**サイドカーJSONに載せるのは `local_id` であって `reading_id` ではない。
- `failure_stage` は既存 `meter_pipeline.py` が実際に返す `stage` 値に合わせたもの。盤面検出・目盛り検出・OCR・VLMの失敗は現状すべて `scale` に含まれ、区別できない。**細分化はパイプラインの改修（＝精度トラックの凍結解除）を伴うため、今回のスコープ外とする。**判別できない失敗は `failure_code` に理由文字列を入れて残す。

### 画像に紐づく真値（別表）

| フィールド | 型・値 | 内容 |
|---|---|---|
| image_sha256 | SHA-256 | キー |
| operator_value | 数値またはnull | 現場で入力した真値 |
| operator_note | 文字列またはnull | 現場の備考 |
| scale_min | 数値またはnull | 評価に使うフルスケール下限 |
| scale_max | 数値またはnull | 評価に使うフルスケール上限 |
| entered_at | ISO 8601 | 入力時刻 |

既存の `evaluate.py` は引用誤差とJIS 2.5級の合否判定にフルスケール範囲（`min_value` / `max_value`）を必須としており、これが無いと現場で入力された真値を評価データとして使えない。`scale_min` / `scale_max` は任意入力でよいが、入っていれば `eval/groundtruth.json` 形式へ変換できる。CSV / JSONL の出力時にはこの表をレコードへ結合して列として出す（出力の列構成は変えない）。

PC側の出力ルートを基準に、原画像は `images/<image_sha256>.<拡張子>`、ログは `logs/<reading_id>.log`、オーバーレイは `overlays/<reading_id>.png` と命名する。集約ファイルは `readings.csv`（utf-8-sig、Excelで直接開けるため）と `readings.jsonl`（JSON Lines、機械可読）とする。先方が人手で確認するのかシステム連携で取り込むのか未確定のため、両方を出力することが最も安い保険である。

## 3. 送信経路と共通の取り込み口

端末内には未送信キューを1つだけ持つ。送信経路を二重に実装せず、出口だけを切り替える。

- 無線では、キューからPCのHTTPエンドポイントへ画像とメタデータを送信する。PCは受信画像を監視対象フォルダへ置く。
- 有線・SDカード・手動コピーでは、端末の公開フォルダへ `YYYYMMDDTHHMMSS_<local_id>.<拡張子>` と、同じベース名のサイドカーJSONを出力する。
- PCはフォルダに画像が置かれた場合だけを受け口とし、無線・有線を同じ取り込み経路で処理する。

### 取り込みの規約

- 監視フォルダへは一時名で書き、書き終えてから正式名へリネームする。取り込み側は正式名だけを対象にする（**コピー途中の部分ファイルを掴まないため**）。
- サイドカーJSONを先に置き、画像を後に置く。画像の出現を取り込みの開始条件にする。
- 対になる相手が無い場合は取り込まず保留する。

## 画像の取り扱い

企業から受け取った画像を外部へ一切出さないという大原則は、`tasks/企業提供画像の取り扱い.md` を参照する。

- **アプリのバックアップを無効にする。**`android:allowBackup="false"` と `dataExtractionRules` で、クラウドバックアップと端末間転送の両方から除外する。有効のままだと、工場で撮影した設備の写真が利用者個人の Google アカウント経由で外部へ出る（対応済み）。
- **撮影画像を公開領域に常置しない。**アプリ専用領域に保存し、公開フォルダへはPCへコピーする直前に出し、コピー後に削除する。書き出し先には `.nomedia` を置き、ギャラリーやフォトアプリのメディアスキャン対象から外す。
- **HTTP送信先は手元PCのローカルアドレスに限る。**平文HTTPを使う場合は `networkSecurityConfig` でそのホストのみ許可する。

## 4. 機能要件と実装単位

### R1: 共通レコード・保存規約

**内容:** 第2節のレコード生成、原画像保管、重複排除、再処理履歴を実現する。

**受け入れ条件:**
- [ ] 成功・低信頼・失敗のいずれでも、全必須項目を持つレコードが1件作成される
- [ ] 同じ `image_sha256` の通常取り込みは二重登録されず、原画像が無加工で保存される
- [ ] 再処理は新しい `pipeline_version` のレコードを追加し、既存結果を保持する

**検証:** 同一画像の再取り込み、失敗画像、異なる版での再処理を行い、CSV・JSONL・保存ファイルの対応を確認する。  
**依存:** なし　**規模:** M　**担当:** YMさん

### A1: Androidアプリの撮影・キュー・送出

**内容:** 1枚につきメーター1台を撮影し、端末内キューで管理して、2種類の出口へ送出する。画面には撮影ガイド枠をオーバーレイ表示する。機器名は任意で入力または選択でき、真値も任意入力とし、入力値は `operator_value` として送る。リスト画面にはサムネイル、撮影日時、送信状態（未送信／送信済み／失敗）、機器名を表示する。送信済み画像は即時削除せず、保持期間を設定可能にする。

**受け入れ条件:**
- [ ] 通信がない状態でも連続撮影でき、各画像とメタデータが未送信キューに残る
- [ ] 撮影画面にガイド枠が表示され、リストで必要な4項目を確認できる
- [ ] 無線送信と公開フォルダ書き出しのいずれも、同じキューの未送信データを送出できる
- [ ] 機器名・真値が未入力でも送出でき、入力した真値はサイドカーまたはHTTPメタデータに含まれる

**検証:** 圏外で複数枚撮影後にリストを確認し、無線送信と公開フォルダ出力を各1回実施する。  
**依存:** なし（撮影・キュー・リスト画面はR1を待たずに着手できる。R1に依存するのは送出時のサイドカーJSONの項目名だけで、そこはスタブで先に進めてよい）　**規模:** L　**担当:** 本人（キュー）＋ SKくん（UI）

> [!note] 真値入力は必須にしない
> 毎回の入力を強制すると現場負担が増え、「撮るだけ」という利点が失われる。撮影時に値を入力しないケースを正常系として扱う。

### P1: PC側の取り込み・既存パイプライン実行

**内容:** 指定フォルダを監視し、無線・有線の画像を同じ経路で取り込む。`image_sha256` で重複を判定してから既存の `meter_pipeline` を呼び、結果、失敗理由、ログ、オーバーレイを保存する。一括再処理コマンドを持つ。パイプライン本体は変更しない。

**受け入れ条件:**
- [ ] 2経路から届いた画像が同じ監視フォルダ処理を通り、重複なしで1回だけ取り込まれる
- [ ] 既存パイプラインの成功結果と失敗理由が第2節のレコードへ保存される
- [ ] 保存済み原画像を指定して一括再処理し、新規レコードを追加できる

**検証:** 有線・無線で同一内容を投入し、処理回数、失敗記録、ログ・オーバーレイ、再処理履歴を確認する。  
**依存:** R1（**A1の完成は待たない。**監視フォルダへ手作業で画像を置けば単独で検証できる。旧 `tasks/todo.md` のT6-3バッチ取り込みの延長として先行着手する）　**規模:** L　**担当:** SRくん

### E1: 出力・一覧・集約アダプタ境界

**内容:** `readings.csv` と `readings.jsonl` を出力し、機器別・日付別の絞り込みと値の推移グラフを提供する。`manager/export.py`（**現在 `origin/KPdevelopment` にのみ存在。Sprint 1 までに main へ統合する**）にある `filter_readings`、`group_by_device`、`readings_to_series` を流用する。`export_to_csv` は `manager/export.py` の実装を唯一の正とし、`MeterManager.export_to_csv` は削除する。先方サーバー接続は差し替え可能なアダプタのインターフェース定義だけに留め、実接続は実装しない。

**受け入れ条件:**
- [ ] 同一レコード集合から、CSVはutf-8-sig、JSONLは1行1JSONで出力される
- [ ] 機器名と日付の指定で一覧を絞り込み、対象値の推移グラフを表示できる
- [ ] 先方サーバーに依存する処理はアダプタ境界の外へ漏れず、実接続コードを含まない
- [ ] 一覧から1レコードを選び、値と備考を入力して保存すると、`input_method=corrected` として記録される

**検証:** 複数機器・複数日の記録を用いて絞り込み、両出力の内容とグラフ対象が一致することを確認する。  
**依存:** R1、P1　**規模:** M　**担当:** KPくん

日付での絞り込みの基準時刻は `captured_at`（撮影時刻）とする。

## 5. 通しデモの受け入れ条件

- [ ] 圏外でも複数枚を撮影し、端末内キューへ未送信として保持できる
- [ ] 同じ端末キューの画像を、無線と有線・SDカード・手動コピーの各経路でPCへ到達させられる
- [ ] PCが監視フォルダから画像を取り込み、既存パイプラインを実行してレコード・原画像・ログ・オーバーレイを記録できる
- [ ] 読み取り失敗時も `status=failed`、失敗段階・理由付きで残り、手入力または訂正値として記録できる
- [ ] 端末のリストで撮り溜めた画像のサムネイル、撮影日時、送信状態、機器名を確認できる
- [ ] 一覧を機器別・日付別に絞り込み、推移グラフ、CSV、JSONLを確認できる
- [ ] 撮影、送出、PC取り込み、読み取り、失敗時の手修正、一覧・出力までを、11月頃のデモで一連に実演できる

> [!warning] 失敗を捨てない
> 撮影済みの記録が消えることが最悪の挙動である。値を出せない場合も、原画像と理由を残す。これにより、後から人が修正でき、パイプライン改善後にも同じ画像で再処理できる。

## 6. スコープ外

- 端末上でのOCR・VLM・値の算出。読み取りはPC側に置き、既存Python資産を利用する。
- 先方データ管理サーバーへの実接続。
- 丸型以外のメーター（`square`、`fan`、`dark_round`）。2026-08-29の凍結を継続する。
- 複数メーターの同時検出。撮影ガイド枠により1枚1メーターを現場側で担保する。
- 撮影ガイド枠に収まったかを判定して色を変える処理。

## 7. 未確定事項

- 提案の日程（本人が先生に確認する）。
- 実装の担当割り振り。
- 先方のデータ管理サーバー仕様、既存点検表の様式、利用者が点検担当者か集約担当者か（先方の回答待ち）。
- HTTPエンドポイントの具体的プロトコル。暫定案としては、画像ファイルと第2節に対応するメタデータを1回のHTTP送信でPCへ渡す方式とするが、確定ではない。
- 訂正は既存レコードを上書きするのか、新レコードを追加するのか。第2節の「再処理では既存レコードを上書きしない」原則との整合が必要なので、決めずに実装させてはいけない。
- 端末の容量不足時の挙動。
- カメラ・ストレージ権限を拒否されたときの挙動。
- 端末時計のずれ。
