# 実装計画：アナログメーター読み取りシステム（チーム開発版）

## 目的

工場のアナログメーターを撮影するだけでデータ化し、一元管理できるシステムを、
卒業までに完成させる。5人（本人＋メンバー4名）で並行開発するための分割。

## 現状（2026-08-20時点）

**できていること**
- 1画像1メーターのGUIパイプライン（VLMクロップ → Hough中心 → PCA目盛り検出 →
  RapidOCR目盛り数値 → Hough針 → 角度の線形補間で値を算出）
- 精度を自動測定する評価基盤（`evaluate.py` / `meter_pipeline.py` / `meter_reader.py` / `tests/`）
- 実機写真13枚を評価データセットに登録（真値は未記入）

**分かっている問題**
| # | 問題 | 影響 |
|---|---|---|
| P1 | Hough円検出がネジ等を中心と誤検出する | 丸型でも引用誤差37%FS（人の補助なしの場合） |
| P2 | 角形PSK-100は回転中心が黒帯の裏＝盤面外。「中心は画像内」制約が正解を棄却する | 角形メーターが読めない |
| P3 | 可動鉄片形の目盛りは非線形だが、両端2点の線形補間で値を出している | 中間域に系統誤差 |
| P4 | 1枚に複数メーターと銘板が写り、OCRが無関係な数字を拾う | レンジの誤検出 |
| P5 | 写真が90度回転しており、目盛り数字が横倒しでOCRが読めない | レンジ検出の失敗 |
| P6 | 扇形メーターは暗背景に白目盛り。指示針と赤い設定針が併存 | 未対応 |
| P7 | **「一元管理」の部分が未着手** | 最終目標の半分が手つかず |

## 重要な認識

### 現状の「±5程度」は人の補助込みの数字

GUIは各段階で候補を表示して人が修正できる。評価基盤で人の補助なしの
実力を測ると引用誤差37%FSだった。工場で「撮るだけ」を実現する以上、
**人の補助なしの精度が本番の性能**であり、そこを基準に改善する。

### 一元管理システムが未着手

最終目標は「撮影 → データ化 → 一元管理」だが、これまでの開発は
すべて「データ化」に集中しており、「一元管理」は1行も書かれていない。
画像認識の精度をいくら上げても、この部分が無ければ納品物にならない。
**CV班と分離して並行で進める**（必要なスキルも別なので分担しやすい）。

### 人数を増やして速くするための条件

人を増やすと調整コストで逆に遅くなることがある。それを避けるため、
分割は次の3条件を満たすように設計した。

1. **ファイルの担当を分ける** — 同じファイルを2人が触らない
2. **各トラックが単独で成否を判定できる** — 評価基盤の数値が合格基準になる
3. **接続部（インターフェース）を先に決める** — 決めてから並行作業に入る

## リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| 真値ラベルが誤っていて評価が信用できない | 高 | 迷ったら未記入のまま残す。誤ラベルは無ラベルより有害 |
| T1の中心推定が丸型メーターで退行する | 高 | 既存の回帰テスト（過去ログ24件）を必ず通す |
| 複数人が同じファイルを触って衝突 | 中 | 新規ファイルに実装し、既存への接続は最小限の1行に留める |
| 一元管理システムが後回しになり間に合わない | 高 | CV班と独立して今すぐ着手。CVの完成を待たない |
| 評価用データが13枚では少なく、過学習的な改善になる | 中 | 撮影を追加する（T0）。条件（距離・角度・照明）を変えて撮る |
