# Android・PC集約 スプリント計画（`plan.md` 追記候補）

## 目的・前提

確定仕様を、学校での1回の作業日（3時間）単位へ分解する。対象は Android の撮影・キュー・送出、PC側の取り込み、共通レコード保存、一覧・出力であり、既存の読み取り精度や `meter_pipeline.py` 本体は変更しない。

5人とも週4回、残り約8週（1人あたり約32スプリント）が目安である。実装タスクはSprint 7までにそろえ、Sprint 8を版間比較実験に充て、以後は不具合修正、統合、デモ練習のバッファにする。HTTPの具体的プロトコルと先方サーバー仕様は未確定として扱う。

本研究の新規性は読み取り精度そのものではなく、**失敗を捨てず、版を重ねた再処理で改善を測れる運用設計**に置く。したがって「通しで1本動くこと」（Sprint 5）と「版を変えると誤差が改善すると数値で示せること」（Sprint 8）の2つが、卒論として外せない到達点である。

### Sprint 1 を先に置く理由

過去はT0-2の「先に決めるインターフェース」（中心推定・目盛り較正点・読み取り結果の3型）を合意せず着手した。その結果、SKくんとYMさんはモジュールを本番パイプラインへ結線できず、SRくんとKPくんは `export_to_csv` を二重実装した。同じ失敗を避けるため、最初の3時間を全員同席の確定に使う。

## 依存関係と通しデモの方針

Androidは未送信キューを1つだけ持ち、公開フォルダとHTTPを出口にする。PCは経路を区別せず監視フォルダだけを入口にし、R1は保存、P1は取り込み、E1は一覧・出力を担当する。

**Sprint 5が最初の通しデモ**である。「撮影 → enqueue → 公開フォルダ送出 → PC取り込み → 読み取り → レコード保存 → 一覧」を1本通す。HTTP、再送、全失敗分岐、グラフは後続で完成させる。

## 共通運用

- Sprint 1の1時間でキューAPI、サイドカーJSON、監視フォルダ規則を合意する。候補項目は `local_id`、`captured_at`、`device_name`、`operator_value`、`operator_note` とし、PC側付与項目を混ぜない。残り2時間は環境準備に使う。
- SKくんには、Codexが事前に生成・動作確認した雛形（プロジェクト、カメラ権限、保存先設定）を渡す。白紙から作らせない。
- SRくんは**毎回の着手前に必ず** `git fetch origin && git rebase origin/main` を実行する。競合を解消・確認してから実装する。
- YMさんには「対象を開く → 指定データを作る／保存する → テスト」の順で渡す。KPくんは目的を明記し1機能だけを担当する。先方サーバーの実接続は実装しない。
- チェックポイントではPC側の共通テスト、Android実機画面、保存物・出力を確認する。

> [!important] 「仕様書への依存」と「他人の実装物への依存」を混同しない
> レコードスキーマは仕様書で確定済みなので、**それを参照する作業は誰の実装も待たない**。
> 手書きのダミーレコードやスタブで先に進め、実物ができたら差し替える。
> 依存として書いてよいのは「その人の書いたコードを実際に呼ぶ」場合だけ。
> **同じスプリント内で一方が他方を待つ依存は、必ず破綻する。**見つけたらその場で外す。

> [!warning] チェックポイントで遅れたときの削り方
> 人を増やせないので、間に合わせる手段はスコープを削ることしかない。
> **上から順に外す**（下に行くほど守る）:
>
> 1. 無線経路（SR-08 と O-05）。デモは公開フォルダ経路1本で成立する
> 2. 値の推移のグラフ表示（KP-06）
> 3. 機器別・日付別の絞り込み（KP-05の絞り込み部分）
> 4. 撮影ガイド枠の表示（SK-04）
> 5. 保持ポリシー（O-07）
> 6. 一括再処理（SR-07・YM-07）
>
> **通しで1本通ること（撮影 → 送信 → 取り込み → 読み取り → 一覧）は削らない。**
> ここが通らなければ提案そのものが成立しない。

**評価と卒論執筆のスプリント（Sprint 8）は削らない。**『通しで1本通ること』と同格で守る。
版間比較の数値が無いと、新規性の主張そのものが実証されないまま卒論を書くことになる。

```text
venv\Scripts\python.exe -m unittest discover -s tests
venv\Scripts\python.exe evaluate.py eval/groundtruth.json --no-vlm --scope round
```

## Sprint 8: 版間比較実験と評価データの接続

> [!important] このスプリントは卒論の主張そのものを支える
> 本研究の新規性は「失敗を捨てず、版を重ねた再処理で改善を測れる運用設計」に置く。
> この主張を実証するには、**同じ画像集合を版を変えて再処理すると誤差が改善する**という数値が要る。
> 通しデモ（撮影 → 送信 → 取り込み → 読み取り → 一覧）が「動くこと」を示すのに対し、
> こちらは「その設計に意味があること」を示す。**削り方リストには入れない。**

> [!note] 新しく実験を回す必要はない
> 比較対象のデータはすでにgit履歴の中にある。精度が上がった各段階のコミットを
> `pipeline_version` として扱い、同じ丸型9枚に遡って再処理すれば版間比較表が作れる。
> **パイプラインには一切手を入れないので、精度凍結の方針とも矛盾しない。**

### 検証済みの前提（2026-09-01時点）

実験の実行可能性は本人が確認済み。以下は調査結果であり、着手時に再確認する必要はない。

  現在の `evaluate.py` から旧版パイプラインをそのまま駆動できる。

- 旧版に無い `scale_diagnostics` は `row.get()` と `diagnostics or {}` で吸収済み。落ちない。
- **ただし `--scope` は `81ef30c` より前の `evaluate.py` に存在しない。**
  そのため「旧コミットを丸ごとcheckoutして旧 `evaluate.py` を実行する」方式は取れない。
