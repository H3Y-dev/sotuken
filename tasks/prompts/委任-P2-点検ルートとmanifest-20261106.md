## 実装すること
1. **点検ルート(DB)**: 新しいテーブル `inspection_routes`(route_id TEXT PK、name、updated_at)と `inspection_route_devices`(route_id、position、device_id、device_name)。ルートIDは自動生成(例: `R-` + 日時 + 乱数4文字、`[A-Za-z0-9._-]` 1〜64文字)。機器は既存の機器の表 `devices` から選ぶ(devicesに無いIDも「手入力で追加」できる。機器IDは validate_device_id、名前は validate_device_name)。既存DBを壊さないマイグレーション(CREATE TABLE IF NOT EXISTS)。
2. **PC画面**: app.py に新しいタブ「点検ルート」。ルートの一覧、新規作成(名前・機器の追加・並べ替え・削除)、編集、削除(確認つき)。画面の見出しで「点検結果」(機器ごとの判定)との違いが分かる文言にする。**ルートQRの表示**: 選んだルートについて `SOTUKEN-ROUTE:` + JSON(取り決めどおり。`devices` を含む。約1,500バイトを超えるときはQRを出さず「Wi-Fiで取得してください」と表示)を、既存の qrcode でQR画像にして出す(PairingのQR表示の流儀に合わせる)。
3. **受信口(manager/receiver.py)**: `GET /routes`、`GET /routes/<route_id>`(どちらも X-Sotuken-Token 必須、401/404、取り決めどおりのJSON)。`POST /inspections/<inspection_id>/manifest`(トークン必須、本文はJSON、サイズ上限と本文の読み取り期限は既存の /upload に合わせる、`validate` は取り決めどおり。無効なJSONは400)。受信口とStreamlit画面は別プロセスの場合があるので、受信口がDBを読むときは既存の流儀(storage の接続の作り方)に従う。
4. **manifestの保存と判定**: テーブル `inspections`(inspection_id PK、inspection_name、route_id、operator、place、started_at、completed_at、manifest_received_at、manifest_json)と、判定。manifestの `photos` の各 `sha256` を、受信済みの画像と突き合わせる(受信済みの画像のsha256は、既存のどこかで保持・計算している。無ければ、meter_readings の画像から計算する関数を足す。重い再計算を毎回しない)。点検の状態: 「受信中」(manifest未着)、「完了」(manifestの全写真が到着)、「不足あり」(N枚未着。ファイル名一覧)。manifestの再送は同じ点検IDで上書き。応答は取り決めの `{"ok":true,"matched":N,"missing_photos":[...]}`。
5. **点検の状態の画面**: 記録タブの点検の機器一覧表(#119)に、点検を選んだときの状態(受信中/完了/不足あり、未着の写真)、ルートがある点検では「ルートの機器 × 撮影済み/未撮影」「一覧外の機器=追加」を足す(manifestの `missing`/`extra` と、実際の写真から求めた値を両方使い、食い違えば写真を正とする)。ルートが無い点検では今までの表のまま。
6. **サイドカーの `route_id`**: 任意キー `route_id` を、sidecar.py・receiverの検証・DB(meter_readings.route_id TEXT)・再処理・書き出しへ、#119 の inspection_id と同じ扱いで足す(旧データ・旧アプリは今までどおり)。
