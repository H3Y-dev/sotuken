## 1. プロジェクトの背景

### 何を作っているのか

工場のアナログメーター（電流計・温度計など）を**スマホ等で撮影するだけで**、針の指す値を自動で読み取り、データ化して一元管理するシステムを作っています。**日本製鋼所様との共同研究**で、卒業までの完成が目標です。

現場では今、点検員がメーターを目視して紙やExcelに転記しています。この転記作業をなくすのが最終的な狙いです。「撮影 → 読み取り → 記録 → 一覧」が通しで動くところまでが完成形で、現在は「読み取り」の精度を上げている段階です。

### 現在のパイプライン

1画像1メーターを前提に、次の順で処理しています。

```
VLM(Qwen3-VL)で盤面をクロップ
  → Hough円検出で回転中心を推定    ← ここがSKくんの担当箇所（他候補と併用）
  → PCAベースで目盛り線を検出（数十本）
  → RapidOCRで目盛りの数値を読み取り、目盛り線に対応付け
  → Hough変換で針を検出
  → 針の角度を線形に按分して値を算出
```

### 精度の測り方（チーム共通の言語）

主指標は **引用誤差 [%FS]** です。定義は次のとおりで、`evaluate.py` の `reference_error()` に実装されています。

```
引用誤差[%FS] = |読取値 − 真値| / |val_max − val_min| × 100
```

相対誤差（真値で割る）ではなく引用誤差を使うのは、真値が0付近だと相対誤差が発散して比較できなくなるためです。また、計器の確度階級（**JIS C 1102 の 2.5級 = ±2.5%FS**）もフルスケール基準で定義されているので、そのまま合否判定に使えます。合格ラインはこの ±2.5%FS です。

なお、人の補助なしの現状の実力は**引用誤差 37%FS** です（円形メーターでの実測値。評価基盤 `evaluate.py` による）。目標との差は大きく、SKくんのタスクはその差を詰める複数トラックのうちの1つです。詳しい経緯は `卒研/進捗ログ.md` にあります。

### チーム構成（並行開発中）

5人で並行開発しており、**ファイルの担当を分けることで衝突を避ける**方針です。他メンバーが同時に別のファイルを触っています。詳細は `tasks/plan.md` と `tasks/todo.md` にあります。

## 2. SKくんの担当タスク: T1-2 中心候補の検証と選択

### 何が問題なのか

現在、メーターの回転中心（＝針の軸）は Hough円検出（`tick_detect.auto_detect_center`）で決めています。これが**メーター盤面の裏にあるネジや反射などの、別の丸い模様を誤検出する**ことがあります。

さらに別の問題があります。「角形PSK-100」という型のメーター（`C:\卒研\images\20260817_*.jpg` のうち5枚）は、針の回転軸が**黒いプラスチック帯の裏＝盤面のクロップ画像の外**にあります。ところが現行コードの `tick_detect.refine_center_from_ticks` には次の制約があります。

```python
h, w = img_shape[:2]
if not (0 <= cx < w and 0 <= cy < h):
    return None
```

「中心は画像内でなければならない」というこの制約が、角形メーターの正しい中心を弾いてしまいます。この2つの問題（ネジの誤検出／画像外の中心を扱えない）を合わせて、円形メーターでも人の補助なしの引用誤差は37%FSという結果になっています。

これに対して、中心推定を作り直すプロジェクトT1が動いています。目盛り線は必ず盤面の中心を通るという幾何学的な性質を使い、**目盛り線同士の交点をRANSAC＋最小二乗で求める**新しい推定関数 `estimate_center(img, ticks)` を、本人（リポジトリオーナー）が実装中です（T1-1）。この関数は「中心が画像の外（負の座標や画像サイズを超える座標）を返してもよい」設計にします。インターフェースは `tasks/plan.md` で既にチーム合意済みです。

### SKくんの担当（T1-2）— 2つの仕事

**1. 円フィッティングによる独立した中心推定**

検出済みの目盛り線の重心点群（`tick_detect.detect_scale_ticks` が返す各要素の `centroid`）に対して円をフィッティングし、中心を推定します。これは「目盛り線が実際に円弧上に並んでいる」という、T1-1（目盛り線の交点）とは**別の幾何学的事実**を使う検証経路です。T1-1が線の「向き」を使うのに対し、こちらは点の「位置」だけを使います。

**2. 複数候補からの選択ロジック**

最大3つの中心候補が出揃います。

- Hough円検出の結果（`tick_detect.auto_detect_center`）
- `estimate_center` の結果（T1-1、本人実装）
- 円フィッティングの結果（上記1、SKくん実装）

これらの一致度（互いの距離が画像サイズに対してどれだけ近いか）を見て、どれを採用するか（多数決、全員不一致なら棄却してNoneを返す、等）を決めるロジックを実装します。

現行コードはこの判定を単純な2択でやっています。`meter_pipeline.py` の `_detect_center` がそれです。

```python
def _detect_center(img):
    h, w = img.shape[:2]
    hough = tick_detect.auto_detect_center(img)
    seed = (hough[0], hough[1]) if hough is not None else (w // 2, h // 2)
    try:
        refined, _ticks = tick_detect.refine_center_iterative(img, seed)
    except Exception:
        refined = None
    if hough is not None and refined is not None:
        shift = math.hypot(refined[0] - hough[0], refined[1] - hough[1])
        if shift > min(h, w) * 0.03:
            return refined, 'corrected'
        return (hough[0], hough[1]), 'hough'
    if hough is not None:
        return (hough[0], hough[1]), 'hough'
    if refined is not None:
        return refined, 'ticks'
    return None, None
```

「Houghと目盛り線推定が画像短辺の3%以上ずれたら目盛り線側を採用」という単純な2択判定です。これを3候補対応・根拠のある判定に置き換えるのがSKくんの仕事です。

**この関数の戻り値の型は変えないでください。** `(center, center_source)` のタプルで、`center` は `(x, y)` の int/float タプルか `None`、`center_source` は文字列か `None` です。`meter_pipeline.read_meter()` がこれを `result['center_source']` にそのまま入れ、`evaluate.py`（触ってはいけないファイル）がレポートに転記します。`center_source` の文字列の中身（`'hough'` 以外にどんな値を入れるか）は自由に決めてよく、既存コードはこの文字列の値で分岐していません。

### 重要な配線上の注意（見落としやすい点）

現行の `_detect_center` は目盛り線ベースの候補を `tick_detect.refine_center_iterative` から得ています。この関数は内部で `refine_center_from_ticks` を呼んでおり、**そこに例の「中心は画像内」制約があります**。つまり、新しい `_detect_center` でもし目盛り線側の候補を `refine_center_iterative` から取り続けると、角形PSK-100の問題（中心が画像外）は解決されないままになります。

新しい `_detect_center` では、目盛り線ベースの候補は `tick_detect.refine_center_iterative` ではなく、**`center_estimate.estimate_center`（T1-1／スタブ）から取ってください。** `tick_detect.py` 自体は今回触ってはいけないファイルなので、このモジュールの制約を書き換えることはできません。書き換えずに済むように、T1-1は新しい別関数として作られています。

### 「独立」の限界について（設計時に意識してほしいこと）

`estimate_center`（T1-1）も円フィッティング（SKくん担当）も、入力は同じ `ticks`（`tick_detect.detect_scale_ticks(img, center)` の出力）です。この `detect_scale_ticks` は**引数の `center` を使って、輪郭が放射方向を向いているか・距離が妥当かをフィルタしています**。つまり「どの目盛りが目盛りとして採用されるか」自体が、最初に与えた中心（シード）に依存します。

これが意味するのは、もしシードが大きくずれていた場合（Houghがネジを誤検出した場合など）、正しい目盛り線が「中心を向いていない」と判定されて弾かれ、`ticks` 自体が痩せる／空になる可能性がある、ということです。この場合、`estimate_center` と円フィッティングは「別の幾何学的事実を使っている」とはいえ、**同じ（偏った）入力点群を共有しているため、両者が同時に間違う相関がありえます。** 一方Houghは目盛り検出を経由しない完全に独立な経路です。

この点を踏まえると、選択ロジックの「多数決」は次のように考えるとよさそうです。

- estimate_centerと円フィッティングが一致している ＝ 「同じ ticks から2通りの方法で導いても一致した」という程度の裏付け
- それに加えてHoughも一致している ＝ 独立な経路からも裏付けが取れた、最も信頼できる状態
- Houghだけが他の2つと食い違う ＝ ネジ等の誤検出を疑ってよい根拠になる

どの ticks を（どのシードで）候補全体に使うかは、T1-1側の実装（本人）とも関わる設計判断です。**推測で決め打ちせず、着手前に本人と認識を合わせてください。**

## 3. 円フィッティングの数学的な選択肢

目盛りの重心点群 `{(x_i, y_i)}` から円の中心 `(a, b)` と半径 `r` を求める代数的円フィッティングには、主に次の選択肢があります。

| 手法 | 計算 | 特徴 |
|---|---|---|
| **Kåsa法** | `x_i² + y_i² = D·x_i + E·y_i + F` の形の線形最小二乗（`numpy.linalg.lstsq` 1発）。中心は `(D/2, E/2)` | 実装が最も簡単。ただし点群が円周の一部（狭い弧）しかカバーしていない場合、**半径を小さく見積もる系統的バイアス**が知られている |
| **Taubin法** | 中心化した座標のモーメント行列から一般化固有値問題を解く | Kåsaより幾何学的（実際の距離）に近い評価をするため、狭い弧でのバイアスがKåsaよりかなり小さい。閉形式（反復なし）で、numpyだけで書ける（30〜40行程度） | 
| **非線形最小二乗**（真の幾何学的フィット） | 各点と中心の距離 `r_i = hypot(x_i-a, y_i-b)` の分散を最小化。反復法（Gauss-Newton等）が必要 | 最も正確だが実装コストが高く、初期値（Kåsa等の結果）が要る |

**判断の指針:** 目盛り線は盤面のどれだけの角度範囲に分布しているか（扇形メーターなら180°未満のこともある）によってKåsaのバイアスの大きさが変わります。**まずKåsa法で実装し、`meter1.png`〜`meter4.jpg` や `tests/fixtures/` の画像で実際に中心のずれを確認してください。** バイアスが無視できないと分かった場合にTaubin法へ進む、という順序が合理的です（このリポジトリの他の実装判断も「まず簡単な方法で数字を出し、足りなければ次の手」という順序を踏襲しています）。

外部ライブラリは使わず、`numpy` の範囲で実装してください（`requirements.txt` に scipy の記載がなく、依存を増やさない方針のため）。

**縮退ケースに注意してください。**
- 点が3点未満では円は定まりません（`None` を返す）
- 点がほぼ一直線上に並んでいる場合（狭い弧、またはノイズで潰れている場合）、線形最小二乗の行列が悪条件になります。フィット結果の妥当性（半径が画像サイズに対して常識的な範囲か等）を確認するチェックを入れてください
- 例外は投げず、`None` で安全側に倒してください（このリポジトリの一貫した流儀です。`tick_detect.py` の各関数も同様の書き方をしています）

## 8. SKくんから出そうな質問への回答（先回り）

**Q. T1-1（`estimate_center`本体）がまだ終わっていません。どう進めればいいですか？**
A. 待つ必要はありません。3節に書いたインターフェース通りのスタブを自分で用意し、円フィッティングと選択ロジックを先に書き進めてください。本人の実装が完成したら、シグネチャさえ守っていれば差し替えるだけで済みます。テストは合成データ（人工的に生成した円周上の点群）で書けるので、実画像や本物の`estimate_center`が無くても着手できます。

**Q. なぜ候補を3つも作るんですか？ Houghと目盛り線推定の2つで十分では？**
A. 現行の2択判定の弱点は、「目盛り線推定」自体が単一の方法（線の交点）に依存していることです。もしその方法自体が失敗する条件（目盛り線の検出精度が悪い等）だと、2択のどちらも信用できません。円フィッティングは目盛り線推定とは別の幾何学的性質（点が円周上に並ぶこと）を使うので、目盛り線推定が間違っていても円フィッティングだけは正しい、というケースが生まれます。3つあれば「2つが一致すれば信頼できる」という多数決が成立し、Houghがネジを誤検出したケースを、他の2つの不一致から検出して棄却できます。

**Q. Kåsa法とTaubin法、最初からどちらを使うべきですか？**
A. **まずKåsa法で実装してください。** 実装が簡単で、線形最小二乗1発で解けます。目盛り線が円周の狭い範囲にしか分布していない場合（扇形メーターなど）はバイアスが出ることが知られていますが、円形メーターの目盛りは通常270°前後をカバーするので、実害があるかどうかは実際に `meter1〜4` や `tests/fixtures/` で確かめてから判断するのが順序です。バイアスが無視できないと分かったときにTaubin法に進んでください。最初から凝った手法を選ぶのは、複雑さを増やして得られるものが小さい典型例です。

**Q. `ticks` はどこから取ればいいですか？ Houghの結果が間違っていたらticksも間違いませんか？**
A. 鋭い指摘です。2節「独立の限界について」に書いた通り、`tick_detect.detect_scale_ticks(img, center)` は与えた `center`（シード）で目盛りをフィルタするため、シードが大きくずれるとticks自体が痩せます。この「どのシードでticksを作るか」は`estimate_center`側（T1-1、本人）の実装にも関わる設計判断なので、**推測で決めずに本人と相談してください。** 少なくとも、`estimate_center`と円フィッティングが同じticks集合を共有している以上、この2つの一致は「独立した2つの証拠」というより「同じ入力からの2通りの計算が一致した」程度の裏付けだと捉えておくのが安全です。

**Q. Houghが失敗して、`estimate_center`と円フィッティングのどちらか一方しか候補が無いときはどうしますか？**
A. これも設計判断です。現行コードは「Houghか目盛り線推定、片方でもあればそれを採用する」という寛容な作りになっており、これのおかげで多くの丸型メーターが動いています。候補が1つしかないときに厳しく棄却しすぎると、既存の成功ケースまで退行させる恐れがあります。5節の回帰確認テスト（`tests/fixtures/`との比較）で実際に確かめながら、閾値や棄却条件を調整してください。

**Q. 選択ロジックの一致度の閾値はいくつにすればいいですか？**
A. 数値を先に決めるのではなく、**画像の短辺に対する比率（%）で決めてください。** 現行コードの `refine_center_from_ticks` の `max_shift_ratio` や、`meter_pipeline._detect_center` の `0.03`（3%）がこの考え方の前例です。絶対ピクセル数で決めると、画像の解像度が変わるたびに意味を失います。具体的な値は、`meter1〜4` と `tests/fixtures/` で候補同士の距離の分布を実際に見てから決めるのが順序です。

**Q. `tests/test_regression_logs.py` が通ったので中心検出も大丈夫ですよね？**
