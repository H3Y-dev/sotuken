## 1. 最初にすること：rebaseを終えてから始める

`SRdevelopment` ブランチの最終コミットは2026-08-28で、mainから大きく遅れています。今日の作業では、**何より先にrebaseを終えること**が必要です。次のコマンドを1つずつ実行してください。

```text
git status
git fetch origin
git rebase origin/main
```

`git rebase origin/main` が成功したら、その結果を整理メモに記録してください。

競合（conflict）が出たら、**無理に直そうとしないでください。** 競合が表示された画面のスクリーンショットを撮り、本人（大久保）に見せて止まってください。自分だけでファイルを書き換えたり、推測で競合を解消したりしないことが大切です。

## 2. 今日やること：SR-02 監視フォルダ設計と `manager/batch.py` の現状を整理する

これは**実装タスクではありません。** `manager/batch.py` を直したり、新しい監視処理を書いたりせず、今ある状態を調べて1枚に整理する調査・設計タスクです。

成果物は、`tasks/design/` に置くMarkdownファイル1枚を提案します。S1の規則に沿って、次の4点を1枚にまとめてください。

## 3. なぜ必要か

工場から届いた画像をPCが受け取るとき、どの場所を見ればよいか、処理中のファイルをどこへ置くかが曖昧だと、同じ画像を二度読んだり、途中コピーの画像を読んだりします。先に流れを1枚にしておけば、次回の実装で「何を使えて、何がまだ無いか」を全員が同じように見られます。

## 6. 守ってほしいこと

- 着手前に必ず `git fetch origin` と `git rebase origin/main` を実行する
- rebaseで競合が出たら無理に直さず、画面のスクリーンショットを撮って本人（大久保）に見せる
- 企業提供画像・DBファイル（`manager.db`）・出力CSVをコミットしない。`git add -A` は使わず、変更したファイルを個別に指定して add する
- `print()` に絵文字を使わない（Windowsのcp932でUnicodeEncodeErrorになる）
- 分からないことがあれば本人（大久保）に聞く
- 今回は調査・設計だけです。`manager/batch.py` の実装・修正はしないでください

## 8. 最後に必ずやること：日報を書く

今日の作業が終わったら（途中で終わった場合も含めて）、日報をMarkdownファイル1枚にまとめてください。
ファイル名は `日報_<名前>_<YYYYMMDD>.md` です。書く内容は次の8項目です。
**分からない項目は「なし」と書き、空欄にしないでください。**

1. **名前と日付**
2. **今日のタスク名**（タスクIDを付ける。例: SK-02 Android雛形を実機で起動する）
3. **やったこと** — 実際に手を動かした内容を3〜5行で。やろうとしたが着手できなかったことは、そう書く
4. **成果物** — 作成・変更したファイルのパス。コミットしたなら**コミットのハッシュ（先頭7文字）と
   ブランチ名**も書く。コミットしていないなら「未コミット」と書く
5. **テスト結果** — 実行したコマンドと、何件中何件パスしたか。実行していないなら「未実行」と、その理由
6. **受け入れ条件の達成状況** — 渡された受け入れ条件を1つずつ書き出し、達成／未達成を付ける
7. **詰まったところ・分からなかったこと** — **ここが一番大事です。** 解決できなかった点、判断に迷った点、
   推測で進めた箇所を正直に書いてください。「特になし」で済ませず、少しでも自信のない箇所は書き出してください
8. **次に必要なこと** — 次回やること、または大久保に判断・確認してほしいこと

### 日報を書くときの注意

- **できなかったことを隠さないでください。** 進捗が無かった日も、どこで止まったかが分かれば次の手を打てます。
  うまくいったように書かれるのが一番困ります
- **推測で断定しないでください。** 確認していないことは「未確認」と書いてください
- 企業提供画像そのものや、その内容が分かる記述を日報に含めないでください
- 絵文字は使わないでください（Windowsのcp932で文字化けします）
