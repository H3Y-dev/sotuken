## 1. T1-2の価値が上がっています

8/25〜8/26にかけて、目盛り検出とその先の処理が作り直されました。その結果、**中心推定の精度が、それより下流の全ての処理の前提になりました。**

具体的には、現在の処理はこうなっています。

1. 中心を推定する
2. その中心を原点として画像を極座標に変換し、**角度方向に周期的に現れる暗い線**を目盛りとして検出する（`tick_detect.detect_scale_ticks`）
3. 検出した目盛りを円弧に沿った「通し番号」に直し、**等間隔の格子**として扱う（`scale_value_detect._tick_slots`）
4. OCRで読んだ数字と通し番号の間に直線を当てはめ、主目盛りの周期と位相を求める（`scale_value_detect.build_tick_grid`）
5. その格子を検出範囲の外へ延長して、写っていない位置の目盛り座標を計算する（`scale_value_detect.extend_ticks_to_numbers`）

**中心がずれると、2番の極座標変換の時点で目盛りが等間隔に並ばなくなります。** そうなると3〜5がすべて崩れます。中心のずれは、下流で「目盛りの検出漏れ」や「周期が求まらない」という別の症状として現れるため、原因が分かりにくくなります。

つまりT1-2は「中心の精度が少し上がる」タスクではなく、**その先の周期モデル全体が成り立つかどうかを決めるタスク**になりました。この位置づけをSKくんに伝えてください。

## 3. 現在の中心推定の実装（ここに手を入れる）

`meter_pipeline.py` の `_detect_center(img)` が入口です。現状は2候補しか使っていません。

- `tick_detect.auto_detect_center(img)` … Hough円検出。**戻り値は `(x, y, r)` の3要素タプル**（`(x, y)` ではありません。ここを間違えると `ValueError: too many values to unpack` になります）。失敗時は `None`
- `tick_detect.refine_center_iterative(img, seed_center, iterations=2, max_shift_ratio=0.35)` … 目盛り検出を挟んで中心を反復補正する。戻り値は `(center, ticks)` のタプル
- `tick_detect.refine_center_from_ticks(ticks, fallback_center, img_shape, max_shift_ratio=0.15)` … 検出済みの目盛りから中心を補正する。**`fallback_center` は2要素タプルを渡すこと**

3候補目にあたる `center_estimate.estimate_center(img, ticks=None)` は実装済みでmainに入っていますが、`_detect_center` からは呼ばれていません。**ここを統合するのがT1-2の中核です。**

## 4. 独立性についての重要な注意

3つの候補は**対等な3票ではありません。**

- `estimate_center`（目盛り線の交点）と `fit_circle_to_ticks`（目盛り重心への円フィッティング）は、**どちらも同じ `tick_detect.detect_scale_ticks` の出力を入力にしています。** 目盛り検出そのものが誤れば、この2つは同じ理由で同時に外れます
- Hough円検出だけが、目盛りとは無関係な**盤面外周のベゼル**という別の画像特徴を見ています

したがって「3つ一致したから正しい」という単純な多数決は成り立ちません。**「Hough」対「目盛りベースの2手法」という2系統の構造がある前提で一致度を評価してください。** この限界はそのまま卒論に書ける内容なので、実装のコメントに理由として残しておくとよいです。
