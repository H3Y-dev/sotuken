## 2. 3候補統合ロジックの詳細設計

まず、3つの候補がそれぞれ何を返すかを正確に把握してください。

**候補1: Hough円検出**（`detect_meter_center_v2.py`の`detect_meter_center_from_raw(raw_img)`）
戻り値は`dict`（`center`, `radius`, `diameter`, `param2`, `selection_mode`, `crop_box`）または検出失敗時`None`。`center`は元画像上のグローバル座標。

**候補2: `estimate_center`**（`center_estimate.py`、T1-1として2026-08-24に完成・main統合済み）
シグネチャは`estimate_center(img, ticks=None)`。`ticks`を渡す場合は各要素が`centroid`と`line_angle`を持つ辞書。目盛り線の交点をRANSAC的に総当たりで求め、最小二乗でフィットする実装です。戻り値は`(x, y)`のfloatタプル、推定不能なら`None`。**中心が画像外に出ていてもそのまま座標を返す**（`tests/test_center_estimate.py`の`test_can_return_center_outside_image`で担保されている挙動）ので、統合ロジック側で「画像外だから棄却」という早合点をしないこと。

**候補3: 円フィッティング**（`circle_fit.py`の`fit_circle_to_ticks(ticks, method="taubin")`）
戻り値は`{"center": (xc, yc), "radius": r, "method": method}`。`ticks`は`centroid`キーを持つ辞書列でよく、`estimate_center`とは違って`line_angle`は不要（点群だけで円をフィッティングするため）。

**重要な限界を先に明記しておきます。** `estimate_center`と`fit_circle_to_ticks`はどちらも同じ`tick_detect.py`の目盛り検出結果（`ticks`）を入力に使います。つまりこの2つは「独立した2つの情報源」ではなく、「同じ目盛り検出結果に対する2通りの幾何計算」です。目盛り検出そのものが誤っていれば（例: ノイズを目盛りと誤認識した場合）、この2つは同じ理由で同時に外れる可能性があります。**Hough円検出だけが、目盛り検出とは無関係な独立した情報源**（盤面の外周ベゼルという別の画像特徴を見ている）です。3候補一致を「3つの独立した投票」として単純に多数決するのではなく、「Hough vs (目盛りベースの2手法)」という構造がある前提で一致度を評価する必要があります。この限界は卒論にもそのまま書ける内容なので、実装コメントに残しておくとよいです。

**一致度判定の設計**は、既存の`meter_pipeline.py`の`_detect_center`（32〜57行目）と矛盾しない形にしてください。現状のロジックは次の通りです。

```python
def _detect_center(img):
    h, w = img.shape[:2]
    hough = tick_detect.auto_detect_center(img)
    seed = (hough[0], hough[1]) if hough is not None else (w // 2, h // 2)
    try:
        refined, _ticks = tick_detect.refine_center_iterative(img, seed)
    except Exception:
        refined = None
    if hough is not None and refined is not None:
        shift = math.hypot(refined[0] - hough[0], refined[1] - hough[1])
        if shift > min(h, w) * 0.03:
            return refined, 'corrected'
        return (hough[0], hough[1]), 'hough'
    if hough is not None:
        return (hough[0], hough[1]), 'hough'
    if refined is not None:
        return refined, 'ticks'
    return None, None
```

これは「Houghと目盛り側（`tick_detect.refine_center_iterative`、`estimate_center`とは別の既存関数）の2択、画像短辺の3%を閾値にずれていたら目盛り側を採用」という単純な2択ロジックです。3候補版でもこの**画像短辺に対する割合で閾値を決める**という考え方はそのまま引き継いでください（環境やメーターのサイズによらず相対的なスケールで判定できるため）。

3候補版の判定案（たたき台。SKくんと相談して決めてよい）:

1. Hough (`h`)、`estimate_center` (`e`)、円フィッティング (`f`) の3点をそれぞれ求める（取得できなかったものは候補から除外）。
2. 候補が3つとも揃った場合、3点間の距離 `dist(h,e)`, `dist(h,f)`, `dist(e,f)` を計算し、画像短辺の一定割合（例えば3%、既存の`_detect_center`の閾値を踏襲）を閾値`T`とする。
3. 2点以上が互いに`T`以内なら「一致している」とみなし、一致しているグループの重心（または中央値）を採用する。
4. 3点がどれも互いに`T`以内に収まらない（＝全て割れている）場合は棄却して`None`を返す。呼び出し側（`meter_pipeline.py`）は`None`を「中心検出失敗」として扱う（既存の`STAGE_CENTER`と同じ扱い）。
5. 候補が2つしか揃わなかった場合（例えば目盛り検出が失敗して`estimate_center`と円フィッティングが両方`None`）は、既存の`_detect_center`と同じ2択ロジックにフォールバックする。
6. 候補が1つしか無い場合はそれをそのまま採用する（一致度判定はできないため、`center_source`にその旨を記録する）。

この案の閾値・多数決の細部はSKくんと合意した上で決めてください。ポイントは「既存の3%閾値という考え方の一貫性を保つこと」と「全会一致しない場合にNoneを返す棄却パスを必ず用意すること」です。

## 3. ネジ誤検出への対策

`tasks/todo.md`の受け入れ条件「ネジを中心と誤検出した場合に棄却できる」に対応する具体案です。

Houghがネジ・リベットのような小さい円を盤面中心と誤検出するケースを想定すると、有効な対策は**半径の妥当性チェック**です。`detect_meter_center_v2.py`の`detect_meter_center`は`minRadius=int(img_shape[0] * 0.2)`、`maxRadius=int(img_shape[0] * 0.6)`という制約を既に持っているので、この段階である程度は防げているはずですが、`crop_to_meter_face`側の1段階目（`minRadius=int(min(img.shape[:2]) * 0.1)`）はより緩いため、クロップが小さすぎる範囲を切り出してしまう余地が残っています。

追加のチェック案:
- **目盛り線の密度との整合性チェック**: `estimate_center`または円フィッティングが求めた中心から見て、Houghが求めた中心が目盛りの`centroid`群の重心から極端に離れている（例えば目盛り群の外接矩形の対角線の一定割合以上）場合、Houghの候補を「ネジ等の誤検出の疑いが強い」として一致度判定に参加させる前に単独で棄却する。
- **半径の相互チェック**: Hough側の`radius`と、円フィッティング側の`radius`を比較し、大きく食い違う（例えば半分以下）場合はHough候補の信頼度を下げる。ネジのような小さい円は半径が明らかに小さく出るため、この比較だけでもかなり弾けます。

どちらか1つは実装し、実際にネジが写り込んだサンプル画像（無ければ人工的にネジらしい小円を合成した画像でよい）でテストしてください。

## 4. テストの書き方

**`tests/test_regression_logs.py`が何を担保しているか**を必ず理解してから着手してください。このテストは、過去にGUIで実際に検出したときの入力（画像・中心点・ゼロ点・フルスケール点・目盛りの最小/最大値）と出力（角度・値）のペアを`tests/fixtures/`（git管理下、現在5件）と`logs/`（サイズの都合でgit管理外、手元にあれば追加で使われる）から読み込み、同じ入力を与えたときに同じ出力になることを確認する回帰テストです。**このテストが通らなくなったら、既存の丸型メーターの検出結果を壊したということです。** `_detect_center`を書き換えたら、コミット前に必ず

```
venv\Scripts\python.exe -m unittest discover -s tests
```

を実行し、全部通ることを確認してください。これがT1-2の受け入れ条件「丸型メーターで従来の正解が維持される（退行なし）」の実質的な担保です。

**加えて、統合ロジック自体の単体テストを新規に書いてください。** `tests/test_center_estimate.py`のスタイル（`unittest.TestCase`、合成データをその場で作る、`assertAlmostEqual`で許容誤差付き比較）を踏襲し、例えば`tests/test_center_consensus.py`のようなファイルを新規作成して、少なくとも次のケースをカバーしてください。

- 3候補がほぼ一致する場合に、その近傍の値を返す
- 1候補だけが大きく外れている場合に、残り2候補側を採用する
- 3候補が互いに全く一致しない場合に`None`を返す（棄却）
- 候補の一部が`None`（検出失敗）の場合に、残りの候補で正しくフォールバックする

`circle_fit.py`自体にも、現状は`if __name__ == "__main__"`のスクリプト実行による目視確認しかなく、`unittest`形式の自動テストがありません。`fit_circle_kasa`・`fit_circle_taubin`・`fit_circle_to_ticks`についても、`tests/test_center_estimate.py`と同じ形式で`tests/test_circle_fit.py`を新規作成し、既知の中心・半径から生成した合成データを使って復元誤差が許容範囲内であることを確認するテストを書いてください（`circle_fit.py`の`_make_synthetic_ticks`・`_run_comparison`のロジックをテストのassertion付き版に転用できます）。

## 5. `meter_pipeline.py`への結線

`meter_pipeline.py`の32〜57行目にある`_detect_center(img)`が接続対象です。現状はHoughと目盛り側の2択ロジック（前述）で、戻り値は`(center_tuple, center_source_str)`のタプルです。`center_source`は呼び出し元（109〜110行目）で`result['center_source']`として結果に格納され、評価基盤やGUIで「どの手法で中心を決めたか」を追跡するのに使われています。この文字列の役割（`'hough'` / `'corrected'` / `'ticks'`）は維持しつつ、3候補版に対応した値（例: `'consensus'`＝3候補一致、`'fallback_2'`＝2候補判定にフォールバック、`'single'`＝候補1つのみ）を追加する形で拡張してください。**戻り値の型（`(x, y)`のタプルまたは`None`、`str`または`None`のペア）は変えないこと** — 呼び出し側の111〜114行目がこの型を前提にしているためです。

`_detect_center`の中身を、2.で設計した3候補統合ロジックを呼ぶ形に書き換えてください。Hough候補は`detect_meter_center_v2.detect_meter_center_from_raw(img)`、目盛り検出は既存の`tick_detect.detect_scale_ticks`（`estimate_center`が内部で使っているのと同じ関数）を使って`ticks`を1回だけ求め、それを`estimate_center(img, ticks)`と`fit_circle_to_ticks(ticks, method="taubin")`の両方に渡す設計にしてください（2.で述べた「独立ではない」という限界はこの実装からも分かります）。

## 6. 開発環境の注意点

- Python 3.8.8、`venv`使用。テストランナーは**pytestではなくunittest**（`tests/test_regression_logs.py`のdocstringに実行コマンドあり）。
- **`print()`に絵文字を使わないこと。** 日本語Windowsのコンソールはcp932で、絵文字（サロゲートペア文字含む）を出力すると`UnicodeEncodeError: 'cp932' codec can't encode character`でクラッシュします。今日、別メンバーの提出物で実際にこのクラッシュが再現しています。ログ・print文には日本語テキストと半角記号のみを使ってください。
- 全角パス対応: 画像の読み書きは`cv2.imread`/`cv2.imwrite`ではなく、`cv2.imdecode(np.fromfile(path, dtype=np.uint8), cv2.IMREAD_COLOR)`と`cv2.imencode`+`.tofile()`を使うこと（`detect_meter_center_v2.py`の`main`関数が既にこの作法に従っているので、そのまま真似てよい）。
- コミットメッセージは日本語で。
- 企業提供の実写真（`recieved_meter`、`気密試験_昇圧前圧力計.jpg`等）はSlack経由で共有済みなのでローカルでの検証利用は問題ありません。**ただしgitへのコミット・pushはまだ避けてください。** 日本製鋼所様への外部利用許可の確認（`tasks/先方への確認事項.md` 質問9）がまだ回答待ちのためです。テスト・検証には`meter1.png`〜`meter4.jpg`と`tests/fixtures/`（いずれも非工場データ、git管理下）を優先的に使ってください。
