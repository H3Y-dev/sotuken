# 3. プロジェクトの背景と目的

このプロジェクトは、**工場に設置されたアナログメーター（針が回るタイプの計器）の写真から、針が指している値を自動で読み取るシステム** を作るものです。人が現場を巡回して目視で記録している作業を、写真を撮るだけで済むようにするのが目的です。

システムは大きく次の順で動きます。

1. 写真からメーターの盤面と針を見つける
2. 盤面に刻まれた **目盛り線** を検出する
3. 盤面に書かれた **目盛りの数字**（0, 5, 10, 15 …）を OCR で読み取る
4. 「この位置が 0、この位置が 15」と分かるので、針の角度から実際の値を計算する

**ここで YMさんの担当が効いてきます。** 3 で数字が読めないと、そのメーターが「0〜15A」なのか「0〜60A」なのかが分かりません。目盛りの範囲が分からなければ、針の角度が正確に分かっていても値を計算できません。**つまり、数字が読めない = 読み取りそのものが失敗する**、ということです。

そして今、現場の写真の多くは **スマホを横に持って撮ったせいで90度回転しています**。盤面の数字が横倒しになっているため、OCR がほとんど読めていません。ここを直せば、システム全体の成功率が一気に上がります。**YMさんの担当は、全体のボトルネック（一番詰まっている場所）を直す仕事です。**

# 4. YMさんの担当タスク: T3「画像の向き正規化とOCR強化」

## 一文で言うと

**画像を4方向（0度・90度・180度・270度）に回してそれぞれ OCR にかけ、一番たくさん数字が読めた向きを採用する。**

やることはこれだけです。難しいアルゴリズムを考える必要はありません。「4回試して一番良かったものを選ぶ」という、素直な方法です。

## なぜこれで解決するのか

正しい向きに戻った画像では、数字がまっすぐ立つので OCR が読めます。読めた数字の個数は、正しい向きのときに明確に多くなります。だから「読めた個数が最大の向き」を選べば、正しい向きが分かります。**「向きを当てる」問題を「個数を数える」問題に置き換えているのがポイント** です。

## 効果の測り方（これが一番大事）

このタスクの良いところは、**効果が数字ですぐ見える** ことです。

`scale_value_detect.py` の中に `read_scale_numbers(img)` という関数があります。これは画像を渡すと、**読み取れた数字のリスト** を返します。リストの中身は次のような辞書（dict）です。

```
[{'value': 0.0, 'x': 120.5, 'y': 300.2, 'score': 0.95}, ...]
```

- `value` … 読み取れた数字そのもの
- `x`, `y` … その数字が画像のどこにあったか
- `score` … OCR がどれくらい自信を持っているか（0〜1）

つまり、**`len(read_scale_numbers(img))` がそのまま「読めた数字の個数」** になります。これを **回転前** と **回転後** で比べれば、効果が数字で出ます。

テスト用の写真は `C:\卒研\images\20260817_*.jpg` に13枚あります。**すべて90度回転した実機の写真** です。13枚それぞれで「前 → 後」の個数を並べれば、それがそのまま成果の報告になります。

## 受け入れ条件（これを満たせば完了）

1. 回転した写真で、OCR が読める数字の個数が **増える**（13枚の数値で示せること）
2. 正対した写真（もともと回転していない写真）で結果が **悪化しない**
3. 判定にかかる時間が許容範囲であること。OCR を4回走らせるのが重すぎる場合は、より軽い判定方法を検討する

条件2について補足してください。同じ個数だった場合は 0度（元のまま）を優先する、といった工夫が必要になります。これは YMさん自身に「同点のときどうする？」と考えてもらうのに良い問いです。

## 必ず守る技術的な注意（知らないと確実にハマります）

### (A) 日本語を含むパスの画像は `cv2.imread` では読めません

`C:\卒研\...` のようにパスに全角文字が入っていると、`cv2.imread` は **エラーを出さずに `None` を返します**。「なぜか画像が読めない、しかもエラーも出ない」という一番厄介な詰まり方をします。

**必ず次の書き方を使ってください。** これは丸暗記する必要はなく、コピーして使う定型句として扱って構いません。

```python
import cv2
import numpy as np

def imread_ja(path):
    """全角文字を含むパスでも画像を読み込めるようにした cv2.imread の代わり。"""
    data = np.fromfile(path, dtype=np.uint8)   # ファイルをバイト列として読む
    return cv2.imdecode(data, cv2.IMREAD_COLOR)  # バイト列を画像に変換する
```

YMさんが最初のスクリプトを書くときに、**必ずこれを先に渡してください。**

### (B) 画像の回転は OpenCV の関数を使う

```python
cv2.rotate(img, cv2.ROTATE_90_CLOCKWISE)        # 時計回りに90度
cv2.rotate(img, cv2.ROTATE_180)                  # 180度
cv2.rotate(img, cv2.ROTATE_90_COUNTERCLOCKWISE)  # 反時計回りに90度（＝270度）
```

0度は「何もしない」＝ `img` そのままです。

### (C) Python 3.8 で動く書き方に限る

Python 3.8 は少し古いバージョンです。ネットで見つけたコードが動かない場合、**新しいバージョン向けの書き方かもしれません。** よくある例:

- `list[int]` のような型の書き方 → 3.8 では `List[int]`（`from typing import List` が必要）。そもそも型注釈は書かなくても動くので、迷ったら書かない
- `match` 文 → 3.8 にはありません。`if / elif` を使う
- `x := 1` のようなセイウチ演算子は 3.8 でも使えますが、無理に使う必要はありません

**エラーに `SyntaxError` と出たら、まずバージョン違いを疑ってください。**

### (D) `print()` に絵文字を使わない

Windows のコンソールで絵文字を出そうとすると `UnicodeEncodeError` で落ちます。`[OK]` `[NG]` のような文字で代用してください。

# 10. 想定される質問への答え（先回りして用意しておいてください）

**Q. OCR って何ですか？**
A. Optical Character Recognition（光学文字認識）の略で、**画像の中に写っている文字を読み取ってテキストにする技術** です。スマホのカメラで名刺を撮ると文字が取り込まれる、あれと同じです。このプロジェクトでは RapidOCR というライブラリを使っています。中身の仕組みを理解する必要はありません。「画像を渡すと、読めた文字と、その場所を返してくれる箱」だと思ってください。

**Q. なぜ4方向も試すんですか？1回で正しい向きを当てられないんですか？**
A. 「この写真は何度回っているか」を直接当てるのは、実は難しい問題です。一方で「読めた数字の個数」は簡単に数えられて、正しい向きのときに明らかに多くなります。**難しい問題を、簡単に測れる問題に置き換えている** わけです。4回試すのは力技ですが、確実で、しかも「なぜそう判断したか」が個数という数字で説明できます。研究の発表でも説明しやすい方法です。

**Q. OCR を4回も走らせて、時間がかかりすぎませんか？**
A. その心配はもっともです。ただし **まず測ってから考えましょう。** 実際に何秒かかるかを `time` で計測して、許容できる範囲なら何もしなくて構いません。遅すぎた場合にだけ、判定用に小さくした画像を使うなどの改善を考えます。**測る前に最適化しない**、というのはプログラミング全般で通用する大事な考え方です。

**Q. 画像を回転させたら、数字の座標がずれませんか？**
A. ずれます。回転後の画像で読み取った `x`, `y` は、回転後の画像の中での座標です。だから「向きを直した画像を、そのあとの処理でもずっと使う」という形にするのが素直な解決です。今は気にせず進めて、段階3で一緒に整理しましょう。

**Q. 自分が書いたコードが、他の人の作業を壊してしまわないか不安です。**
A. その心配があるからこそ、触ってよいファイルが決まっています。`orientation.py` と `tests/test_orientation.py` は **新しく作るファイル** なので、他の人のコードには一切影響しません。既存ファイルを変更しない限り、壊しようがありません。安心して書いてください。

**Q. こんな基本的なことを聞いてもいいですか？**
A. もちろんです。**分からないことは悪いことではありません。** 分からないまま進めて後で大きく手戻りするほうが、ずっと損です。むしろ、詰まったポイントを言葉にできるのは大事なスキルです。何度でも聞いてください。
