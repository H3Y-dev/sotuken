# メンバー向け資料をAIエージェントに作らせるときの依頼文テンプレート

`tasks/prompts/` のプロンプトや `tasks/roadmap/` のスプリント表を Codex 等へ生成させるときの雛形。
2026-08-27から2026-09-02までに4回、ほぼ同じ構成の依頼文を毎回書き起こしていたので固定した。

> [!important] 委任しても責任は移らない
> 生成物は必ず全文を読んでから配る。過去4回とも、そのまま出せる品質ではあったが毎回2〜3箇所直している
> （担当外の情報が混ざる、手順の粒度が担当者に合わない、古いテスト件数が残る、など）。

---

## 使い方

下の `【】` を埋めて、そのまま依頼文として渡す。**空欄のまま渡さないこと。**
エージェントは会話履歴を持たないので、ここに書いていないことは伝わらない。

---

## 1. 作業ディレクトリ

```
C:\卒研\git_stk\sotuken
```

## 2. 先に必ず読むファイル（絶対パスで書く）

- 【タスクの定義が書いてあるファイル】 ← これが唯一の情報源
- 【仕様の根拠になるファイル】
- 【書式と文体の見本にする既存ファイル】

「**これ以外から情報を持ってこない。書かれていることを並べ替えるのが仕事で、
タスクを増やす・減らす・受け入れ条件を書き換えるのは禁止**」と明記する。

## 3. 作成するファイル（絶対パス、新規か上書きかを明示）

- 【出力パス1】
- 【出力パス2】

## 4. 各ファイルに必ず含める構成

番号付きで列挙する。特に次は毎回入れる。

1. プロジェクト全体の目的・チーム体制・その人の担当範囲を3〜5行（**メンバーの支援AIは会話履歴を持たないため毎回必要**）
2. 今日やること（1タスクのみ、3時間で終わる粒度）
3. なぜ必要か（**工場の現場の情景で説明する**。抽象的な理由は伝わらない）
4. 受け入れ条件（元ファイルのチェックボックスをそのまま写す）
5. 検証のしかた
6. 守ってほしいこと
7. push前の確認
8. **最後に必ずやること：日報を書く**（下の9章の定型文をそのまま貼る。2026-09-03から必須）

## 5. 共通の事実（毎回、最新の値に更新してから渡す）

- 共通テストコマンド: `venv\Scripts\python.exe -m unittest discover -s tests`
- **現在のテスト件数: 【N】件**（← 必ず実測してから書く。古い数字を渡した事故が複数回ある）
- 着手前に `git fetch origin` と `git rebase origin/main`
- 企業提供画像・`manager.db`・出力CSVをコミットしない。`git add -A` は使わず個別に add
- `print()` に絵文字を使わない（Windowsのcp932で `UnicodeEncodeError`）

## 6. メンバーごとの書き分け（ここを外すと使い物にならない）

| 誰 | 書き方 |

| SKくん | プログラミング能力が高い。技術的な説明をそのまま書いてよい。ただし**スコープ外に手を出さないよう明示的に止める**（過去に指示外のタスクへ着手した実績あり） |
| SRくん | 頭は良いがgit操作、特にrebaseのコンフリクトでつまずく。**rebaseの手順を1コマンドずつ**書き、**コンフリクトが出たら自分で直さずスクリーンショットを送る**と明記する |
| YMさん | プログラミングに不安がある。**手順を番号付きで1つずつ**示す。専門用語には短い説明を添える。設計判断を求めない |

## 7. 禁止事項（毎回入れる）

- 指定したファイル以外を作成・変更しない
- git のコミット・push をしない
- 受け入れ条件を増やしたり、タスクの範囲を広げたりしない
- 絵文字を使わない
- 日本語で書く。読み手は初学者を含む

## 8. 完了報告の指定

「作成したファイルのパスと行数だけを報告し、本文の全文は報告に含めないこと」と書く。
これを書かないと生成物の全文が報告に載り、こちら側の文脈を無駄に消費する。

## 9. メンバーに書かせる日報の書式（定型文。プロンプト末尾へそのまま入れる）

完了報告・日報は各メンバーが自分のAIに書かせる運用（2026-09-03、ユーザー指示で必須化）。
**下の8項目で固定する。書式を毎回変えない。** 変えると過去の日報と突き合わせられなくなる。

1. 名前と日付
2. 今日のタスク名（タスクIDを付ける）
3. やったこと（3〜5行。着手できなかったことはそう書く）
4. 成果物（ファイルパス、**コミットハッシュ先頭7文字とブランチ名**、無ければ「未コミット」）
5. テスト結果（**コマンドと何件中何件パスか**。未実行ならその理由）
6. 受け入れ条件の達成状況（1つずつ達成／未達成）
7. **詰まったところ・分からなかったこと**（最重要。推測で進めた箇所を正直に。「特になし」で済ませない）
8. 次に必要なこと（次回やること、大久保に判断してほしいこと）

ファイル名は `日報_<名前>_<YYYYMMDD>.md`。Slackへファイル添付で投稿させる。

**なぜこの8項目か**

- **4と5があるとGitHubの実測と突き合わせられる。** 「やったと言っている」と「実際にpushされている」の
  食い違いは過去に複数回起きている。本人にハッシュとテスト件数を書かせて、こちらの確認コストを下げる
- **6があると次の指示の再開地点がそのまま決まる**
- **7を「特になし」で済ませないと明記する。** SRくんが設計書を無視して独自実装し、実行時エラーと
  設計違反を同時に出した件は、迷った時点で言ってもらえていれば防げた

注意書きも毎回添える。「できなかったことを隠さない」「推測で断定せず未確認と書く」
「企業提供画像の内容が分かる記述を含めない」「絵文字を使わない」。

## 渡した後にこちらでやること

1. **生成物を全文読む。** 特にメンバーごとの書き分けが効いているか
2. 古い数字（テスト件数など）が残っていないか grep する
3. 担当外の情報が混ざっていないか見る（KPくんに仕様書全文、など）
4. 直したうえで commit・push し、Slackへ渡す
5. **Slackの本文にMarkdownの表を貼らない。** 送信は成功するのに表だけ無言で消える
   （2026-09-03、YMさんへ渡す転記対象の表が丸ごと消えた実例あり）。箇条書きへ展開する
6. **投稿したら `slack_read_channel` で読み直して、本文が欠けていないか確認する。**
   message_linkが返ることは本文が届いた保証にならない

# Gemini用プロンプトのテンプレート（2026-09-08追加）

**メンバーへ渡すプロンプトの既定はGemini。** Antigravityは枠が持たないため
（`tasks/Antigravity使い方マニュアル.md` 8章）。Antigravity用との違いは1点に集約される。

> **Geminiはメンバーのパソコンの中のファイルを見られない。コマンドも実行できない。**

そのため、Antigravity用なら「既存コードを読んで把握して」で済むところを、
**必要な情報を全部プロンプトへ書き下ろす**必要がある。

## Gemini版で必ず入れる4点

2026-09-08にSR-04・KP-04・YM環境の3本を書き直して固まった型。

1. **「あなたはファイルを見られない」の明示**と、貼り付けを頼む言い方の実例
2. **必要なファイルの `Get-Content` コマンドを、絶対パス込みで先回りして書く**
3. **文脈の埋め込み。** 仕様表・競合の中身・エラー全文など、判断に要る情報を本文へ転記する
4. **開発環境の明記。** リポジトリを見られないので、書かないと古い書き方を出してくる

## 雛形

```
あなたはこれから、卒業研究のチーム開発に参加している【名前】さんの作業に伴走してください。

【重要な前提】
あなたは【名前】さんのパソコンの中のファイルを直接見ることができません。コードの中身やコマンドの
実行結果が必要なときは、「このコマンドを実行して、出力をそのまま貼り付けてください」と具体的に
頼んでください。

例:
「【ファイル名】の中身を見たいので、PowerShellで次を実行して、出てきた内容を貼り付けてください。
 Get-Content C:\卒研\git_stk\sotuken\【パス】」

プログラムを実行した結果やエラーもあなたには見えません。実行を指示したら必ず「出力をそのまま全部
貼り付けてください」と添えてください。エラーは途中を省略されると原因が分からなくなるので、
「省略せず全部で大丈夫です」と伝えてください。

【本人について】
【特性。やる気・スキル・つまずきやすい所】
1回の返答で示すのは次の一歩だけにして、一気に全手順を説明しないでください。
返答の冒頭に「現在: 手順3 / 全7手順」のように現在地を書いてください。
初めて出す専門用語には短い説明を添えてください。

【開発環境（正確に守ってください）】
リポジトリ: C:\卒研\git_stk\sotuken
OS: Windows 11（コマンドはPowerShell）
Python: 3.8.8。実行は venv\Scripts\python.exe（python ではなくこれ）
テスト: pytestは無い。標準のunittest
テスト実行: venv\Scripts\python.exe -m unittest discover -s tests
コミットメッセージ: 日本語

Python 3.8で動く書き方に限る。list[int] は使えない（List[int]、または型注釈を書かない）。
match文も無い。SyntaxError が出たら、まずバージョン違いを疑う。

【プロジェクトの背景】
【3〜5行。この研究が何で、本人の担当が全体のどこに効くか】

【今日のタスク: 【タスクID】 【タスク名】】
範囲: 【やること】
【やらないこと。次のスプリント送りにする範囲】

【仕様（変更しないこと）】
【表・JSON例・項目名などを全部ここへ転記する。「仕様書を見て」は通じない】

【受け入れ条件】
【計画書からそのまま】

【手順】
手順1. 【コマンド】 → 出力を貼り付けてもらう
手順2. …
（各手順に「こう出れば成功」を書く）

【絶対に守ること】
- meter_pipeline.py / meter_reader.py / scale_value_detect.py / tick_detect.py は変更しない（精度は凍結中）
- テストが落ちたときに、期待値やアサーションを緩めて通さない。理由が分からなければ大久保に相談する
- git add -A は使わない。変更したファイルを個別に指定する
- 企業提供画像・manager.db・出力CSV/JSONLをコミットしない
- print() に絵文字を使わない（cp932でUnicodeEncodeError）

【最後にやること: 日報】
【8項目。既存の記述を流用】

【最初にすること】
1.「準備できました」と伝える
2. 今日のタスクを2〜3行で説明する
3. 手順1のコマンドだけを渡し、出力を貼り付けてもらう
手順2以降の説明は、このタイミングではしないでください。
```

## Antigravity用との差分（書き換えるときの目印）

| Antigravity用 | Gemini用 |
|---|---|
| 「既存コードを読んで構成を把握する」 | 「`Get-Content` で貼り付けてもらい、構成を確認する」 |
| 「TODOが2箇所あります: ファイル:行番号」 | 同じ。ただし**周辺のコードも本文へ転記**する |
| 「仕様書 `tasks/spec/...` を参照」 | **仕様の中身をプロンプトへ全部転記** |
| 自動承認モードの注意（`reset --hard` 等で止める） | 不要。本人が手で打つので自然に止まる |
