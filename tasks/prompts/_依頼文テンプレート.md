# メンバー向け資料をAIエージェントに作らせるときの依頼文テンプレート

`tasks/prompts/` のプロンプトや `tasks/roadmap/` のスプリント表を Codex 等へ生成させるときの雛形。
2026-08-27から2026-09-02までに4回、ほぼ同じ構成の依頼文を毎回書き起こしていたので固定した。

> [!important] 委任しても責任は移らない
> 生成物は必ず全文を読んでから配る。過去4回とも、そのまま出せる品質ではあったが毎回2〜3箇所直している
> （担当外の情報が混ざる、手順の粒度が担当者に合わない、古いテスト件数が残る、など）。

---

## 使い方

下の `【】` を埋めて、そのまま依頼文として渡す。**空欄のまま渡さないこと。**
エージェントは会話履歴を持たないので、ここに書いていないことは伝わらない。

## 2. 先に必ず読むファイル（絶対パスで書く）

- 【タスクの定義が書いてあるファイル】 ← これが唯一の情報源
- 【仕様の根拠になるファイル】
- 【書式と文体の見本にする既存ファイル】

「**これ以外から情報を持ってこない。書かれていることを並べ替えるのが仕事で、
タスクを増やす・減らす・受け入れ条件を書き換えるのは禁止**」と明記する。

## 3. 作成するファイル（絶対パス、新規か上書きかを明示）

- 【出力パス1】
- 【出力パス2】

## 4. 各ファイルに必ず含める構成

番号付きで列挙する。特に次は毎回入れる。

1. プロジェクト全体の目的・チーム体制・その人の担当範囲を3〜5行（**メンバーの支援AIは会話履歴を持たないため毎回必要**）
2. 今日やること（1タスクのみ、3時間で終わる粒度）
3. なぜ必要か（**工場の現場の情景で説明する**。抽象的な理由は伝わらない）
4. 受け入れ条件（元ファイルのチェックボックスをそのまま写す）
5. 検証のしかた
6. 守ってほしいこと
7. push前の確認
8. **最後に必ずやること：日報を書く**（下の9章の定型文をそのまま貼る。2026-09-03から必須）

## 5. 共通の事実（毎回、最新の値に更新してから渡す）

- 共通テストコマンド: `venv\Scripts\python.exe -m unittest discover -s tests`
- **現在のテスト件数: 【N】件**（← 必ず実測してから書く。古い数字を渡した事故が複数回ある）
- 着手前に `git fetch origin` と `git rebase origin/main`
- 企業提供画像・`manager.db`・出力CSVをコミットしない。`git add -A` は使わず個別に add
- `print()` に絵文字を使わない（Windowsのcp932で `UnicodeEncodeError`）

## 7. 禁止事項（毎回入れる）

- 指定したファイル以外を作成・変更しない
- git のコミット・push をしない
- 受け入れ条件を増やしたり、タスクの範囲を広げたりしない
- 絵文字を使わない
- 日本語で書く。読み手は初学者を含む

## 8. 完了報告の指定

「作成したファイルのパスと行数だけを報告し、本文の全文は報告に含めないこと」と書く。
これを書かないと生成物の全文が報告に載り、こちら側の文脈を無駄に消費する。

## 9. メンバーに書かせる日報の書式（定型文。プロンプト末尾へそのまま入れる）

完了報告・日報は各メンバーが自分のAIに書かせる運用（2026-09-03、ユーザー指示で必須化）。
**下の8項目で固定する。書式を毎回変えない。** 変えると過去の日報と突き合わせられなくなる。

1. 名前と日付
2. 今日のタスク名（タスクIDを付ける）
3. やったこと（3〜5行。着手できなかったことはそう書く）
4. 成果物（ファイルパス、**コミットハッシュ先頭7文字とブランチ名**、無ければ「未コミット」）
5. テスト結果（**コマンドと何件中何件パスか**。未実行ならその理由）
6. 受け入れ条件の達成状況（1つずつ達成／未達成）
7. **詰まったところ・分からなかったこと**（最重要。推測で進めた箇所を正直に。「特になし」で済ませない）
8. 次に必要なこと（次回やること、大久保に判断してほしいこと）

ファイル名は `日報_<名前>_<YYYYMMDD>.md`。Slackへファイル添付で投稿させる。

**なぜこの8項目か**

- **4と5があるとGitHubの実測と突き合わせられる。** 「やったと言っている」と「実際にpushされている」の
  食い違いは過去に複数回起きている。本人にハッシュとテスト件数を書かせて、こちらの確認コストを下げる
- **6があると次の指示の再開地点がそのまま決まる**
- **7を「特になし」で済ませないと明記する。** SRくんが設計書を無視して独自実装し、実行時エラーと
  設計違反を同時に出した件は、迷った時点で言ってもらえていれば防げた

注意書きも毎回添える。「できなかったことを隠さない」「推測で断定せず未確認と書く」
「企業提供画像の内容が分かる記述を含めない」「絵文字を使わない」。

## 渡した後にこちらでやること

1. **生成物を全文読む。** 特にメンバーごとの書き分けが効いているか
2. 古い数字（テスト件数など）が残っていないか grep する
3. 担当外の情報が混ざっていないか見る（KPくんに仕様書全文、など）
4. 直したうえで commit・push し、Slackへ渡す
5. **Slackの本文にMarkdownの表を貼らない。** 送信は成功するのに表だけ無言で消える
   （2026-09-03、YMさんへ渡す転記対象の表が丸ごと消えた実例あり）。箇条書きへ展開する
6. **投稿したら `slack_read_channel` で読み直して、本文が欠けていないか確認する。**
   message_linkが返ることは本文が届いた保証にならない
