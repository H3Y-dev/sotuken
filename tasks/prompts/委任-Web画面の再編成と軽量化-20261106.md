## 背景とユーザー(大久保)の要望
現在の画面は、`app.py`(471行)に、タブ4つ(読み取り / 記録 / 点検結果 / 点検ルート)と、サイドバー(スマホの送信先、QR登録)が全部入っている。要望は2つ: **(1)もう少し分かりやすい構造にしたい。(2)動作が重いので軽量化したい。** 決定済みの方針(ユーザー確認済み): ①画面の主役は「*点検の結果を確認する管理者*」(現場の点検が完了したか、撮り忘れはないか、値は正常か、を点検ごとに見る)。②構造は「*目的別に再編成*」。③見た目(方眼紙風の背景、タブのデザイン、CSS)は**現在のものを維持**する。構造と文言だけを整理する。

## 現状の問題(読んで確かめる。`app.py`、`manager/inspection_ui.py`、`manager/routes_ui.py`、`manager/pending_images.py`、`manager/export.py`、`manager/manager.py`)
- **重さの最有力候補**: `st.tabs` は、*選ばれていないタブの中身も、毎回の再実行で全部実行する*。記録タブ(DBの全件取得、画像のサムネイル、表の組み立て)や点検結果タブが、「読み取り」タブを見ているだけでも毎回動く。さらに、ウィジェットを1つ操作するたびにスクリプト全体が再実行される。他の候補: モジュール読み込み時の重い処理(OCR・画像処理のimport。`manager.pipeline_caller` など)、毎回の `get_history()` などの全件取得、全履歴の表の全行描画、画像の毎回の読み込み。
- **構造の分かりにくさ**: 「記録」タブが1枚の長いページで、(読み取りの記録の絞り込み → 点検の選択 → 点検の受信状態 → ルートの撮影状況 → この点検のメーター一覧 → 各メーターの最新の読み取り → 全履歴(折りたたみ) → 機器別の推移)が混在している。「点検結果」タブ(機器ごとの判定。点検フローの「点検」とは別物)と「点検(巡回)」が名前で紛らわしい。主な用途(スマホから届く点検の確認)より、手動の画像読み取り(開発・評価用)が先頭のタブにある。

## 作ること

### 1. まず計測する(必須。着手の最初)
軽量化の前に、現状の重さを数字で押さえる。`tools/` に、計測用の小さなスクリプト(例: `tools/profile_web.py`。*コミットしてよい*)を作り、`streamlit.testing.v1.AppTest`(使えなければ、関数の直接呼び出しと `time.perf_counter`)で、(a)アプリの初回の実行時間、(b)ウィジェット操作後の再実行時間、(c)どの処理が時間を使っているか(cProfileの上位10件など)、を、*DBが空のとき*と、*テストデータが入っているとき*(一時DBに、点検つきの記録を200〜500件ほど作る)の両方で出す。結果を、PRの説明と `tasks/reports/web-profile-20261106.md` に、変更の前後で並べて書く。

### 2. 構造の再編成(目的別)
`st.tabs` をやめ、**選ばれた画面だけを実行する**切り替え(`st.navigation` / `st.Page`、または `st.radio`・`st.segmented_control` の横並びの選択+選ばれた画面の関数だけを呼ぶ。1.40.1で使えるものを選び、選んだ方式と理由をPRに書く)に変える。画面(名前は、現場の人が読める日本語)は次の構成:
- **ホーム**: いま何が起きているかの要約。受信口の状態(待ち受けURL)、「読み取り中 N枚」(`manager/pending_images.py`)、最近の点検(最新5件。点検名・状態(受信中/完了/不足あり)・写真の枚数・機器の数)。点検の名前から、その点検の画面へ移れる。
- **点検**: 点検の一覧(新しい順、状態つき)→ 選ぶと**その点検の詳細**: 状態、ルートの撮影状況(撮影済み/未撮影/追加)、この点検のメーター一覧(情報の出所つき)、写真の一覧(サムネイルは、表示中の分だけ)。点検の結果の書き出し(CSV/JSONL。現在の「点検の結果を書き出す」「JSONLを書き出す」)もここ。
- **機器**: 各メーターの最新の読み取り、機器別の推移(グラフ)、機器ごとの判定(現在の「点検結果」タブの内容)。※名前は「点検結果」から「機器の判定」などに変え、点検フローの「点検」と区別する。
- **ルート**: 現在の「点検ルート」タブ(そのまま移す)。
- **接続・設定**: 現在のサイドバーの内容(スマホの送信先URL、合言葉、スマホを登録するQR)を、ここへ集める。サイドバーには、受信口の状態の一行と、画面の切り替えだけを残す。
- **手動読み取り(開発用)**: 現在の「読み取り」タブ(画像を選んで読み取る)。*画面の末尾に置く*。この画面を開いたときだけ、重い処理(OCR・画像処理の読み込み)を行う(`manager.pipeline_caller` などの重いimportは、この画面の中で初めて行う遅延import)。
- 既存の機能(絞り込み(機器名・開始日・終了日・点検)、全履歴の表、CSV/JSONLの書き出し、再処理、更新ボタン・自動更新(既定オフ)、読み取り中の表示)は、**すべて残す**(置き場所が変わるだけ)。画面の名前・見出しの文言は、点検フロー(`tasks/design/点検フロー設計.md`)の用語に合わせる。

### 3. 軽量化(計測の結果で優先順位を決める。少なくとも、次を実施)
- 選ばれていない画面を実行しない(上の切り替え)。
- DBの読み込みは、`st.cache_data` で結果をキャッシュする(キャッシュのキーに、DBファイルの更新時刻や最大の記録番号を含め、新しい記録が入ったら、更新ボタン・自動更新で確実に最新になること)。
- 全履歴などの大きい表は、**ページ分け**(既定で最新100〜200件。「さらに表示」で増やす)にする。サムネイルは、表示中の行だけ生成・読み込みする(`image_cache.get_thumbnail_path` の既存のキャッシュを使う)。
- 自動更新は、`st.fragment(run_every=...)` で、*必要な部分だけ*を更新する(ページ全体を再実行しない)。
- 重いモジュールの読み込みは、必要になったときまで遅らせる(遅延import)。
- 計測で見つかった、その他の無駄(同じDB読み込みの重複、毎回のファイルのハッシュ計算など)。
