# 依頼: Androidアプリ「点検フロー」の画面案(静的HTMLのモック)を3案作る

作業場所(この中だけ触る): C:\卒研\git_stk\sotuken-wt-ui (ブランチ docs/ui-mockups、main 2f65ac8から)
成果物(新規): `tasks/design/ui案/案A.html`、`案B.html`、`案C.html`、`tasks/design/ui案/README.md`。コードは変更しない。実装(Kotlin)はしない。
使うSkill: `frontend-design`(見た目の方向性)、日本語の画面文言は `yomiyasu` で整える(文言の意味・専門用語は変えない)。

## 背景
卒研のメーター読み取りシステム。Androidアプリ(Jetpack Compose)で、工場内の複数のメーターを撮って回り、PCへ送る。いまのアプリは「撮影→1枚ごとに送信箱に積む→履歴で確認」という写真単位の作りで、点検という単位がない。
現行の画面の構造は、次のファイルを読んで把握する(読むだけ): android/app/src/main/kotlin/jp/sotuken/metercapture/ui/MeterCaptureApp.kt、ui/QueueListScreen.kt、ui/QueueDisplay.kt、ui/PairingScreen.kt。

## ユーザー(大久保)が決めた要件
1. **最初に「点検」を作成する**(工場内の複数のメーターを読んで回る単位)。点検名(または日付からの自動名)・担当者・場所などの最小限の入力。
2. 点検の中で、メーターを1つずつ撮る。撮るときに **機器名のQR**(機器ラベルのQR。`{"v":1,"id":"A-101","name":"ボイラー圧力計",...}`)を読むと、機器名と機器IDが自動入力される(手入力もできる)。**撮った写真と、機器名・機器ID・撮影時刻などの情報は、必ず紐づけて見える**(例: 点検中の一覧の1行=1枚の写真+機器名+機器ID+撮影時刻)。
3. 点検中に、その点検で撮ったメーターの履歴(何を撮ったか、何枚か、撮り直し・削除)を確認できる。
4. 「点検完了」ボタンを押すと、その点検が **送信待ち** になる。
5. Wi-Fi接続(PCの受信口に届くこと)が確認できたら **自動で送信**する。
6. 無線が使えないときは **USBテザリング**(スマホをUSBでPCにつなぎ、テザリングを入れる)で同じ送信をする。アプリ側は、接続の種類(Wi-Fi/USBテザリング/未接続)と、PCに届くかどうかを表示するだけでよい。
7. 送信の形は、写真1枚ずつに **点検ID** を付けて送り、完了時に写真の一覧(manifest)を小さなJSONで送る(まとめて1つのzipにはしない)。つまりアプリの画面では「点検」が送信の単位に見えるが、中身は写真単位。点検の状態は 作業中 → 送信待ち → 送信中 → 送信済み(一部失敗あり)で表示する。

## 画面案に含める画面(各案で同じ範囲。静的HTMLで、スマホ幅 360〜412px、1ファイルに画面を縦に並べて見せる)
1. 点検の一覧(ホーム): 作業中・送信待ち・送信済みの点検、「新しい点検を作る」。接続状況(Wi-Fi/USBテザリング/未接続、PCに届くか)の常時表示。
2. 点検の作成。
3. 点検中の撮影画面: 機器QRを読むボタン、機器名・機器IDの表示、撮影ボタン、いま何枚撮ったか。「点検完了」への導線。
4. 点検中の履歴: その点検で撮った写真の一覧(写真・機器名・機器ID・撮影時刻)、撮り直し・削除、撮っていない機器がわかる工夫(点検対象の機器の一覧が事前にあれば、ただし無いときも成り立つこと)。
5. 点検完了の確認(枚数、機器の数、未撮影や重複の注意)と、完了後の送信待ち状態。
6. 送信中・送信済み・一部失敗(失敗した写真だけ再送)の状態の見せ方。
7. 接続が無いときの案内(Wi-Fiが無い→USBテザリングの手順を短く)。

## 案の違い(方向性を変えて3案)
- 案A: 「現場で手袋・片手でも押せる」を最優先。大きなボタン、少ない文字、1画面1操作。
- 案B: 「点検の進み具合が一目でわかる」を優先。チェックリスト/進捗バー型。点検対象の機器の一覧が事前にある場合に強い。
- 案C: 「情報量を保ちつつ整理」。現行アプリの見た目(Material 3)の延長で、実装コストを最も小さく保つ案。
各案の先頭に、その案の狙い・長所・短所・実装の重さ(小・中・大)を3行で書く。
