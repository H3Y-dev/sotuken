## 2. 8/26にmainで変わったこと（T6に影響します）

### 2-1. `read_meter` の戻り値に `ticks` が増えました

`meter_pipeline.read_meter(img, use_vlm=True)` が返す辞書に、**`ticks` キーが追加されました。** 検出した目盛り線のリストで、各要素は次の形です。

```python
{'angle': float,        # 中心から見た角度（ラジアン）
 'centroid': (x, y),    # 画像上の座標
 'line_angle': float,
 'length': float,
 'is_major': bool,      # 主目盛りかどうか
 'synthetic': bool}     # 検出できず計算で補った点なら True（無い場合もある）
```

**辞書のキーを固定で列挙している箇所があると、そこに影響が出る可能性があります。** 保存層で `result` をそのままDBやJSONへ書いている場合、`ticks` は件数が多く（1枚あたり20〜85個）そのまま保存すると肥大化するので、**保存対象から除くか、件数だけ記録する形にしてください。**

### 2-2. `--no-vlm` の意味が変わりました（重要）

これまで `use_vlm=False` は「盤面クロップのAI呼び出しだけ」を止めており、**目盛り数値を読む処理の中からは毎回AIモデル（Ollama）へ問い合わせが飛んでいました。**

その結果、**同じ画像・同じコードでも実行のたびに結果が変わる**状態でした。実測では、同じ写真を4回読ませて1回目だけ違う値が出ています。

8/26にこれを修正し、**`use_vlm=False` は本当にAI呼び出しを一切行わなくなりました。**

T6への影響はこうです。

- **Ollamaが動いていない環境でも、`use_vlm=False` なら安定して動きます。** テストやCIで使うならこちらを指定してください
- **`use_vlm=True`（デフォルト）のままだと、Ollamaの状態次第で結果が変わります。** 記録システムとして「同じ写真を読み直したら違う値が出た」は説明が難しいので、**運用でどちらを使うかは本人（大久保）と相談してください**
- `manager` 配下のテストで `read_meter` を呼んでいる箇所があれば、**`use_vlm=False` を明示してください。** そうしないとテストの結果が実行環境に依存します

## 3. T6-3の残っている受け入れ条件

- [ ] 写真を投入すると自動で読み取られ記録される（フォルダ監視 or バッチ）
- [ ] 同じ写真を二重に取り込まない
- [ ] 読み取り失敗した写真に人が手で値を入力できる

### 設計上の助言

**「同じ写真を二重に取り込まない」の判定は、ファイル名ではなく中身で行ってください。** 現場では同じ名前で撮り直される可能性があります。ファイルのバイト列のハッシュ（`hashlib.sha256`）を取って、それをキーにするのが確実です。ファイル名も一緒に記録しておけば、後から人が探せます。

**「読み取り失敗した写真に手で値を入力できる」は、失敗した写真だけでなく、成功した写真の値も直せるようにしておいてください。** 読み取りが成功していても値が間違っていることがあります（実際、誤差の数値上は良く見えるのに、目盛りの範囲を誤検出していた事例がありました）。**自動で読んだ値なのか、人が直した値なのかを区別して記録する**と、後で精度を集計するときに役立ちます。
