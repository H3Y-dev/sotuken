### ステップ1: 絞り込み機能を保存層に足す

`storage.py`の`get_all_readings()`を拡張するのではなく、新しく`get_readings(device_name=None, date_from=None, date_to=None)`のような絞り込み専用メソッドを足すのが素直です（既存の`get_all_readings()`は内部実装やテストで使われているので、シグネチャは変えずに残してください）。SQL文は保存層の中だけに閉じ込める、という`SRくん-Gemini用.md`で最初に伝えた方針をそのまま維持してください。

```python
def get_readings(
    self,
    device_name: Optional[str] = None,
    date_from: Optional[str] = None,
    date_to: Optional[str] = None,
) -> List[MeterReading]:
    """機器名・日付範囲で絞り込んで記録を取得する"""
    query = "SELECT id, timestamp, device_name, value, stage, image_path, raw_data_json FROM meter_readings WHERE 1=1"
    params = []
    if device_name:
        query += " AND device_name = ?"
        params.append(device_name)
    if date_from:
        query += " AND timestamp >= ?"
        params.append(date_from)
    if date_to:
        query += " AND timestamp <= ?"
        params.append(date_to)
    query += " ORDER BY id DESC"
    # 以下は get_all_readings と同じ組み立て方
```

`manager.py`側にも、これを呼ぶ薄いラッパー（例: `get_history(device_name=None, date_from=None, date_to=None)`の引数を増やす形）を足してください。**既存の呼び出し元（`format_history_for_cli`/`format_history_for_ui`）が引数無しで呼んでも壊れないよう、デフォルト値は必ず`None`にしてください。**

### ステップ2: CSV出力

新規ファイル`manager/export.py`を作り、`export_to_csv(readings, output_path)`関数を実装してください。`readings`は`get_readings()`が返す`MeterReading`のリストをそのまま受け取れる形にします。

```python
import csv
from typing import List
from storage import MeterReading


def export_to_csv(readings: List[MeterReading], output_path: str) -> None:
    """読み取り履歴をCSVファイルに書き出す。Excelで開いても文字化けしないようutf-8-sigを使う。"""
    with open(output_path, "w", encoding="utf-8-sig", newline="") as f:
        writer = csv.writer(f)
        writer.writerow(["ID", "日時", "機器名", "値", "ステージ", "画像パス"])
        for r in readings:
            writer.writerow([r.id, r.timestamp, r.device_name, r.value, r.stage, r.image_path])
```

`utf-8-sig`にする理由は、`tasks/T6-仮要件.md`の「既存の記録がExcelである可能性が高い」という仮定に合わせるためです（`utf-8`だとExcelで日本語が文字化けします）。

**この`export_to_csv`は、実はKPくんに任せるのにちょうど良い独立タスクです。** 「`List[MeterReading]`を受け取ってCSVファイルに書き出す」という入出力がはっきりした純粋関数で、保存層のDB操作を一切知る必要がなく、単独でテストできます（ダミーの`MeterReading`のリストを自分で作って渡すだけで動作確認できる）。次の「3. KPくんとの分担について」で詳しく触れます。

## 3. KPくんとの分担について

これまでの日報を見る限り、**T6は「SRくんリード＋KPくんサポート」の2人体制として設計しましたが、実際にはSRくんの単独作業が続いており、KPくんの動きが08-21・08-24・08-25と3回連続で確認できていません。** これは咎めるための指摘ではなく、分担の渡し方自体を見直すタイミングという提案です。

**T6-2の中で、`export_to_csv`をKPくんの独立タスクとして切り出すことを提案します。** 理由:
- 入力（`List[MeterReading]`）と出力（CSVファイル）がはっきりしている
- SRくんの保存層・絞り込みロジックの完成を待たずに着手できる（ダミーデータで動作確認できるため）
- KPくん自身が「Excelで開いて文字化けしないか」を目で確認でき、達成感を得やすい

KPくんには別途、この`export_to_csv`だけに絞った独立プロンプト（`tasks/prompts/KPくん-独立タスク-20260825.md`）が渡されます。**SRくんが先に`MeterReading`の形（フィールド名と型）をKPくんに一言で伝えてから任せる**のが、`SRくん-Gemini用.md`第9節で説明した「良い分担の条件」に沿った進め方です。KPくんの成果物（`export.py`）が上がってきたら、SRくんが`storage.py`の絞り込み結果と組み合わせる形で統合してください。
