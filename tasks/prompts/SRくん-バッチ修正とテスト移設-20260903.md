### SR-03-a: `manager/batch.py` の実行時エラーを直す

`manager/batch.py` の35行目です。

```python
if res.stage == "ok":
```

`manager.process_image()` は**辞書**を返すので、これは `AttributeError` になります。正しくは次のとおりです。

```python
if res["stage"] == "ok":
```

`process_image` の戻り値は `{"reading": ..., "val": ..., "stage": ..., "is_alert": ..., "alert_message": ...}` です。実物を `manager/manager.py` で確認してから直してください。

### SR-03-c: 重複排除を画像のハッシュ値へ変える

現状の `get_unprocessed_images()` は**絶対パス**で既処理を判定しています。

```python
processed_paths = {row['image_path'] for row in self.manager.format_history_for_ui()}
return [f for f in all_files if os.path.abspath(f) not in processed_paths]
```

これだと、**同じ写真が別の名前でコピーされたら二重に取り込まれ、ファイルを移動したら再処理されます。** SRくん自身が設計メモの3章で「画像のハッシュ値」と書いたとおり、**中身で判定する形へ変えてください。**

方針は次のとおりです。

- 画像ファイルの内容から SHA-256 を計算する関数を作る（`hashlib.sha256` を使い、大きなファイルでも困らないよう**チャンク単位で読む**）
- 既に処理した画像のハッシュ一覧と照合して、未処理のものだけ返す

**ハッシュの保存場所をどうするかは、判断に迷うところだと思います。** 既存のDBに列を足すのか、別に持つのか。**迷ったら、迷ったまま実装せず、日報の「詰まったところ」に書いて大久保に相談してください。** 今回は「ファイルパスではなく中身で判定する形になっている」ことが達成できていれば十分です。

## 6. 守ってほしいこと

- 着手前に必ず `git fetch origin` と `git rebase origin/main` を実行する
- push は `git push --force-with-lease origin SRdevelopment`。**ただの `--force` は使わない**
- 企業提供画像・DBファイル（`manager.db`）・出力CSVをコミットしない。`git add -A` は使わず、変更したファイルを個別に指定して add する
- `print()` に絵文字を使わない（Windowsのcp932でUnicodeEncodeErrorになる）
- **テストが落ちたときに、期待値やアサーションを緩めて通さないでください。** 落ちた理由が分からなければ、そのまま日報に書いて大久保に相談してください
- `meter_pipeline.py` など読み取り側のコードは変更しない（精度は凍結中で、SRくんの担当範囲でもありません）
- 分からないことがあれば大久保に聞く

## 7. push前の確認

```text
git status
```

`git status` に見覚えのないファイル、特に企業提供画像・`manager.db`・出力CSVが出ていないか確認してください。変更したファイルを個別に `git add` して、コミットしてから push してください。

## 8. 最後に必ずやること：日報を書く

今回の作業が終わったら（途中で終わった場合も含めて）、日報をMarkdownファイル1枚にまとめてください。
ファイル名は `日報_<名前>_<YYYYMMDD>.md` です。書く内容は次の8項目です。
**分からない項目は「なし」と書き、空欄にしないでください。**

1. **名前と日付**
2. **今日のタスク名**（タスクIDを付ける。例: SR-03 バッチ処理の修正とテスト移設）
3. **やったこと** — 実際に手を動かした内容を3〜5行で。やろうとしたが着手できなかったことは、そう書く
4. **成果物** — 作成・変更したファイルのパス。コミットしたなら**コミットのハッシュ（先頭7文字）と
   ブランチ名**も書く。コミットしていないなら「未コミット」と書く
5. **テスト結果** — 実行したコマンドと、何件中何件パスしたか。実行していないなら「未実行」と、その理由
6. **受け入れ条件の達成状況** — 渡された受け入れ条件を1つずつ書き出し、達成／未達成を付ける
7. **詰まったところ・分からなかったこと** — **ここが一番大事です。** 解決できなかった点、判断に迷った点、
   推測で進めた箇所を正直に書いてください。「特になし」で済ませず、少しでも自信のない箇所は書き出してください
8. **次に必要なこと** — 次回やること、または大久保に判断・確認してほしいこと

### 日報を書くときの注意

- **できなかったことを隠さないでください。** 進捗が無かった日も、どこで止まったかが分かれば次の手を打てます。
  うまくいったように書かれるのが一番困ります
- **推測で断定しないでください。** 確認していないことは「未確認」と書いてください
- 企業提供画像そのものや、その内容が分かる記述を日報に含めないでください
- 絵文字は使わないでください（Windowsのcp932で文字化けします）
