## 0. プロジェクト全体

工場のアナログメーターを撮影し、PCで読み取って一覧・ファイルに残す5人チームです。SKはAndroid、SRは取り込み、YMは保存規約、KPは一覧・出力、大久保は全体判断です。今日はSR・YMが不在で、大久保が取り込みとオーバーレイを確認します。KPは一覧・書き出しを担当します。

10/21の発表で「画面の値が正しく保存・出力できる」と説明できるよう、実際の画面とJSONLを照合するのが目的です。既存コードは他メンバーとつながっているため今日は変更しません。

## 1. 準備

1. 作業クローンの場所を本人に聞き、`git status -sb` を実行してもらう。未コミット変更や未追跡ファイルがあれば消さず大久保に相談する。
2. cleanであれば `git fetch origin`、`git switch main`、`git pull --ff-only origin main` を1つずつ実行。エラー時は出力を大久保に渡して止まる。無理にrebaseしない。
3. `SETUP.md`のWeb UI手順で起動。「記録」タブを開く。履歴が0件なら大久保に非機密の検証データを相談する。既存DBの削除・上書きはしない。

## 2. 今日の確認（KP-04 / KP-05）

1. **版列**：一覧に「版」があるか確認。新しい処理結果で版の値が見えるか記録。旧記録の空欄はそのまま報告し、勝手に埋めない。
2. **機器名の絞り込み**：「すべて」の件数と、1つの機器名を選んだ件数をメモ。対象外の行が混ざらないか確認。データ構成によって同数でも正常なので、件数が必ず変わるとは決めつけない。
3. **日付の絞り込み**：開始日・終了日を指定し、表示行がその範囲にあるか確認。変更前後の日付条件と件数を記録。データ不足なら未確認と理由を書く。
4. **JSONLの行数**：絞り込みを「すべて」・全期間に戻し、「N件 / 全N件」のNをメモ。「JSONLを書き出す」→「JSONLを保存」を押す。空行を除いた行数がNと一致するか確認。
5. **JSONLの中身**：一覧にある同じ記録を1件選び、JSONLの `reading_id`・`device_name`・`value` を照合。画面に日時・判定がある記録では `captured_at`・`status` がnullになっていないかも確認。10/09のPR #42で修正済みなので、実際に確認する。
6. 各行が1個のJSONとして読めるか確認。手元のPythonが使える場合は下のコマンドを、ダウンロードしたファイル名に合わせて実行してよい。出力内容そのものはAIに貼らず、行数と成功/エラーだけ伝える。

```powershell
venv\Scripts\python.exe -c "import json,pathlib; p=pathlib.Path(r'readings_export.jsonl'); rows=[json.loads(s) for s in p.read_text(encoding='utf-8-sig').splitlines() if s.strip()]; print('JSON行数:',len(rows))"
```

実行場所はクローンのルート。`readings_export.jsonl`が別フォルダなら、そのファイルの実際の絶対パスを指定します。Pythonが使えなければ推測で成功にせず、大久保に検証を依頼してください。

**注意：現行app.pyの出力は絞り込みに関係なく全履歴です。** 絞り込み後の表示件数とJSONL行数が違うだけでバグと判定しません。上記4の全件表示に戻して照合します。この挙動は日報にも書いてください。

## 3. 守ることと終了条件

6項目を成功・失敗・未確認で報告。失敗時は操作手順とエラー全文を大久保へ渡し、修正・コミット・pushはしません。テスト結果や件数を推測しません。

企業提供画像・DB・CSV/JSONLそのものをSlackや外部AIへ送らない。AIには非機密の件数・項目名・伏せたエラーだけを伝えます。終わったら発表担当の8・10の読み合わせを行います。
