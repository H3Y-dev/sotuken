## 1. 何が起きたか

`20260817_134745.jpg`（丸型温度計、真値9.0℃）で、中心がメーター盤面の中心ではなく、**盤面下部の取り付けネジ（ソケット）付近**に誤検出されました。

| | 結線前（main） | 結線後（SKdeveropment） |
|---|---|---|
| 誤差 | 1.02%FS（OK） | **9.00%FS（NG）** |
| 検出中心 | 盤面の中心（針の付け根） | ネジのすぐ上あたり |
| `center_source` | `hough` | `consensus` |
| 目盛り検出点数 | 49本 | 58本 |

目盛り検出の点（オーバーレイ画像の緑の点）が、盤面の目盛りだけでなく**ネジのねじ山模様にまで伸びていました。** つまり、`tick_detect.detect_scale_ticks()` がネジのねじ山を目盛り線と誤検出しています。

## 2. 原因の見当（本人の仮説）

`center_consensus.py`のdocstringに、SKくん自身がこう書いていました。

> estimate_center と fit_circle_to_ticks はどちらも同じ tick_detect.detect_scale_ticks の結果（ticks）を入力に使う。（中略）目盛り検出そのものが誤っていれば、この2つは同じ理由で同時に外れる可能性がある。

**まさにこれが起きたと考えられます。** ネジのねじ山が目盛りとして混入した状態で `estimate_center` と `fit_circle_to_ticks` の両方を計算すると、**両方とも同じ理由でネジ寄りにズレます。** 3候補中「2つが一致」という判定基準では、この2つが（本来は間違っているのに）一致してしまい、`consensus`または`fallback_2_agree`として採用されてしまいます。

現在の誤検出対策（`_check_hough_radius_consistency`・`_check_hough_tick_distance`）は、**「Houghが単独でズレた場合」だけを想定しています。** 今回のように「目盛りベースの2候補（estimate/fit）が同じ理由で一緒にズレ、Houghの方が正しい」という逆のケースへの対策がありません。

## 3. お願いしたいこと

**対策の方向性は2つ考えられます。どちらか、または組み合わせで検討してください。**

### 案A: 目盛り検出結果（ticks）自体から、盤面の外側にある点を除外する

Hough検出（`hough["radius"]`）で盤面のおおよその半径が分かっているので、それより明らかに外側（例: 半径の1.3倍以上離れた位置）にある目盛り候補は、`estimate_center`・`fit_circle_to_ticks`に渡す前に除外する。**根本原因（ネジがticksに混入すること）を断つ対策です。**

### 案B: `resolve_center_consensus`側に、Hough vs 目盛りベース2候補の距離チェックを追加する

`n == 3`のケースで、estimate/fitが一致していても、**その一致点がHough候補と大きく離れている場合は、目盛りベース側を疑って棄却する**（Houghの方を単独採用するか、`None`にする）ロジックを追加する。**対症療法ですが、`center_consensus.py`側だけで完結します。**

**どちらのアプローチを取るか、まずSKくん自身に考えてもらってください。** 難しければ、案Bの方が触るファイルが`center_consensus.py`1つで完結するので着手しやすいはずです。
