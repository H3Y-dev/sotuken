```bash

venv\Scripts\python.exe evaluate.py eval/groundtruth.json --no-vlm -o eval/rep.json
```

### T1-4: 主目盛り（is_major）判定の再設計【本人】✅完了（2026-08-26）
**内容:** 目盛り位置の検出は完了したが、主目盛りの判定が壊れている。
OCRの数字を目盛りに対応付ける段階で失敗し、ゼロ点・フルスケール点が
誤った位置に付く。

**設計書:** `tasks/design/主目盛り判定の再設計.md`（着手前に必ず読む）

**実測（`気密試験_昇圧後`、主目盛りは0/50/100/150の4本）:**
23本を角度順に並べて主目盛りを記号化すると `MMM.M.................M` となり、
**主目盛りが3つ連続**していた（156.2/165.1/173.9度、間隔8.9度）。
実際は約88度間隔のはず。

原因は**撮影の遠近**。同じ副目盛りでも左上は長さ41〜55、右側は23〜31と
2倍近い差がある。`is_major` が「長さ > 全体中央値 * 1.3」という単一しきい値
なので、遠近差だけで左上が全部主目盛りと誤判定される。

**受け入れ条件:**
- [x] 主目盛りが連続しない（隣接するものを同時に主目盛りとしない）
- [x] 主目盛りが等間隔に現れる（既存の周期構造を使う）
- [x] ~~長さの比較を局所的に行う~~ → **長さを一切使わない方式に変更**（下記）
- [x] **目視で、マゼンタの点が実際の主目盛りに乗っている**（9枚を確認）
- [x] 回帰テストが通る（47件）

#### 結果

**9枚すべてで主目盛りが厳密に周期的になった。隣接する主目盛りはゼロ件。**
破綻例 `MMM.M.................M` は `M.......M.......M......` になった。

#### 採った方法（設計書から変更した点）

**長さは使わなかった。** 局所比較も試したが効かず、長さの分布を実測したところ
同じ種類の目盛りが3〜43までばらついており、**長さには主目盛りかどうかの情報が
ほとんど残っていない**ことが分かったため。

代わりに、数字が印字されているのは必ず主目盛りだという性質を使う。

1. 目盛りを円弧に沿った**通し番号**に直す（`_tick_slots`）。角度の刻み幅で
   割るので、検出漏れがあっても間隔を数え違えない
2. OCRの数字と通し番号の間に**直線を当てはめる**（`_fit_major_cadence`）。
   2点で決まる直線を総当たりし、最も多くの数字が乗るものを採る。
   誤読（100を108と読む等）は外れ値として落ちる
3. 傾き×数字の間隔＝**周期**、切片＝**位相**。周期を2以上に限定したので、
   主目盛りが隣接することは原理的に起きない

**実装は `tick_detect.py` ではなく `scale_value_detect.py`。** OCRの数字が
必要なので、目盛り検出の段階ではなく数値対応付けの段階に置いた。

**検証:** `tools_render_overlays.py` で画像を生成し目視 ＋ 評価基盤
**依存:** なし　**規模:** M　**ファイル:** `scale_value_detect.py`

### T1-6: OCRが0を読めない問題【本人】✅完了（2026-08-27）
**内容（当初の見立て）:** 針が0を指しているとき、針が0の目盛りを覆って検出できず、
ゼロ点が別の目盛りに対応付いてしまう、という仮説だった。

**実測（2026-08-26）:** `耐圧試験_昇圧前`で、針は正しく0を指し目盛りも正確に取れているのに、
**0の位置だけ検出点が無く**、ゼロ点が「100」に付いて引用誤差24.97%FS。

**2026-08-27の再調査で判明した真因:** 針の遮蔽ではなく、**RapidOCRの文字検出
段階が単独の「0」を検出候補にすら上げていなかった**（誤読ではなく検出漏れ）。
詳細・実測の裏取りは `tasks/design/T1-6-ゼロ点OCR検出漏れの対策.md`。

**検討済みで失敗した方法:**
VLMへの問い合わせ（`vlm_scale_value.check_needle_overlaps_zero`）は実装済みだが、
4枚すべてに同じ答えを返して機能しなかった（2026-08-25検証）。質問の仕方を
4通り試したが、A/B/Dは全画像に同一の回答で判別していない。**4Bモデルでは
遮蔽判定は成立しない。** 今回の解決策はVLMに依存しない形にした。

**実装した解決策:** ゼロ点を等間隔性から予測した座標に対して、複数の切り出し
半径（60/80/100/130px）で拡大再OCRを試し、実際に「0」を確認できた場合のみ
採用する（`_verify_label_near_position_multi`）。Codex（`gpt-5.6-terra`）が実装、
本人が診断・設計・検証を担当。

**受け入れ条件:**

- [x] 目視でゼロ点が正しい目盛りに乗っている（`eval/overlays/08,09`で確認）
- [x] 針が0を指していない画像で退行しない（他7枚の数値・テスト50件に変化なし）
