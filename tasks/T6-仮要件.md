## 確定していること（写真から読み取れた事実）

推測ではなく、`C:\卒研\images` の実機写真13枚から確認できた事実。

- メーターは**壁面のパネルに複数台まとまって設置**されている。1枚の写真に2〜3台写ることがある
- 各メーターの**すぐ隣に銘板**があり、機器名と定格が書かれている
  - 確認できた機器: `冷却水ポンプ 1.5kW`（0〜15A）、`冷却塔 0.6KW`（0〜5A）、`水冷式パッケージ NO.1 12.1KW`（0〜60A）、判読不能な「…ター」（0〜10A）、銘板なし（0〜75A）
- メーターの種類は電流計だけではない。**温度計（0〜100℃）**、**ブレーカ付きの扇形電流計**もある
- 計器はいずれも **JIS C 1102 2.5級**（確度±2.5%FS）
- 撮影は**スマホを横に持って**行われている（写真が90度回転している）

## 仮定した要件

### 1. 記録の単位

**仮定**: 「1回の点検」で複数のメーターを回り、それぞれの値を記録する。
写真1枚 = 1機器の記録、が基本単位。

**根拠**: パネルに複数台並んでおり、点検は巡回作業と考えるのが自然。
**覆った場合の影響**: 小。記録テーブルに「点検ID」を足すだけ。

### 2. 機器マスタが必要

**仮定**: 機器（メーター）を事前に登録しておく。
登録項目: 機器名、設置場所、計器の種類（電流計/温度計）、単位（A/℃）、
レンジ（最小値・最大値）、確度階級、正常範囲（あれば）。

**根拠**: 銘板に機器名と定格が書かれている＝現場に機器の識別体系がある。
また、レンジを事前に持っていれば**画像から読み取る必要が減り、精度が上がる**
（現在レンジの誤検出が失敗要因の一つ）。

> [!tip] これは設計上かなり効く仮定
> 「どの機器を撮ったか」を人が選ぶ or QRコード等で特定できれば、
> レンジ（0〜5Aなのか0〜60Aなのか）を画像から推定する必要がなくなる。
> 読み取り精度の問題が半分消える。**CV班にも共有する価値がある。**

**覆った場合の影響**: 中。マスタ無しでも動くよう、機器未登録でも値を保存できる形にしておく。

### 3. 記録する項目

| 項目 | 必須 | 備考 |
|---|---|---|
| 日時 | ○ | 撮影日時（画像のExifがあればそこから） |
| 機器 | ○ | マスタへの参照。未登録なら自由入力 |
| 値 | ○ | 読み取り結果 |
| 単位 | ○ | 機器マスタから |
| 元画像へのパス | ○ | 後から目視確認できるように |
| 入力方法 | ○ | `auto`（自動読取）/ `manual`（手入力）/ `corrected`（自動を人が修正） |
| 撮影者 | △ | 誰が点検したかの記録が要る運用は多い |
| 読み取りの信頼度 | △ | `read_meter()` が返す `stage` / `scale_source` をそのまま保存 |
| 備考 | △ | 異常時のメモ |

**根拠**: 既存のアナログ記録（紙の点検表）に一般的に含まれる項目。
`入力方法` を持つのは、**自動読取の精度が実運用に達していない現状**で、
どれが機械の値でどれが人の値かを区別できないと信用されないため。

### 4. 手入力のフォールバックは必須

**仮定**: 自動で読めなかった写真は一覧に出て、人が値を手で入れられる。

**根拠**: 現時点の自動読取は完全自動で引用誤差37%FSのケースがある。
**読めない写真が出るのは仕様**と考えて設計する。読めなかった写真が
どこにも残らない作りにすると、点検の記録が欠落する。

### 5. 出力形式

**仮定**: CSV（Excelで開く前提）。文字コードは `utf-8-sig`。
機器別・日付別の絞り込みと、値の推移グラフ。

**根拠**: 既存の記録がExcelである可能性が高い（工場の点検記録として一般的）。
`utf-8-sig` にしないとExcelで開いたとき日本語が化ける。

**覆った場合の影響**: 小。出力層だけの差し替えで済む——**だから保存層と
表示層を分けておく**（[[tasks/plan.md]] のガイドライン）。

### 6. 動作環境

**仮定**: 工場内のWindows PC。スマホで撮影した写真をPCに取り込んで処理する。

**根拠**: 現行のシステムがWindows前提のPythonアプリで、Ollama（VLM）を
ローカルで動かしている。スマホ単体で動かすには作り直しになる。

> [!warning] ここが覆ると影響が大きい
> 「スマホで撮ってその場で結果を見たい」という要件だと、Web化かサーバー化が必要になる。
> そのため**保存層をSQLite直叩きにせず、関数越しに触る**設計にしておく。
> 後からサーバー経由に差し替えられる余地を残す。

## 本要件が来たときに確認すること

優先順。上から3つが分かれば大半の設計が確定する。

1. **既存の記録様式（紙の点検表 or Excel）の実物**。項目・単位・粒度がすべて分かる。**これ1つで上の仮定の半分が確定する**
2. **誰が使うか**（点検担当者本人 / まとめる側 / 両方）
3. **どこで動かすか**（工場内PC / サーバー / スマホ）
4. 記録の保存期間、既存システムとの連携の要否
5. 機器の一覧（何台あるか、識別番号はあるか）

> [!tip] 先生に頼むなら「1」だけでも先にもらう
> 全部を待つより、**既存の点検表を1枚もらう**ほうが早く、得られる情報が多い。
> 部分的にでも先に来れば、そこから設計を詰められる。

## 進め方

SRくん・KPくんは**この仮要件に向けて作ってよい**。本要件を待つ必要はない。
ただし、上の「覆った場合の影響」が中〜大の項目は、差し替えられる形にしておくこと。

具体的には:
- 保存層（DBを触る部分）と表示層（画面・出力）を分ける
- 保存する項目は、後から足せるようにしておく（読み取り結果のdictはJSON1カラムに丸ごと逃がすなど）
- 機器マスタが無くても値を保存できる形にする
