# SRくんのSprint 1〜8ロードマップ

担当範囲はPC側の取り込みです。<br>
監視フォルダで画像を見つけ、サイドカーJSONを読み、既存パイプラインを呼び出すところまでを担当します。

各Sprintの着手前に必ず `git fetch origin` と `git rebase origin/main` を実行します。コンフリクトが出たら自分で直さず、画面のスクリーンショットを本人（大久保）へ送ってください。

1スプリント = 学校での作業日1回 = 3時間です。デモ予定は2026年10月末から11月初です。読み取り精度は2026-09-01に凍結済みで、この表には精度を改善するタスクは含まれません。

## 全体の流れ

```text
【SKくん】撮影(Android) → 未送信キュー(Android) [本人（大久保）]
        → 公開フォルダまたはHTTPで送出 [本人（大久保）]
        → 【SRくん: PC側の監視フォルダ → 取り込み → 既存パイプラインで読み取り】
        → 【YMさん】レコード保存（原画像・ログの保管を含む）
        → 【KPくん】CSV/JSONL出力・一覧・グラフ・アダプタ
```

### 検証のしかた

- S1-ALL: 合意メモを全員で読み合わせる。SKくんは雛形をビルドして実機起動を目視し、PC側は共通テストコマンドを実行する。
- SR-02: gitコマンドの結果と整理メモを本人へ提示し、S1の規則と矛盾がないことを目視確認する。
- SR-03: 監視中に画像を手動配置し、検出記録を目視する。共通テストコマンドを実行する。
- SR-04: 入力あり・未入力の2つのJSONを監視フォルダへ置き、読み取った値を目視する。
- SR-05: 既知画像を監視フォルダへ置き、呼び出し記録と受け取った結果を確認する。共通テストコマンドを実行する。
- SR-06: 同一画像を2回監視フォルダへ置き、パイプライン呼び出し回数とレコード件数を確認する。
- SR-07: 保存済み画像を指定して再処理し、旧新2件のレコードと`pipeline_version`を確認する。

> 計画書に名前だけ残っていた「SR-08（無線経路のPC側受け口）」は、2026-09-02に **O-05b として本人（大久保）の担当**になりました。**SRくんの担当ではありません。**送る側（Android）と受ける側を同じ人が作るほうがプロトコルの食い違いが起きないためです。受け口は監視フォルダへファイルを置くだけなので、SRくんのSR-03以降の取り込み処理はそのまま使えます。

## 待たなくてよいもの

SR-05はYMさんの保存層を待ちません。既存パイプラインを呼び、戻り値または失敗情報を受け取るところまでは独立しているためです。レコード保存への結線だけは、YM-03・YM-04がそろってから行います。

仕様書への依存と、他人の実装物への依存は別です。仕様書で確定した項目を参照するだけなら実装完成を待たず、実際に他の人のコードを呼ぶときだけ待ちます。

## 遅れたときに削るもの

1番目の削減候補は無線経路（O-05・O-05b）ですが、これは本人の担当なのでSRくんの表からは外れています。SRくんの担当で削減候補になっているのは6番目のSR-07（一括再処理）だけです。通しで1本通ること（Sprint 5）と、版間比較（Sprint 8）は削りません。
