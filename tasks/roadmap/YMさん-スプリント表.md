# YMさんのSprint 1〜8ロードマップ

担当範囲は、画像を読んだ結果を残す共通レコードと保存の決まりです。<br>
レコードとは「画像1枚を読んだ結果をまとめた1件の記録」です。原画像、ログ、画面に重ねるオーバーレイ画像も、決めた場所に保管します。

1スプリント = 学校での作業日1回 = 3時間です。デモ予定は2026年10月末から11月初です。読み取り精度は2026-09-01に凍結済みで、この表には精度を改善するタスクは含まれません。

## 全体の流れ

```text
【SKくん】撮影(Android) → 未送信キュー(Android) [本人（大久保）]
        → 公開フォルダまたはHTTPで送出 [本人（大久保）]
        → 【SRくん】PC側の監視フォルダ → 取り込み → 既存パイプラインで読み取り
        → 【YMさん: レコード保存、原画像・ログ・オーバーレイの保管】
        → 【KPくん】CSV/JSONL出力・一覧・グラフ・アダプタ
```

### 検証のしかた

- S1-ALL: 合意メモを全員で読み合わせる。SKくんは雛形をビルドして実機起動を目視し、PC側は共通テストコマンドを実行する。
- YM-02: 定義した項目一覧を仕様書第2節の表と1行ずつ照合し、共通テストコマンドを実行する。
- YM-03: 同一画像を2回投入してハッシュを照合し、保存ファイルを目視する。共通テストコマンドを実行する。
- YM-04: 3種類の結果と真値入力の有無を表で照合し、単体テストと共通テストコマンドを実行する。
- YM-05: 意図的な失敗入力で作成したレコードを仕様表と照合し、共通テストコマンドを実行する。
- YM-06: 1件処理後にログ、オーバーレイ、レコードの3つを目視照合する。
- YM-07: 通常取り込みと再処理をそれぞれ実行し、レコード件数・版・原画像パスを照合する。

## 待たなくてよいもの

YM-05はSR-05を待ちません。失敗分岐の列挙は既存パイプラインのコードを読めばできるためです。SRくんの取り込みが動いていなくても、パイプラインを直接呼んで検証できます。

仕様書への依存と、他人の実装物への依存は別です。仕様書で確定した項目を参照するだけなら実装完成を待たず、実際に他の人のコードを呼ぶときだけ待ちます。

## 遅れたときに削るもの

6番目の削減候補はYM-07の再処理時の新レコード追加です。通しで1本通ること（Sprint 5）と、版間比較（Sprint 8）は削りません。

- 企業提供画像・`manager.db`・出力CSVをコミットしない。`git add -A` は使わず個別にadd
- `print()` に絵文字を使わない
